# 검토 기록

## 의존성 선정

- `chacha20poly1305 0.10.1`: RustCrypto, 순수 Rust. 프로젝트는 NCC Group 감사 이력을 공개합니다. 과거 라이브러리 감사가 현재 앱 전체 또는 모든 후속 버전을 보증하지는 않습니다. https://docs.rs/chacha20poly1305/0.10.1/chacha20poly1305/#security-notes
- `argon2 0.5.3`: RustCrypto Argon2id 구현. 공개 구현과 명세·테스트를 검토하며, 이 버전의 독립 감사 완료를 주장하지 않습니다. https://docs.rs/argon2/0.5.3/argon2/
- `hmac 0.12.1`, `sha1 0.10.6`, `sha2 0.10.9`: RustCrypto의 OTP HMAC 및 난수 컨디셔닝. SHA-1은 TOTP HMAC에만 사용.
- `zeroize 1.8.2`: 민감한 Rust 버퍼와 Argon2 메모리 소거. 복사 방지·잠긴 메모리·커널 보호 기능과 동일하지 않음.
- `subtle 2.6.1`: OTP 비교에 사용. 런타임 조작/바이너리 패치를 막지는 않음.
- 전이 의존성은 Cargo.lock 고정. RNG 기본 기능을 꺼 Windows RNG 호출 경로를 제외. `rand_core`가 암호화 라이브러리의 타입 의존성으로 남아도 `OsRng`는 호출하지 않음.

## 보안 테스트와 리뷰

2026-10-16, Windows x64 / rustc 1.98.1 환경에서 검증했습니다. 전문 감사·침투 테스트·하드웨어 인증을 완료했다고 주장하지 않습니다.

- 내부 독립 에이전트 2명: 암호화·저장, Windows UI·보안 흐름을 각각 읽기 전용 검토. 발견 사항 수정 후 재검토. 마지막으로 표준 Enter/Escape 명령 매핑 권고까지 반영했습니다.
- 사용자 요청에 따라 `llm-analysis` MCP의 `delegate_analysis`를 통해 **claude-opus-5-5** 검토를 총 3회 받았습니다. 전체 소스 최초 검토 → 수정본 전체 재검토 → 마지막 UI 수정사항 집중 검토 순서입니다. 최초 원문은 `OPUS_INITIAL.md`, 두 번째는 `OPUS_FOLLOWUP.md`, 마지막은 `OPUS_FINAL.md`입니다. 각 MCP 응답 JSON(`opus-review-*.json`)도 보존했습니다. 검토 요청에 쓴 MCP 호출 스크립트는 개발 PC 설정에 묶여 있어 공개 저장소에는 넣지 않았습니다. 마지막 답변은 검토 범위에서 미해결 조치 사항과 즉각적인 회귀를 발견하지 못했다고 밝혔습니다. 이는 앱 전체의 무결점 인증이 아닙니다.
- 초기 검토의 일반 마스킹이 Rust 타입·테스트 숫자 일부를 변형한 제한이 있었습니다. 수정본 검토에는 사용자 정보가 없는 소스·가짜 테스트 데이터만 선별하여 정확한 원문을 제공했습니다.
- (2026-10-16 기준) 자동 테스트 총 17개 통과(라이브러리 13개, UI 4개). 2026-10-17 변경 후 수치는 아래 절을 보세요. AEAD 변조·잘린 파일·인증된 악성 구조·OTP 표준 벡터/재사용·생성/저장/백업/복원·잘못된 비밀번호·비밀번호 변경 실패 단계·동시 세션·하드링크/ADS·UTF 입력·네이티브 컨트롤 보호·페이지 표시 폭·지연 잠금/종료를 검사했습니다. 이후 변경한 부분은 해당 테스트를 다시 실행했습니다.
- Argon2id와 XChaCha20-Poly1305 고정 벡터를 각각 Python cryptography 및 PyNaCl/libsodium의 독립 결과와 대조했습니다.
- `cargo clippy --all-targets --locked -- -D warnings` 통과.
- OSV 질의로 Cargo.lock의 27개 레지스트리 패키지를 확인했으며 조회 당시 반환된 취약점은 0개입니다. 알려지지 않은 취약점까지 없다는 의미는 아닙니다. `dependency-audit.json`에 조회 시각·버전 기록.
- 릴리스 실행 파일의 `--self-check` 통과: 프로세스 완화 정책, Windows 버전, 캡처 제외 속성, 로컬 세션·디버거 확인, 타이머·RDSEED 초기화, 실제 입력 컨트롤의 암호 입력 범위 및 IME 분리.
- PE 헤더/직접 import 검사: `DependentLoadFlags=0x800`, CFG, Windows 암호화·난수 함수 직접 import 없음. 상세는 `binary-inspection.json`. 운영체제 DLL 내부 동작까지 추적한 검증은 아닙니다.

## 0.2.0 변경: OTP 등록 QR

이 변경도 외부 모델 검토를 받지 않았습니다.

- `src/qr.rs`: 바이트 모드, 버전 6(41×41), 오류 정정 M 전용 자체 인코더. 외부 QR 라이브러리를 쓰지 않은 이유는 OTP 비밀키가 담기는 코드워드·오류 정정·모듈 버퍼를 모두 `zeroize`로 지우기 위해서입니다. 등록 주소(`otpauth://totp/Goyo%20Vault?secret=…&issuer=Goyo%20Vault`, 87바이트)도 재할당 없이 만든 소거 버퍼에 담습니다.
- 독립 구현 대조: 같은 입력에서 8개 마스크 모두 python-qrcode 8.2와 모듈 배열이 완전히 같습니다(SHA-256 고정값을 테스트에 포함). segno 1.6.6은 기능 패턴·형식 정보·데이터가 같고, 바이트 경계에서 끝난 종료 비트 뒤에 `0x00`을 한 바이트 더 넣는 점만 다릅니다. ISO/IEC 18004는 이 경우 곧바로 채움 코드워드를 두므로 python-qrcode와 같은 방식을 택했습니다.
- 실제 화면에 그려진 QR(다크·라이트)을 zxing-cpp 디코더로 읽어 `otpauth` 주소 형식이 그대로 나오는 것을 확인했습니다. 실제 휴대폰 앱으로 스캔하는 확인은 하지 않았습니다.
- QR은 캡처 제외 창에 직접 그리며 파일로 저장하지 않습니다. 등록 키 글자를 화면에 표시하던 것과 노출 범위는 같습니다. 휴대폰 일반 카메라·렌즈 앱이 이미지를 클라우드로 보낼 수 있으므로 화면과 README에서 OTP 앱 내부 스캐너만 쓰도록 안내합니다.
- 자동 테스트 총 21개 통과(라이브러리 16개, UI 5개).

## 0.2.1 변경: 비밀번호 보기 버튼

이 변경도 외부 모델 검토를 받지 않았습니다.

- 비밀번호·확인·현재 비밀번호 칸에 눈 버튼을 추가했습니다(OTP 칸 제외). 기본은 가림이고, 누를 때만 표시합니다.
- 가림 해제는 앱이 원래 edit 프로시저를 직접 호출하는 경로뿐입니다. 서브클래스는 외부에서 보낸 `EM_SETPASSWORDCHAR`를 계속 버리므로, 2026-10-16 검토에서 막은 "다른 프로그램이 가림을 푸는" 경로는 그대로 닫혀 있습니다.
- `ES_PASSWORD`를 해제하면 edit 컨트롤이 IME 컨텍스트를 되돌려 놓는 것을 테스트로 확인했습니다. 그대로 두면 한글 입력이 켜지고 입력기가 비밀번호를 학습할 수 있습니다. 그래서 해제 직후 IME를 다시 분리하고 암호 입력 범위를 재적용하며, 둘 중 하나라도 실패하면 다시 가리고 오류를 표시합니다.
- 표시 중에도 복사·잘라내기, 외부 `WM_GETTEXT`, `WM_GETOBJECT`(접근성) 차단과 캡처 제외는 그대로입니다. 잠금·미사용 시간 초과·화면 전환으로 화면을 다시 만들면 새 칸은 가려진 상태입니다. 회귀 테스트가 이 항목들과 외부 `EM_SETPASSWORDCHAR` 무시, 잠금 후 재가림을 확인합니다.
- 남는 위험은 주변 사람이 화면을 직접 보는 것입니다. 사용자가 누를 때만 보이므로 사용자의 선택으로 남깁니다.

## 0.2.2 변경: 비밀번호 최소 길이, 열기 전 화면의 앱 전환

이 변경도 외부 모델 검토를 받지 않았습니다.

- 새 비밀번호 최소 길이를 16자에서 12자로 낮췄습니다. 서로 다른 글자 6개 이상 규칙과 Argon2id 설정(256 MiB, 3회)은 그대로입니다. 열쇠 파일을 가진 공격자는 OTP 없이 오프라인으로 비밀번호를 추측할 수 있으므로, 길이가 실제 방어선이라는 점은 README에 계속 적습니다. 기존 금고 열기와 파일 형식에는 영향이 없습니다.
- 다른 앱으로 전환할 때 잠그는 대상을 열린 금고로 한정했습니다. 금고를 열기 전 화면(열기·새 금고·복원)에는 풀린 비밀이 없으므로 입력 내용과 OTP 등록 정보를 유지하고, 눈 버튼으로 보이게 한 비밀번호만 다시 가립니다. 이전에는 OTP를 휴대폰에 등록하는 도중 전환하면 등록 키가 새로 만들어져 이미 등록한 OTP가 쓸모없어졌습니다. 입력 칸은 전환 중에도 외부 읽기·복사·캡처가 막혀 있고, 미사용 시간 초과(새 금고 5분, 나머지 60초)와 Windows 세션 잠금·절전은 계속 모든 입력을 지웁니다. 바쁜 동안 들어온 전환 이벤트도 같은 규칙을 따르며, 회귀 테스트가 두 경로를 확인합니다.

## 0.3.0 변경: OTP 백업

이 변경도 외부 모델 검토를 받지 않았습니다.

- 금고가 열린 상태에서 **OTP 백업**을 누르고 현재 비밀번호를 다시 입력하면, 세션이 가진 TOTP 비밀키를 생성 때와 같은 QR·등록 키로 보여 줍니다. 비밀번호는 세션의 열쇠 파일 사본으로 Argon2id 검증하고(`Session::otp_setup`), 실패는 다른 인증과 같은 재시도 대기 시간을 적용합니다.
- 등록 키를 금고 항목으로 저장하는 방식은 택하지 않았습니다. 금고를 열려면 OTP가 필요하므로 휴대폰 분실 시 꺼낼 수 없고, 백업이 된 것처럼 오해하게 만듭니다.
- 비밀키는 `OtpSetup`(소거 버퍼)에만 담겨 화면을 닫거나 잠글 때 버려집니다. QR은 캡처 제외 창에 직접 그리며 파일로 저장하지 않습니다. 표시 중 미사용 잠금 시간은 등록 화면과 같은 5분이고, 다른 앱 전환·세션 잠금 때는 금고와 함께 바로 닫힙니다.
- 남는 위험: 열린 금고 앞에 앉은 사람이 비밀번호까지 알면 자기 기기에 OTP를 등록할 수 있습니다. 그 사람은 이미 열린 금고의 모든 항목을 볼 수 있는 상태이므로 새로 생기는 노출은 크지 않다고 판단했습니다.
- 회귀 테스트: `Session::otp_setup`이 맞는 비밀번호에서만 생성 때와 같은 키·URI를 돌려주는지, UI에서 틀린 비밀번호는 표시하지 않고 대기 시간을 거는지, 닫기·앱 전환 잠금이 비밀키를 버리는지 확인합니다. 자동 테스트 총 22개 통과(라이브러리 16개, UI 6개).

## 0.3.1 변경: 앱 전환 즉시 잠금 → 30초 유예

이 변경도 외부 모델 검토를 받지 않았습니다.

- 이전에는 다른 앱이 포커스를 가져가는 순간 열린 금고를 잠갔습니다. 스크린샷 도구의 선택 화면이나 복사한 값을 붙여넣으러 잠깐 가는 것만으로도 비밀번호와 새 OTP로 다시 열어야 했습니다. 이 잠금이 막는 위험은 대부분 다른 장치가 이미 맡고 있습니다. 화면 캡처는 캡처 제외가, 자리를 비우는 경우는 60초 미사용 잠금이 막습니다. 같은 사용자 권한의 악성 프로그램은 원래 범위 밖입니다.
- 지금은 전환 순간 보이던 것을 모두 가립니다(15초 보기 종료, 복사 허용 해제, 보이게 한 비밀번호 재가림, OTP 백업 QR 닫기). 다른 앱에 30초 넘게 머무르면 잠급니다. 활성화 메시지를 놓쳐도 타이머가 전경 창이 금고인지 확인하므로, 사용 중인 금고를 잘못 잠그지 않습니다. 60초 미사용, 세션 잠금·절전 잠금은 그대로입니다.
- 남는 위험: 다른 앱을 보는 동안 최대 30초까지 금고 목록과 편집 중인 내용이 화면에 남습니다. 비밀정보 자체는 기본적으로 가려져 있고, 편집 화면만 내용이 보입니다.
- 회귀 테스트: 전환 시 QR·보기·복사 허용이 꺼지고 금고는 열려 있는지, 30초 안에 돌아오면 유지되는지, 30초를 넘기면 잠기는지 확인합니다.

- **코드 서명·GitHub 불변 릴리스·빌드 출처 증명(attestation):** 비용이나 저장소 설정 변경이 필요해 소유자 결정 사항으로 남깁니다.
- **앱이 앞에 있을 때 같은 사용자 프로그램이 넣는 가짜 입력:** 입력 출처(`GetCurrentInputMessageSource`)로 거를 수 있지만, 실제 하드웨어 입력에서 검증하지 못해 넣지 않았습니다.
- **하드 링크로 같은 금고를 두 번 여는 것:** 정보 등급이라 문서에만 적었습니다.
- **OTP 분실 복구, 데이터 키 교체(re-key), 단어 비밀번호 생성기:** 설계 결정이 필요합니다.
- **토큰 기본 DACL:** 새 스레드는 생긴 뒤 최대 0.5초 동안 기본 DACL입니다. 토큰 기본 DACL을 바꾸면 이 틈도 없앨 수 있지만, 셸과 주고받는 객체가 깨질 수 있어 바꾸지 않았습니다.
- **SYSTEM이나 디버그 권한으로 실행:** 자기 자신을 열어 보는 시작 검사가 성공해 버려서 앱이 시작을 거부합니다. 일반 사용 방식이 아니어서 그대로 둡니다.

**검증**
- 자동 테스트 총 25개 통과(라이브러리 16개, UI 9개). 새로 추가한 회귀 테스트는 다음을 확인합니다.

  - 나중에 생긴 스레드도 다른 프로그램이 열 수 없는지
  - 실행 파일 폴더에서 로드된 DLL을 자체 점검이 보고하는지
  - 대기열 가짜 메시지를 버리는지

- **재실험:** 처음 점검 때의 실험(해제된 힙·스택 잔여물, 다른 프로세스의 창 메시지, 프로세스 DACL, DLL 심기, 절전·Windows 종료 잠금)을 새 코드로 다시 돌렸고, 모두 고쳐진 것을 확인했습니다. 대조군으로 0.3.1 라이브러리를 같은 하네스에 넣으면 원래 누수가 그대로 재현됩니다.
- **코드 리뷰:** 수정분에서 아래 문제를 새로 찾았고, 모두 고쳤습니다.

|발견|등급|처리|
|---|---|---|
|`SendNotifyMessage`·`SendMessageCallback`으로 보낸 메시지가 "다른 스레드" 판별(`ISMEX_SEND`만 확인)을 통과해, 가짜 클릭으로 복사까지 가능|높음(재현)|`ISMEX_SEND`·`NOTIFY`·`CALLBACK`을 모두 외부로 판단. 회귀 테스트에 `SendNotifyMessage` 추가|

**두 번째 재검증.** 위 수정분을 다른 에이전트가 다시 실험했습니다. 별도 데스크톱에 숨긴 창을 만들어 실제 메시지 상자와 창 이동 루프를 돌렸습니다. 이 에이전트의 보고서는 두 번째 항목을 쓰던 중 안전 필터에 막혀 끝까지 저장되지 않았습니다. 그래서 끝까지 적힌 두 항목은 고쳤고, 나머지 질문(지연 잠금 사이의 상태, 스레드 순회, DLL 경로 비교, 비밀번호 검사의 최악 시간 약 11ms)은 직접 코드와 테스트로 확인했습니다.

|발견|등급|처리|
|---|---|---|
|모달 상태를 창 메시지(`WM_EXITMENULOOP`·`WM_EXITSIZEMOVE`)로 판단해서, 대기열에 넣은 가짜 "루프 끝" 알림으로 막음을 풀고 가짜 명령(복사 허용, 보기)을 실행할 수 있음. 대기열로 넣은 `WM_SYSCOMMAND(SC_MOVE)`로 사용자 조작 없이 이동 루프를 시작할 수도 있음|높음(재현)|모달 상태는 앱이 직접 연 대화상자 카운터와 Windows의 스레드 상태(`GetGUIThreadInfo`)로만 판단. `WH_GETMESSAGE` 훅이 모든 루프에서 대기열 필터를 적용. 대기열 `WM_SYSCOMMAND`는 닫기·최소화·복원만 허용. 훅을 끄면 회귀 테스트가 실패하는 것을 확인|
|가짜 "루프 시작" 알림으로 카운터가 0보다 크게 남아 명령이 계속 무시됨|낮음|위와 같은 수정으로 해결(메시지로 카운터를 바꾸지 않음)|

## 0.5.0 변경: OTP를 선택 사항으로

**이유.** TOTP 번호는 30초마다 바뀌어 암호화 키로 쓸 수 없고, 앱이 번호를 확인하려면 휴대폰과 같은 비밀키를 PC(열쇠 파일 안)에 저장해야 합니다. 그래서 OTP는 복호화에 참여하지 않고, 두 파일과 비밀번호를 가진 사람은 OTP 없이 복호화할 수 있습니다. OTP가 막는 것은 비밀번호를 아는 사람이 이 PC에서 이 앱으로 여는 경우뿐인데, 휴대폰을 잃으면 금고를 못 여는 위험은 모든 사용자가 집니다. 그래서 새 금고의 OTP를 선택 사항으로 바꾸고 기본값을 꺼짐으로 했습니다. 파일 도난에 대한 실제 두 번째 요소는 따로 둔 열쇠 파일이라는 점은 그대로입니다.

**형식.** OTP를 쓰는 열쇠 파일은 기존 `GOYOKE01`(148바이트) 그대로입니다. OTP를 쓰지 않는 열쇠 파일은 `GOYOKE02`(128바이트, 평문은 데이터 키 32바이트)입니다. 매직은 AAD에 들어 있고 매직과 길이가 정확히 짝을 이뤄야 하므로, 한 종류를 다른 종류로 바꿔 붙이거나 잘라 내면 인증에 실패합니다(회귀 테스트로 확인). 금고 파일 형식은 바뀌지 않았고, OTP 미사용 금고의 OTP step은 0입니다. 0.4.x 이하는 `GOYOKE02`를 읽지 못합니다.

**동작.**
- 새 금고 화면은 OTP 꺼짐으로 시작합니다. 'OTP 사용'·'OTP 끄기'로 바꿔도 입력한 비밀번호와 OTP 비밀키는 그대로라, 이미 스캔한 QR이 무효가 되지 않습니다. OTP 사용 여부는 만들 때만 정하고, 기존 금고의 OTP를 켜거나 끄는 기능은 없습니다.
- 금고 열기·복원 화면은 열쇠 파일의 평문 매직이 `GOYOKE01`일 때만 OTP 칸을 보입니다. 이것은 화면 배치용 힌트이고, 실제로 OTP를 확인할지는 복호화한 열쇠 파일의 종류로 정합니다. 매직을 바꾸면 복호화가 실패하므로 OTP 확인을 건너뛰게 만들 수 없습니다.
- '찾기'로 열쇠 파일을 고르면 OTP 칸을 그에 맞게 다시 그립니다(입력한 비밀번호 유지). 경로를 직접 입력해 OTP 금고를 고른 경우, 첫 제출에서 OTP 칸을 추가하고 입력을 요청하며 인증 실패로 세지 않습니다.
- OTP 미사용 금고에는 'OTP 백업' 버튼이 없고(명령도 거부), 비밀번호 변경에 OTP 칸이 없습니다.
- OTP 미사용 금고는 잠금 해제만으로는 금고 파일을 다시 쓰지 않습니다. 기록할 OTP step이 없기 때문입니다. 복원은 기존대로 새 파일에 씁니다.
- 0.5.1: 기본값은 그대로 꺼짐이지만, OTP 카드를 초록 테두리·'권장' 표시·초록 'OTP 켜기' 버튼으로 눈에 띄게 하고, 끈 채로 만드는 버튼은 'OTP 없이 금고 만들기'로 표시합니다. 이 PC와 파일이 남의 손에 들어가지 않는 한 OTP는 비밀번호 유출을 실제로 막아 주기 때문입니다. 보안 동작과 파일 형식은 바뀌지 않았습니다.
- '찾기'로 경로를 바꾼 뒤 열쇠 칸의 위치 경고가 갱신되지 않던 문제(변경 알림이 상태 사용 중에 도착해 버려짐)도 함께 고쳤습니다.

**확인.**
- 자동 테스트 총 27개 통과(라이브러리 17개, UI 10개). 새 테스트는 다음을 확인합니다.
  - `vault_without_otp`: OTP 미사용 금고의 생성·열기·백업·복원·비밀번호 변경, 128바이트 열쇠, 잠금 해제 시 금고 파일 미변경, OTP 백업 거부, OTP 금고는 코드 없이 열리지 않음
  - `key_password_and_tamper`: 두 열쇠 종류의 매직을 서로 바꾸거나 잘라 내면 거부
  - `optional_otp_create_and_open`: 기본 꺼짐, 전환 시 비밀번호·OTP 비밀키 유지, OTP 없이 만든 금고를 비밀번호만으로 다시 열기, 경로를 직접 입력한 OTP 금고는 실패로 세지 않고 OTP 칸 추가
- UI 테스트는 전환 후 비밀번호 복원과 첫 제출 시 OTP 칸 추가 처리를 각각 일부러 빼면 실패하는 것을 확인했습니다.
- 이번 변경은 별도 에이전트의 독립 검토를 받지 않았습니다.

## 남은 검증 한계와 의도한 동작

실제 비밀·사용자 클립보드를 사용하는 UI 자동화는 수행하지 않았습니다. 숨겨진 자체 테스트 창과 가짜 값으로 검증했습니다. 사용자 클립보드를 실제로 덮어쓰는 통합 테스트, 모든 캡처 프로그램·IME·셸 확장, FAT/exFAT 전원 차단, 장치별 물리 난수 검증은 수행하지 않았습니다. 실제 한국어 IME를 통한 제목/경로 입력은 수동 확인하지 않았으며, 암호 입력 범위 때문에 한글 입력이 제한될 수 있음을 README에 명시했습니다.

클립보드 점유가 풀리지 않으면 종료가 대기할 수 있습니다. 이는 비밀이 남은 채 자동 종료하지 않기 위한 선택입니다. 다른 앱에 30초 넘게 머무르면 잠그며, 편집 중인 미저장 내용도 이때 지웁니다. 파일창도 60초 잠금 대상입니다. 운영체제 메모리 사본·관리자/커널 공격·경로 메타데이터·암호화 임시 파일·오래된 백업/열쇠의 효력은 README에 설명한 한계가 유지됩니다.

Windows 설정 검증 근거: [정적 DLL 검색 플래그](https://learn.microsoft.com/en-us/cpp/build/reference/dependentloadflag?view=msvc-170), [파일 선택창 플래그](https://learn.microsoft.com/en-us/windows/win32/api/commdlg/ns-commdlg-openfilenamew), [클립보드 시퀀스](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber), [입력 컨트롤 스타일](https://learn.microsoft.com/en-us/windows/win32/controls/edit-control-styles).

입력기 설정 근거: [SetInputScope](https://learn.microsoft.com/en-us/windows/win32/api/inputscope/nf-inputscope-setinputscope), [ImmAssociateContextEx](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontextex). 암호 입력 범위는 OS 서비스에 대한 힌트이며 완전한 격리 보장이 아닙니다.
