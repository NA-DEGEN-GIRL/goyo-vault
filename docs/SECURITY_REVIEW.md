# 검토 기록

## 의존성 선정

- `chacha20poly1305 0.10.1`: RustCrypto, 순수 Rust. 프로젝트는 NCC Group 감사 이력을 공개합니다. 과거 라이브러리 감사가 현재 앱 전체 또는 모든 후속 버전을 보증하지는 않습니다. https://docs.rs/chacha20poly1305/0.10.1/chacha20poly1305/#security-notes
- `argon2 0.5.3`: RustCrypto Argon2id 구현. 공개 구현과 명세·테스트를 검토하며, 이 버전의 독립 감사 완료를 주장하지 않습니다. https://docs.rs/argon2/0.5.3/argon2/
- `hmac 0.12.1`, `sha1 0.10.6`, `sha2 0.10.9`: RustCrypto의 OTP HMAC 및 난수 컨디셔닝. SHA-1은 TOTP HMAC에만 사용.
- `zeroize 1.8.2`: 민감한 Rust 버퍼와 Argon2 메모리 소거. 복사 방지·잠긴 메모리·커널 보호 기능과 동일하지 않음.
- `subtle 2.6.1`: OTP 비교에 사용. 런타임 조작/바이너리 패치를 막지는 않음.
- 전이 의존성은 Cargo.lock 고정. RNG 기본 기능을 꺼 Windows RNG 호출 경로를 제외. `rand_core`가 암호화 라이브러리의 타입 의존성으로 남아도 `OsRng`는 호출하지 않음.

## 보안 테스트와 리뷰

2026-10-16, Windows x64 / rustc 1.98.1 환경에서 검증했습니다. 전문 감사·침투 테스트·하드웨어 인증을 완료했다고 주장하지 않습니다.

- 내부 독립 에이전트 2명: 암호화·저장, Windows UI·보안 흐름을 각각 읽기 전용 검토. 발견 사항 수정 후 재검토. 마지막으로 표준 Enter/Escape 명령 매핑 권고까지 반영했습니다.
- 사용자 요청에 따라 `llm-analysis` MCP의 `delegate_analysis`를 통해 **claude-opus-5-5** 검토를 총 3회 받았습니다. 전체 소스 최초 검토 → 수정본 전체 재검토 → 마지막 UI 수정사항 집중 검토 순서입니다. 최초 원문은 `OPUS_INITIAL.md`, 두 번째는 `OPUS_FOLLOWUP.md`, 마지막은 `OPUS_FINAL.md`입니다. 각 MCP 응답 JSON(`opus-review-*.json`)도 보존했습니다. 검토 요청에 쓴 MCP 호출 스크립트는 개발 PC 설정에 묶여 있어 공개 저장소에는 넣지 않았습니다. 마지막 답변은 검토 범위에서 미해결 조치 사항과 즉각적인 회귀를 발견하지 못했다고 밝혔습니다. 이는 앱 전체의 무결점 인증이 아닙니다.
- 초기 검토의 일반 마스킹이 Rust 타입·테스트 숫자 일부를 변형한 제한이 있었습니다. 수정본 검토에는 사용자 정보가 없는 소스·가짜 테스트 데이터만 선별하여 정확한 원문을 제공했습니다.
- (2026-10-16 기준) 자동 테스트 총 17개 통과(라이브러리 13개, UI 4개). 2026-10-17 변경 후 수치는 아래 절을 보세요. AEAD 변조·잘린 파일·인증된 악성 구조·OTP 표준 벡터/재사용·생성/저장/백업/복원·잘못된 비밀번호·비밀번호 변경 실패 단계·동시 세션·하드링크/ADS·UTF 입력·네이티브 컨트롤 보호·페이지 표시 폭·지연 잠금/종료를 검사했습니다. 이후 변경한 부분은 해당 테스트를 다시 실행했습니다.
- Argon2id와 XChaCha20-Poly1305 고정 벡터를 각각 Python cryptography 및 PyNaCl/libsodium의 독립 결과와 대조했습니다.
- `cargo clippy --all-targets --locked -- -D warnings` 통과.
- OSV 질의로 Cargo.lock의 27개 레지스트리 패키지를 확인했으며 조회 당시 반환된 취약점은 0개입니다. 알려지지 않은 취약점까지 없다는 의미는 아닙니다. `dependency-audit.json`에 조회 시각·버전 기록.
- 릴리스 실행 파일의 `--self-check` 통과: 프로세스 완화 정책, Windows 버전, 캡처 제외 속성, 로컬 세션·디버거 확인, 타이머·RDSEED 초기화, 실제 입력 컨트롤의 암호 입력 범위 및 IME 분리.
- PE 헤더/직접 import 검사: `DependentLoadFlags=0x800`, CFG, Windows 암호화·난수 함수 직접 import 없음. 상세는 `binary-inspection.json`. 운영체제 DLL 내부 동작까지 추적한 검증은 아닙니다.

## 0.2.0 변경: OTP 등록 QR

이 변경도 외부 모델 검토를 받지 않았습니다.

- `src/qr.rs`: 바이트 모드, 버전 6(41×41), 오류 정정 M 전용 자체 인코더. 외부 QR 라이브러리를 쓰지 않은 이유는 OTP 비밀키가 담기는 코드워드·오류 정정·모듈 버퍼를 모두 `zeroize`로 지우기 위해서입니다. 등록 주소(`otpauth://totp/Goyo%20Vault?secret=…&issuer=Goyo%20Vault`, 87바이트)도 재할당 없이 만든 소거 버퍼에 담습니다.
- 독립 구현 대조: 같은 입력에서 8개 마스크 모두 python-qrcode 8.2와 모듈 배열이 완전히 같습니다(SHA-256 고정값을 테스트에 포함). segno 1.6.6은 기능 패턴·형식 정보·데이터가 같고, 바이트 경계에서 끝난 종료 비트 뒤에 `0x00`을 한 바이트 더 넣는 점만 다릅니다. ISO/IEC 18004는 이 경우 곧바로 채움 코드워드를 두므로 python-qrcode와 같은 방식을 택했습니다.
- 실제 화면에 그려진 QR(다크·라이트)을 zxing-cpp 디코더로 읽어 `otpauth` 주소 형식이 그대로 나오는 것을 확인했습니다. 실제 휴대폰 앱으로 스캔하는 확인은 하지 않았습니다.
- QR은 캡처 제외 창에 직접 그리며 파일로 저장하지 않습니다. 등록 키 글자를 화면에 표시하던 것과 노출 범위는 같습니다. 휴대폰 일반 카메라·렌즈 앱이 이미지를 클라우드로 보낼 수 있으므로 화면과 README에서 OTP 앱 내부 스캐너만 쓰도록 안내합니다.
- 자동 테스트 총 21개 통과(라이브러리 16개, UI 5개).

## 0.2.1 변경: 비밀번호 보기 버튼

이 변경도 외부 모델 검토를 받지 않았습니다.

- 비밀번호·확인·현재 비밀번호 칸에 눈 버튼을 추가했습니다(OTP 칸 제외). 기본은 가림이고, 누를 때만 표시합니다.
- 가림 해제는 앱이 원래 edit 프로시저를 직접 호출하는 경로뿐입니다. 서브클래스는 외부에서 보낸 `EM_SETPASSWORDCHAR`를 계속 버리므로, 2026-10-16 검토에서 막은 "다른 프로그램이 가림을 푸는" 경로는 그대로 닫혀 있습니다.
- `ES_PASSWORD`를 해제하면 edit 컨트롤이 IME 컨텍스트를 되돌려 놓는 것을 테스트로 확인했습니다. 그대로 두면 한글 입력이 켜지고 입력기가 비밀번호를 학습할 수 있습니다. 그래서 해제 직후 IME를 다시 분리하고 암호 입력 범위를 재적용하며, 둘 중 하나라도 실패하면 다시 가리고 오류를 표시합니다.
- 표시 중에도 복사·잘라내기, 외부 `WM_GETTEXT`, `WM_GETOBJECT`(접근성) 차단과 캡처 제외는 그대로입니다. 잠금·미사용 시간 초과·화면 전환으로 화면을 다시 만들면 새 칸은 가려진 상태입니다. 회귀 테스트가 이 항목들과 외부 `EM_SETPASSWORDCHAR` 무시, 잠금 후 재가림을 확인합니다.
- 남는 위험은 주변 사람이 화면을 직접 보는 것입니다. 사용자가 누를 때만 보이므로 사용자의 선택으로 남깁니다.

## 0.2.2 변경: 비밀번호 최소 길이, 열기 전 화면의 앱 전환

이 변경도 외부 모델 검토를 받지 않았습니다.

- 새 비밀번호 최소 길이를 16자에서 12자로 낮췄습니다. 서로 다른 글자 6개 이상 규칙과 Argon2id 설정(256 MiB, 3회)은 그대로입니다. 열쇠 파일을 가진 공격자는 OTP 없이 오프라인으로 비밀번호를 추측할 수 있으므로, 길이가 실제 방어선이라는 점은 README에 계속 적습니다. 기존 금고 열기와 파일 형식에는 영향이 없습니다.
- 다른 앱으로 전환할 때 잠그는 대상을 열린 금고로 한정했습니다. 금고를 열기 전 화면(열기·새 금고·복원)에는 풀린 비밀이 없으므로 입력 내용과 OTP 등록 정보를 유지하고, 눈 버튼으로 보이게 한 비밀번호만 다시 가립니다. 이전에는 OTP를 휴대폰에 등록하는 도중 전환하면 등록 키가 새로 만들어져 이미 등록한 OTP가 쓸모없어졌습니다. 입력 칸은 전환 중에도 외부 읽기·복사·캡처가 막혀 있고, 미사용 시간 초과(새 금고 5분, 나머지 60초)와 Windows 세션 잠금·절전은 계속 모든 입력을 지웁니다. 바쁜 동안 들어온 전환 이벤트도 같은 규칙을 따르며, 회귀 테스트가 두 경로를 확인합니다.

## 0.3.0 변경: OTP 백업

이 변경도 외부 모델 검토를 받지 않았습니다.

- 금고가 열린 상태에서 **OTP 백업**을 누르고 현재 비밀번호를 다시 입력하면, 세션이 가진 TOTP 비밀키를 생성 때와 같은 QR·등록 키로 보여 줍니다. 비밀번호는 세션의 열쇠 파일 사본으로 Argon2id 검증하고(`Session::otp_setup`), 실패는 다른 인증과 같은 재시도 대기 시간을 적용합니다.
- 등록 키를 금고 항목으로 저장하는 방식은 택하지 않았습니다. 금고를 열려면 OTP가 필요하므로 휴대폰 분실 시 꺼낼 수 없고, 백업이 된 것처럼 오해하게 만듭니다.
- 비밀키는 `OtpSetup`(소거 버퍼)에만 담겨 화면을 닫거나 잠글 때 버려집니다. QR은 캡처 제외 창에 직접 그리며 파일로 저장하지 않습니다. 표시 중 미사용 잠금 시간은 등록 화면과 같은 5분이고, 다른 앱 전환·세션 잠금 때는 금고와 함께 바로 닫힙니다.
- 남는 위험: 열린 금고 앞에 앉은 사람이 비밀번호까지 알면 자기 기기에 OTP를 등록할 수 있습니다. 그 사람은 이미 열린 금고의 모든 항목을 볼 수 있는 상태이므로 새로 생기는 노출은 크지 않다고 판단했습니다.
- 회귀 테스트: `Session::otp_setup`이 맞는 비밀번호에서만 생성 때와 같은 키·URI를 돌려주는지, UI에서 틀린 비밀번호는 표시하지 않고 대기 시간을 거는지, 닫기·앱 전환 잠금이 비밀키를 버리는지 확인합니다. 자동 테스트 총 22개 통과(라이브러리 16개, UI 6개).

## 0.3.1 변경: 앱 전환 즉시 잠금 → 30초 유예

이 변경도 외부 모델 검토를 받지 않았습니다.

- 이전에는 다른 앱이 포커스를 가져가는 순간 열린 금고를 잠갔습니다. 스크린샷 도구의 선택 화면이나 복사한 값을 붙여넣으러 잠깐 가는 것만으로도 비밀번호와 새 OTP로 다시 열어야 했습니다. 이 잠금이 막는 위험은 대부분 다른 장치가 이미 맡고 있습니다. 화면 캡처는 캡처 제외가, 자리를 비우는 경우는 60초 미사용 잠금이 막습니다. 같은 사용자 권한의 악성 프로그램은 원래 범위 밖입니다.
- 지금은 전환 순간 보이던 것을 모두 가립니다(15초 보기 종료, 복사 허용 해제, 보이게 한 비밀번호 재가림, OTP 백업 QR 닫기). 다른 앱에 30초 넘게 머무르면 잠급니다. 활성화 메시지를 놓쳐도 타이머가 전경 창이 금고인지 확인하므로, 사용 중인 금고를 잘못 잠그지 않습니다. 60초 미사용, 세션 잠금·절전 잠금은 그대로입니다.
- 남는 위험: 다른 앱을 보는 동안 최대 30초까지 금고 목록과 편집 중인 내용이 화면에 남습니다. 비밀정보 자체는 기본적으로 가려져 있고, 편집 화면만 내용이 보입니다.
- 회귀 테스트: 전환 시 QR·보기·복사 허용이 꺼지고 금고는 열려 있는지, 30초 안에 돌아오면 유지되는지, 30초를 넘기면 잠기는지 확인합니다.

- `check_dll_planting.py`로 이전 0.3.1 실행 파일은 `sspicli.dll`에서 실패하고, 0.4.0은 통과하는 것을 확인했습니다. 지금은 가짜 파일과 진짜 System32 사본을 모두 심어 봅니다.
- 수정분은 별도 에이전트 3개가 두 차례에 걸쳐 다시 검토했습니다(아래).
- 실제 하드웨어 입력(첫 클릭이 앱 활성화와 함께 처리되는지), 실제 한글 입력기, Modern Standby 노트북, 휴대폰 스캔은 사람이 직접 확인하지 않았습니다.

## 0.5.0 변경: OTP를 선택 사항으로

**이유.** TOTP 번호는 30초마다 바뀌어 암호화 키로 쓸 수 없고, 앱이 번호를 확인하려면 휴대폰과 같은 비밀키를 PC(열쇠 파일 안)에 저장해야 합니다. 그래서 OTP는 복호화에 참여하지 않고, 두 파일과 비밀번호를 가진 사람은 OTP 없이 복호화할 수 있습니다. OTP가 막는 것은 비밀번호를 아는 사람이 이 PC에서 이 앱으로 여는 경우뿐인데, 휴대폰을 잃으면 금고를 못 여는 위험은 모든 사용자가 집니다. 그래서 새 금고의 OTP를 선택 사항으로 바꾸고 기본값을 꺼짐으로 했습니다. 파일 도난에 대한 실제 두 번째 요소는 따로 둔 열쇠 파일이라는 점은 그대로입니다.

**형식.** OTP를 쓰는 열쇠 파일은 기존 `GOYOKE01`(148바이트) 그대로입니다. OTP를 쓰지 않는 열쇠 파일은 `GOYOKE02`(128바이트, 평문은 데이터 키 32바이트)입니다. 매직은 AAD에 들어 있고 매직과 길이가 정확히 짝을 이뤄야 하므로, 한 종류를 다른 종류로 바꿔 붙이거나 잘라 내면 인증에 실패합니다(회귀 테스트로 확인). 금고 파일 형식은 바뀌지 않았고, OTP 미사용 금고의 OTP step은 0입니다. 0.4.x 이하는 `GOYOKE02`를 읽지 못합니다.

**동작.**
- 새 금고 화면은 OTP 꺼짐으로 시작합니다. 'OTP 사용'·'OTP 끄기'로 바꿔도 입력한 비밀번호와 OTP 비밀키는 그대로라, 이미 스캔한 QR이 무효가 되지 않습니다. OTP 사용 여부는 만들 때만 정하고, 기존 금고의 OTP를 켜거나 끄는 기능은 없습니다.
- 금고 열기·복원 화면은 열쇠 파일의 평문 매직이 `GOYOKE01`일 때만 OTP 칸을 보입니다. 이것은 화면 배치용 힌트이고, 실제로 OTP를 확인할지는 복호화한 열쇠 파일의 종류로 정합니다. 매직을 바꾸면 복호화가 실패하므로 OTP 확인을 건너뛰게 만들 수 없습니다.
- '찾기'로 열쇠 파일을 고르면 OTP 칸을 그에 맞게 다시 그립니다(입력한 비밀번호 유지). 경로를 직접 입력해 OTP 금고를 고른 경우, 첫 제출에서 OTP 칸을 추가하고 입력을 요청하며 인증 실패로 세지 않습니다.
- OTP 미사용 금고에는 'OTP 백업' 버튼이 없고(명령도 거부), 비밀번호 변경에 OTP 칸이 없습니다.
- OTP 미사용 금고는 잠금 해제만으로는 금고 파일을 다시 쓰지 않습니다. 기록할 OTP step이 없기 때문입니다. 복원은 기존대로 새 파일에 씁니다.
- 0.5.1: 기본값은 그대로 꺼짐이지만, OTP 카드를 초록 테두리·'권장' 표시·초록 'OTP 켜기' 버튼으로 눈에 띄게 하고, 끈 채로 만드는 버튼은 'OTP 없이 금고 만들기'로 표시합니다. 이 PC와 파일이 남의 손에 들어가지 않는 한 OTP는 비밀번호 유출을 실제로 막아 주기 때문입니다. 보안 동작과 파일 형식은 바뀌지 않았습니다.
- '찾기'로 경로를 바꾼 뒤 열쇠 칸의 위치 경고가 갱신되지 않던 문제(변경 알림이 상태 사용 중에 도착해 버려짐)도 함께 고쳤습니다.

**확인.**
- 자동 테스트 총 27개 통과(라이브러리 17개, UI 10개). 새 테스트는 다음을 확인합니다.
  - `vault_without_otp`: OTP 미사용 금고의 생성·열기·백업·복원·비밀번호 변경, 128바이트 열쇠, 잠금 해제 시 금고 파일 미변경, OTP 백업 거부, OTP 금고는 코드 없이 열리지 않음
  - `key_password_and_tamper`: 두 열쇠 종류의 매직을 서로 바꾸거나 잘라 내면 거부
  - `optional_otp_create_and_open`: 기본 꺼짐, 전환 시 비밀번호·OTP 비밀키 유지, OTP 없이 만든 금고를 비밀번호만으로 다시 열기, 경로를 직접 입력한 OTP 금고는 실패로 세지 않고 OTP 칸 추가
- UI 테스트는 전환 후 비밀번호 복원과 첫 제출 시 OTP 칸 추가 처리를 각각 일부러 빼면 실패하는 것을 확인했습니다.
- 이번 변경은 별도 에이전트의 독립 검토를 받지 않았습니다.

## 0.6.0 변경: 영어 화면

**동작.** 오른쪽 위 **한국어 | English**로 화면 언어를 바꿉니다. 코드 안의 문자열은 한국어 그대로 두고, 화면에 표시하는 지점(컨트롤 생성, 상태 줄, 직접 그리는 글자, 메시지 상자, 파일 선택창)에서만 번역표(`src/i18n.rs`)를 거쳐 영어로 바꿉니다. 오류 비교나 저장 형식처럼 화면 밖에서 쓰이는 문자열은 바뀌지 않습니다. 번역표는 정확히 같은 문자열만 바꾸므로, 경로·항목 이름 같은 사용자 데이터는 그대로 표시됩니다. 예외로 기본 종류(비밀번호·니모닉·프라이빗키·API 키)는 화면 언어로 표시하며, 영어 화면에서 이런 항목을 수정해 저장하면 종류가 영어로 저장됩니다.

**설정 파일.** 선택은 실행 파일 옆 `goyo-vault.lang`에 `en` 또는 `ko`만 저장합니다. 테마 파일과 같은 방식(최대 16바이트 읽기, 기존 파일을 지운 뒤 새로 만들어 링크를 따라가지 않음)이고 비밀은 없습니다. 파일이 없으면 Windows 표시 언어로 정합니다.

**전환.** 언어를 바꾸면 화면을 다시 만들고, 입력하던 비밀번호·OTP·항목 칸은 기존 `rebuild_keeping`(OTP 켜기·끄기에 쓰던 것)으로 지워지는 버퍼를 거쳐 되돌립니다. 보이게 해 둔 비밀번호는 다시 가려집니다. 언어 버튼은 테마 버튼처럼 모든 화면에서 허용되며, 다른 프로그램이 보낸 가짜 클릭을 거르는 기존 필터를 똑같이 거칩니다.

**글꼴.** 영어 화면은 Segoe UI를 씁니다. 맑은 고딕은 역슬래시를 ₩로 그려 경로가 헷갈리기 때문입니다. 두 글꼴 모두 Windows 시스템 글꼴이라 시스템 외 글꼴 차단 정책과 충돌하지 않고, 영어 화면의 한글(항목 이름 등)은 Windows 글꼴 연결로 표시됩니다.

**확인.**
- `english_is_complete`: 소스(테스트 제외)의 모든 한국어 문자열에 영어가 있는지, 영어 화면의 모든 컨트롤과 직접 그리는 글자에 한국어가 남지 않는지 확인합니다.
- `labels_fit_their_boxes`: 두 언어 모두에서 모든 글자 칸과 버튼 이름이 잘리지 않는지, 모든 한 줄 메시지가 상태 줄에 들어가는지 확인합니다.
- `language_switch_keeps_input`: 전환 뒤에도 입력한 비밀번호와 OTP 비밀키가 그대로이고, 상태 줄이 언어를 따라가는지 확인합니다.
- 처음 만든 번역표는 `HashMap`을 써서, 표준 라이브러리의 해시 난수 때문에 Windows 난수 DLL(`bcryptprimitives.dll`)이 실행 파일 가져오기 목록에 들어갔습니다. 배포 전 PE 검사(`scripts/inspect_pe.py`)가 이를 막았고, 해시를 쓰지 않는 `BTreeMap`으로 바꿔 가져오기 목록을 이전과 같게 되돌렸습니다.
- 자동 테스트는 총 30개(라이브러리 17개, UI 13개)입니다. 이번 변경은 별도 에이전트의 독립 검토를 받지 않았습니다.

## 0.7.0 변경: 자동 잠금 시간 설정

**배경.** 혼자 쓰는 PC에서 60초 미사용·다른 앱 30초 잠금이 너무 잦다는 요청이 있었습니다. 이 두 잠금이 막는 것은 주로 "열어 둔 채 자리를 비운 사이 다른 사람이 PC 앞에 앉는 경우"입니다. 화면 캡처는 캡처 제외가, 다른 프로그램의 창 읽기·가짜 클릭은 메시지 필터가 따로 막고, 같은 사용자 권한의 악성 프로그램은 원래 범위 밖입니다(0.3.1 참고). 그래서 이 위험을 사용자가 Windows 화면 잠금으로 직접 관리하겠다면 시간을 늘리거나 끄는 것은 합리적인 선택이라고 판단했습니다. 다만 열려 있는 시간이 길어지면 금고가 복호화된 채 메모리에 있는 시간도 길어지고, 원격 제어 도구처럼 앱이 감지하지 못하는 경로로 화면을 보는 경우도 막지 못합니다. 그래서 기본값은 바꾸지 않았습니다.

**동작.** 금고 화면 오른쪽 아래 **자동 잠금 [1분 | 5분 | 30분 | 끔]** 스위치로 고릅니다.
- **1분**(기본): 이전과 같습니다. 60초 미사용, 다른 앱 30초, OTP 백업 QR 표시 중에는 2분.
- **5분·30분**: 그 시간 동안 쓰지 않으면 잠급니다. 다른 앱에 있는 시간도 미사용으로 셉니다(미사용 시간과 다른 앱에 머문 시간 중 긴 쪽).
- **끔**: 시간으로는 잠그지 않습니다.
- 설정과 관계없이 유지: 잠금 버튼, Windows 세션 잠금·연결 변경, 절전, Windows 종료, 디버거·캡처 차단 실패 감지 잠금. 다른 앱으로 전환할 때 15초 보기·복사 허용·보이게 한 비밀번호·OTP 백업 QR을 바로 가리는 동작도 그대로입니다.
- OTP 백업 QR은 설정과 관계없이 2분 동안 쓰지 않으면 닫습니다. 1분 설정에서는 이전처럼 이때 금고도 잠기고, 더 긴 설정에서는 QR만 닫힙니다.
- 금고를 열기 전 화면의 입력 지우기 시간(새 금고 5분, 나머지 60초)은 바뀌지 않습니다.
- 끔으로 금고를 열면 상태 줄이 "자동 잠금이 꺼져 있습니다. 자리를 비울 때는 잠금 버튼이나 Win+L을 누르세요."라고 알리고, 편집 화면 안내도 고른 설정에 맞춰 바뀝니다.

**설정 파일.** 실행 파일 옆 `goyo-vault.autolock`에 `1`·`5`·`30`·`off`만 저장합니다. 테마·언어 파일과 같은 방식(최대 16바이트 읽기, 기존 파일을 지운 뒤 새로 만들어 링크를 따라가지 않음)이며, 알 수 없는 값은 1분으로 읽습니다. 이 파일을 쓸 수 있는 사람은 설정을 끔으로 바꿀 수 있지만, 그 폴더에 쓸 수 있으면 실행 파일 자체를 바꿀 수 있으므로 새 위험은 아니라고 판단했습니다. 현재 설정은 금고 화면에 항상 보입니다.

**명령.** 스위치는 금고가 열린 금고 화면에서만 허용합니다(`allows`). 다른 버튼과 같은 필터를 거치므로, 다른 프로그램이 보내거나 대기열에 넣은 가짜 클릭, 앱이 뒤에 있을 때의 입력으로는 설정을 바꿀 수 없습니다.

**화면.** 스위치 자리에 있던 "60초 미사용·다른 앱 30초·화면 잠금 시 잠금 / 화면 캡처 차단 · 악성코드까지 막지는 못합니다." 안내는 스위치와 상태 줄로 옮겼습니다. 금고를 열 때 상태 줄이 "화면 캡처는 막지만 악성코드까지 막지는 못합니다."를 알립니다.

**확인.**
- `auto_lock_choices`: 저장 값 해석, 잠긴 화면에서 설정 거부, 스위치 표시, 5분 설정에서 다른 앱 31초는 유지·5분은 잠금, 끔에서 1시간 미사용·이탈에도 유지, 끔에서 OTP QR만 2분 뒤 닫힘, 1분에서 QR 화면 61초는 유지·2분 뒤 잠금을 확인합니다.
- `labels_fit_their_boxes`, `english_is_complete`: 스위치·라벨·상태 줄 문구와, 설정마다 바뀌는 편집 화면 안내가 두 언어에서 잘리지 않고 번역되는지 확인합니다.
- 자동 테스트는 총 31개(라이브러리 17개, UI 14개)입니다. 이번 변경은 별도 에이전트의 독립 검토를 받지 않았습니다.

## 0.8.0 변경: 동기화(선택)

**배경.** 여러 PC에서 같은 금고를 쓰되, 서버에는 암호화된 금고 파일만 두고 열쇠 파일은 절대 올리지 않기를 원한다는 요청이 있었습니다. 금고 앱은 지금까지처럼 네트워크·프로세스 코드 없이 두고, 별도 도구와 서버 스크립트를 더했습니다. 사용법은 [SYNC.md](SYNC.md), 형식은 [FORMAT.md](FORMAT.md)에 있습니다. 동기화를 쓰지 않으면 금고 형식도 동작도 0.7.0과 같습니다.

**구성과 신뢰 경계.**

|구성 요소|신뢰|가진 것|
|---|---|---|
|`goyo-vault.exe`|신뢰 기준. 데이터 키를 쓰는 유일한 프로그램|열쇠 파일, 비밀번호, 평문. 복호화·합치기·'동기화됨' 판정을 모두 여기서 합니다.|
|`goyo-sync.exe`|믿지 않는 데이터 운반자(같은 사용자 권한)|암호문, 서버 접속 수단. 암호 코드와 소켓 코드가 없고, 금고·열쇠 파일을 열지 않습니다.|
|`System32\OpenSSH\ssh.exe`|Windows가 설치한 전송 경로|서버 인증은 사용자의 `known_hosts`(모르는 키·바뀐 키는 거부)|
|서버와 `goyo-sync-server.py`|믿지 않음(적대적일 수 있음)|암호문과 그 기록(금고마다 최근 200개)|

- 금고 앱과 도우미는 금고 옆 `<금고>.sync\` 폴더의 파일로만 주고받습니다. 파일마다 쓰는 쪽은 하나이고, 모두 임시 파일을 쓴 뒤 이름을 바꿔 넣습니다. 이름 있는 파이프, 메시지, 공유 메모리는 쓰지 않습니다.
- 금고 형식 `GOYOVA02`는 사용자가 금고마다 동의한 뒤에만 씁니다. 0.8.0이 모든 금고를 새 형식으로 쓰면 OTP 잠금 해제 한 번으로 0.7.x가 그 금고를 열 수 없게 되기 때문입니다.

**측정한 사실과 거기서 나온 규칙.** 이 PC(Windows 11, NTFS)에서 측정했습니다. 대상 파일에 다른 핸들이 하나라도 열려 있으면 금고 저장에 쓰는 `MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)`가 `ERROR_ACCESS_DENIED`(5)로 실패합니다. 읽기 전용에 삭제까지 공유한 핸들, 접근 권한 0인 핸들, `FILE_READ_ATTRIBUTES`만 연 핸들도 마찬가지입니다. `FindFirstFileW` 디렉터리 목록은 막지 않습니다. 그래서:
- 도우미는 `vault.goyo`를 열지도, 속성을 조회하지도, 읽지도 않습니다. 금고가 있는 폴더의 목록만 봅니다. 도우미가 금고 파일을 읽는 설계안은 이 측정으로 탈락했습니다(저장과 OTP 잠금 해제가 가끔 실패함).
- 두 프로그램 모두 디렉터리 목록의 길이·만든 시각·고친 시각으로만 변경을 알아챕니다. rustc 1.98.1에서 `DirEntry::metadata`가 목록 정보를 쓰고 파일을 열지 않는 것, `MoveFileExW` 교체마다 만든 시각이 바뀌는 것(C:·D: NTFS)을 확인했습니다.
- 교체하는 쪽은 모두 재시도합니다. 금고 저장은 오류 5·32에서 20 ms 간격 5번, 동기화 파일은 50 ms 간격 3번 뒤 다음 주기에 다시 합니다. 동기화 파일 쓰기 실패는 저장 실패로 알리지 않습니다.
- 회귀 테스트: `polling_stamps_never_blocks_a_replace`는 목록 조회를 계속하는 동안 재시도 없는 교체 300번이 하나도 실패하지 않는지 봅니다(조회를 `fs::metadata`로 바꾸면 약 25%가 실패). `passes_never_hold_the_vault_or_key_file`은 도우미가 40번 동기화하는 동안 다른 스레드가 금고·열쇠 파일을 재시도 없이 교체해도 실패가 없는지 봅니다.

**설계 요약.**
- 합치기는 join(CRDT)입니다. 항목은 양쪽의 합집합에서 양쪽 삭제 기록을 뺀 것, 삭제 기록은 합집합, OTP 기록은 큰 값입니다. 합치기가 삭제 기록을 만들지 않으므로, 오래된·되돌린·갈라진 서버 사본은 변경을 늦출 수 있어도 항목을 지우거나 되돌리지 못합니다.
- 내용 변경 횟수 `generation`과 이 PC가 본 가장 큰 값 `seen`을 암호문 안에 둡니다. 서버 사본의 `generation`이 `seen`보다 작으면 되돌림 경고를 띄우고 다시 올립니다.
- '동기화됨'은 도우미가 `incoming`에 둔 사본을 금고 앱이 AEAD로 확인해, 항목(글 포함)·삭제 기록이 같을 때만 표시합니다. 그 사본은 서버가 마지막으로 보낸 것이거나, 서버가 받았다고 답한 이 PC의 업로드 그대로입니다. 그래서 '동기화됨'은 서버가 받았다고 답했다는 뜻이지 저장했다는 증명은 아닙니다. 도우미의 상태 파일은 표시 단어만 고를 수 있습니다. 확인 코드(데이터 키로 계산한 HMAC-SHA256. 살아 있는 항목마다 ID와 글의 SHA-256, 그리고 삭제 기록. 64비트)로 PC끼리 같은 내용인지, 분기가 있는지 확인할 수 있습니다.
- OTP만 바뀐 잠금 해제는 올리지 않습니다. 올라가기를 기다리는 `outgoing`이 이미 같은 서버 버전에서 만든 같은 상태(항목·ID·글·삭제 기록. OTP 기록과 카운터는 보지 않음)를 담고 있으면 잠금 해제 때 다시 쓰지 않습니다. 서버가 잠금 해제 시각을 알지 못하게 하고(업로드를 받지 않는 서버도. 예외는 아래 '남은 한계'), 200개 기록이 잠금 해제로 밀려나지 않게 하려는 것입니다.
- 열쇠 파일을 막는 관문이 셋입니다. ① 금고 앱은 `encode_data` 결과(`GOYOVA02`·자기 금고 ID)만 `outgoing`에 씁니다. ② 도우미는 `outgoing`을 링크를 따라가지 않고 열어, 재분석 지점·하드 링크·크기·`GOYOSOU1`·`GOYOVA02`·고정한 ID를 확인하고 하나라도 어긋나면 ssh를 실행하지 않습니다. ③ 서버는 `GOYOVA02`이고 헤더 ID가 요청과 같은 것만 저장합니다. 도우미 설정에는 열쇠 파일을 가리키는 항목이 없고 `*.goyokey` 경로는 설정 오류입니다.
- 서버의 동시 저장은 `os.link`로 다음 버전 이름을 만드는 compare-and-swap입니다. 이미 있는 이름에는 연결되지 않으므로 같은 기대 버전의 두 요청 중 하나만 성공합니다. 버전 파일은 고치지 않습니다.
- ssh는 `GetSystemDirectoryW()\OpenSSH\ssh.exe`를 고정 인자(`-T -x -a -e none`, `-E <호출마다 새로 만든 로그 파일>`, `BatchMode=yes`, `StrictHostKeyChecking=yes`, `UpdateHostKeys=no`, 포워딩·로컬 명령·터미널 금지, 시간 제한)와 `--` 뒤의 검사한 호스트로 실행합니다. 가변 데이터는 모두 표준 입력의 프레임(길이·SHA-256 포함)으로만 보냅니다. HELLO의 512바이트 왕복이 Win32-OpenSSH 파이프가 이진 데이터를 바꾸지 않는지 확인합니다.
- 도우미는 금고 앱과 같은 프로세스 보호(System32 전용 DLL 검색, 동적 코드·확장 지점·시스템 외 글꼴·원격 이미지 금지, Microsoft 서명 DLL만)를 켜되, `ssh.exe`를 실행해야 하므로 하위 프로세스 금지는 켜지 않습니다. ssh는 kill-on-close Job 객체 안에서 돌고, 표준 출력(8 MiB + 64 KiB + 53바이트)·표준 오류(4 KiB)·시간 제한을 넘으면 끝냅니다. ssh 자신의 메시지는 그 파일(4 KiB, 링크를 따라가지 않고 읽음)로 받아 원격 표준 오류와 나누고, 상태 단어는 그 파일로만 고릅니다. 그 안에서도 상대가 보낸 글을 인용하는 메시지(버전 줄, 연결 끊기 사유, 거부된 로그인의 방법 목록) 뒤는 읽지 않습니다.

**검토 방법.** 이번 변경의 설계·구현·검토는 모두 AI 에이전트가 했습니다. **전문 보안 감사가 아니고, 사람이 코드를 한 줄씩 감사하지도 않았습니다.**
1. 이전에 따로 받은 설계 검토에서 Grok은 "쓰는 PC 하나, 서버는 덧붙이기 백업, 다른 PC는 직접 가져오기"인 최소안에 한해 조건부 승인했고, 양방향 동기화와 자동 병합에는 반대했습니다. Opus 요청은 시간 초과로 답을 받지 못했습니다. 0.8.0은 양방향 동기화와 자동 병합을 택했습니다. 그 검토가 짚은 위험(폴더째 동기화하면 열쇠 파일까지 올라감, 열린 세션이 받은 사본을 덮어써 다른 PC의 변경을 잃음, 암호문에 묶이지 않은 부모·세대 정보, 되돌림·분기, 새 PC의 최신성, PC 간 OTP 재사용)은 각각 금고 파일 하나만 통과시키는 관문, 금고 앱 안에서만 하는 join 합치기, 암호문 안의 `generation`·`seen`, 되돌림 경고와 확인 코드, 문서화한 한계로 다룹니다. 이 결정을 외부 모델에 다시 검토받지는 않았습니다.
2. 독립 AI 설계 패널: 단순성·견고성·보안을 각각 우선한 설계안 3개를 따로 만들고, 정확성·구현 가능성·보안과 사용성 기준으로 서로 다른 심사 에이전트가 점수를 매겼습니다. 가장 높은 보안 우선안(파일로만 주고받는 별도 도우미, v2 형식, CRDT)을 바탕으로 심사에서 나온 진행 멈춤(liveness) 버그를 고치고, 다른 안에서 결정적 v1 ID, `os.link` CAS, "올라갔는데 응답만 잃음" 감지, 이진 왕복 확인, ssh 옵션 강화를 가져왔습니다.

**수동 확인(이 기록 시점까지).** localhost만 대상으로 디버그 빌드 도우미를 돌려, 실제 Win32-OpenSSH가 고정 인자를 받고 모르는 호스트 키를 `hostkey`로 분류하는 것, `--once`가 폴더를 만들고 `idle`을 쓰는 것, 백그라운드 실행·두 번째 실행 종료·`--stop`을 확인했습니다. 릴리스 `--self-check`, PE 검사, DLL 심기 검사는 두 실행 파일 모두 통과했습니다. 이후 실제 Ubuntu 서버(Python 3.12)의 별도 시험 경로에 서버 스크립트를 두고, 가짜 금고로 다음을 확인한 뒤 시험 경로를 지웠습니다.
- 서버에서 `selftest` 통과(`-X dev -W error` 포함). Windows에서 돌리지 못한 폴더 fsync, 심볼릭 링크 저장소 거부, 스레드 경쟁 시험이 여기서 실행됩니다.
- 실제 Win32-OpenSSH로 HELLO 512바이트 이진 왕복이 그대로 돌아옴(`--check`).
- PC 두 대를 폴더 두 개로 흉내 내어: 동기화 켜기와 첫 업로드, `--list`·`--fetch`·복원으로 두 번째 PC 합류(확인 코드 같음), 한쪽 편집이 다른 쪽에 '추가 1개'로 합쳐짐, 같은 항목을 양쪽에서 고치면 두 버전이 모두 남고 충돌 알림이 한 번 나옴, 수렴 뒤 빈 라운드에서 서버 버전이 늘지 않음.
- 백그라운드 실행, 두 번째 실행은 바로 끝남, `--stop`, PowerShell에서 한국어 출력.
- 서버에 남은 파일은 버전 4개뿐이고 모두 `GOYOVA02`와 그 금고 ID로 시작하며, 열쇠 파일의 salt·nonce·감싼 키 바이트가 하나도 없음(공개 금고 ID 16바이트만 같음). 폴더는 0700, 파일은 0600.

보안 검토 수정 뒤에 다시 확인한 것:
- 고친 서버 스크립트의 `selftest`가 실제 Ubuntu 서버(Python 3.12)에서 통과. POSIX에서만 도는 금고 수 잠금(`flock`), 동시 접속 자리, `statvfs` 여유 공간 시험도 여기서 실행됩니다.
- 설정 창의 설치 명령을 그 서버의 별도 시험 경로에 실행해 `PASS`가 출력되고 0700 권한으로 설치됨. 시험 경로는 지웠습니다.
- 설정 창을 두 테마·두 언어로 그려 확인.
- 실제 System32 ssh.exe(9.5p2)가 한글·공백이 든 경로의 -E 파일에 자기 메시지를 쓰고 표준 오류는 비어 있음. 이 PC의 임시 서버로 바뀐 키·모르는 키·거부된 로그인 메시지가 -E 파일에만 나옴. 서버가 보낸 버전 줄·연결 끊기 사유·로그인 방법 목록이 -E 파일에 줄바꿈까지 인용됨(그 뒤는 판단에 쓰지 않음).

업로드 중 네트워크 끊기, 로그오프·로그온 자동 시작, 실제 PC 두 대에서의 장기 사용은 아직 사람이 확인하지 않았습니다. SYNC.md는 설치할 때 서버에서 selftest를 실행하도록 안내합니다.

**남은 한계.**
- 다른 PC의 새 버전을 숨기는 동결은 알아챌 수 없습니다. 이 PC의 업로드를 거부하거나 가진 사본으로 충돌이라고 답하는 동결은 `server`·`refused`로 드러나지만, 받았다고 답하고 버리는 서버 앞에서는 '동기화됨'이 나옵니다. 이 경우와 분기는 확인 코드를 비교해야만 드러납니다.
- '동기화됨'은 서버가 마지막으로 보냈거나 받았다고 답한 사본과 같다는 뜻이고, 저장의 증명이 아닙니다. 털렸거나 버그가 있는 도우미도 이 PC의 업로드를 받은 사본으로 넣어 띄울 수 있습니다.
- 서버는 보통 잠금 해제 시각을 모르지만, 올라가지 않은 변경이 있는 PC에 새 사본이 오면 그 PC는 합친 뒤(닫혀 있었다면 다음 잠금 해제 때) 다시 올리므로 서버가 그 시각을 압니다.
- 새 PC가 서버에서 받는 첫 사본은 서버를 믿습니다. 확인 코드 비교나 USB 복사가 신뢰 기준입니다.
- 한 번 쓴 OTP 번호 거부는 PC마다만 보장합니다.
- 0.9.0에서 열쇠를 바꾸기 전에는 열쇠 사본을 폐기할 수 없습니다. 예전 열쇠 사본과 비밀번호를 가진 사람은 진짜 삭제나 바꿔치기를 보내거나, 위의 서비스 거부를 할 수 있습니다. 합치기 전 사본은 한 세션 안의 손실만 더해 세므로, 잠금 해제마다 조금씩 지우면 사본 없이 알림만 나옵니다. 사본은 최근 3개와 30일이 안 된 것(모두 20개까지)만 남고, 서버에 쓸 수 있는 사람은 200개 기록도 새 업로드로 밀어낼 수 있습니다. 열쇠를 바꾼 뒤에는 새 열쇠 파일을 받은 PC에 대해 이 위험이 끝나고, 바꾸기 전 기록을 읽는 것과 예전 사본으로 동기화를 방해하는 것만 남습니다(아래 '0.9.0 변경').
- `seen`은 다른 변경과 함께만 저장되므로, 다시 시작한 뒤에는 되돌림 감지가 한 단계 약할 수 있습니다(잘못된 경고는 생기지 않습니다).
- 동기화 폴더의 파일을 읽을 때 링크(정션·심볼릭 링크)는 거부하지만, 하드 링크는 거르지 못합니다. 하드 링크를 심으려면 같은 사용자 권한의 코드가 필요하고, 그때 생기는 일은 금고 저장이 잠시 재시도되는 정도입니다.
- v1 ID, 같은 ID·다른 내용의 `id2`, 확인 코드는 항목 글자를 HMAC-SHA256이나 SHA-256에 넣어 계산합니다. 고정한 `sha2`·`hmac` 버전은 내부 작업 버퍼를 지우지 않아, 마지막 블록 일부가 해제된 스택에 남을 수 있습니다. TOTP 키 처리와 같은 성질입니다.
- 삭제 기록은 최대 65,536개이고 압축하지 않습니다.
- 서버를 Windows에서 돌리면 폴더 fsync, 금고 수 잠금(동시에 처음 올리면 64개를 넘을 수 있음), 동시 접속 제한, 디스크 여유 공간 기준, 시간 제한이 모두 빠지므로 시험용으로만 씁니다. 도난당한 동기화 키는 접속 8자리를 모두 붙잡아 모든 PC의 동기화를 멈출 수 있습니다(서비스 거부).
- 목록 상자 등 Windows 컨트롤이 가진 항목 이름 사본은 잠근 뒤에도 해제된 메모리에 남을 수 있습니다(README의 기존 한계). 앱이 관리하는 상태 줄 버퍼는 커지지 않게 만들고 바꿀 때 지웁니다.

**설정 창 (`goyo-sync.exe`를 인자 없이 실행).** goyo-sync.conf를 손으로 쓰고, 서버 스크립트를 scp로 올리고, 명령줄을 써야 하던 설정을 창 하나로 하자는 요청에 따라 더했습니다. 사용법은 [SYNC.md](SYNC.md) 1~3절에 있습니다.
- **실행 방식.** 인자 없이 실행하면 설정 창이 열립니다(실행 파일 경로마다 하나, 창 전용 이름 있는 뮤텍스. 두 번째 실행은 열린 창을 앞으로 가져오고 끝남). 예전의 '인자 없음' 백그라운드 동기화는 `--background`로 옮겼고, `--autostart on`은 `"<exe>" --background`를 등록합니다. 창과 `--background`는 콘솔에 붙지 않습니다(붙으면 그 콘솔을 닫을 때 도우미가 끝남).
- **모양과 코드.** 금고 앱의 `win.rs`·`theme.rs`·`i18n.rs`를 `#[path]`로 그대로 포함해 같은 색·글꼴·직접 그리는 버튼·입력 테두리를 씁니다. `win.rs`의 시작 방어(`initialize_defenses`, 하위 프로세스 금지인 정책 13)는 부르지 않고 `sys.rs`의 방어를 그대로 씁니다. 다크·라이트와 언어는 실행 파일 옆 `goyo-vault.theme`·`goyo-vault.lang`을 따르고, 창이 열린 동안에도 2초마다 따라갑니다. 창의 한국어 문자열은 모두 `i18n.rs`에 영어가 있고, `english_is_complete`가 `gui.rs`도 검사합니다.
- **읽고 쓰는 것.** 설정은 goyo-sync.conf와 같은 규칙으로 검사합니다(만든 글을 `config::parse`로 되읽어 입력과 같은지 확인하고, 주석을 시작하는 `#`나 줄바꿈이 든 값은 미리 거부). 저장은 임시 파일을 쓴 뒤 이름을 바꿉니다. 금고 목록의 상태는 동기화 폴더의 `status`·`helper.state`와 폴더 목록만 읽고, **금고·열쇠 파일은 열지 않습니다**. 경로는 파일 대화상자에서만 받고 `*.goyokey`는 거부합니다. 서버에서 받은 사본을 저장할 새 파일이 이미 있는지도 핸들을 열지 않고 폴더 목록으로 봅니다(사용자가 쓰고 있는 금고를 고를 수도 있어서). 로그 보기는 `goyo-sync.log`(와 `.log.1`)의 끝 400줄만 창 안에서 보여 주고, 다른 프로그램을 실행하지 않습니다.
- **작업 스레드와 결과 전달.** ssh를 쓰는 작업은 모두 작업 스레드에서 돌고 창은 기다리지 않습니다. 결과는 이 프로세스 안의 슬롯(`Mutex`)에 두고 내용 없는 사설 메시지만 보내므로, 다른 프로그램이 결과를 위조하거나 볼 수 없습니다. 대기열로 들어온 가짜 알림은 빈 슬롯을 볼 뿐이고, 다른 스레드가 보낸 알림은 버립니다. 창을 닫으면 실행 중인 ssh는 바로 끝나지만, 도우미 재시작은 끝까지 마친 뒤(최대 25초) 프로세스가 끝납니다. '저장하고 시작' 직후 창을 닫아도 예전 도우미만 멈추고 새 도우미는 시작하지 않은 채 남는 일이 없습니다.
- **메시지 거르기.** 금고 앱과 같은 방식입니다. 창은 다른 스레드가 보낸 명령·클릭·키·마우스·타이머·직접 그리기·색 메시지·작업 알림을 무시하고(버튼이 다른 스레드의 `BM_CLICK`을 처리하며 보내는 명령 포함), 입력 칸과 목록은 다른 스레드가 보낸 모든 메시지를 무시합니다. 메시지 루프와 대화상자 안의 `WH_GETMESSAGE` 필터는 창과 그 자식에게 대기열로 들어온 `WM_COMMAND`·`WM_SETTEXT`·`BM_*`·`EM_*`·`LB_*`·직접 그리기·활성화 메시지와 이동 등의 시스템 명령을 버리고, 키·마우스 입력은 이 프로그램의 창이 앞에 있을 때만 받습니다. 예/아니요 질문은 금고 앱의 `confirm`(CBT 훅으로 지킨 상자)을 씁니다. 회귀 테스트가 다른 스레드에서 보낸 저장 명령·버튼 클릭·글자 바꾸기와 대기열 메시지가 아무것도 바꾸지 않음을 확인합니다.
- **서버 설치.** 서버 스크립트를 실행 파일에 넣고(`include_bytes!`, 테스트가 배포 파일과 바이트 단위로 같은지 확인) ssh 표준 입력으로 보낸 뒤 고정 명령 하나를 실행합니다: `umask 077 && mkdir -p <폴더> && cat > <remote>.new && chmod 700 <remote>.new && <python> -I <remote>.new selftest && mv -f <remote>.new <remote>`. 받은 사본의 selftest가 통과해야 기존 스크립트와 바꾸므로, 전송 중 연결이 끊겨 `cat`이 잘린 사본을 끝까지 받은 것처럼 끝나도 잘린 스크립트가 설치되지 않습니다(검토에서 순서를 바꿈). 명령은 goyo-sync.conf 문자 집합(영문·숫자와 `. _ / ~ + -`, `-`로 시작 불가)으로 검사한 `remote`·`python`으로만 만들므로 셸에서 특별한 뜻을 가진 문자가 없습니다. 앞에 오는 `~`만 홈 폴더로 펼쳐지는데, `serve` 명령도 같아서 스크립트는 도우미가 찾는 곳에 놓입니다. 파일 이름으로 끝나지 않는 경로(`/`, `.`, `..`, `~`로 끝남)는 거부합니다. ssh 옵션은 도우미와 같고(`--` 뒤에 호스트와 명령 한 개), 전용 키는 서버에서 `serve`만 실행하는 강제 명령일 수 있어 쓰지 않고 평소 로그인을 씁니다(확인 창에서 설명). 실행 전에 서버와 경로를 보여 주고 묻습니다. selftest가 정확히 `PASS`만 출력하고 바꾸기까지 끝나야 성공이고, 출력·시간 제한은 `run_bounded`와 같습니다. ssh 자신의 실패(종료 코드 255)와 원격 명령의 실패(예: `mkdir`의 `Permission denied`)를 구별해 알립니다.
- **처음 연결(처음 사용할 때 신뢰).** HELLO가 호스트 키로 실패하면 ssh 자신의 메시지(`-E` 로그. 서버가 출력한 글은 보지 않음)로 '처음 보는 키'와 '바뀐 키 또는 모르는 메시지'를 가릅니다. 처음 보는 키라도 `ssh -G`로 known_hosts에 쓰이는 이름(HostKeyAlias, 또는 `[host]:port`)을 구하고, `ssh-keygen -l -F`로 그 이름에 이미 다른 키가 있으면 묻지 않고 멈춥니다(서버가 알려진 종류의 키를 더 이상 내놓지 않는 경우). 아무 키도 없을 때만, 처음 사용할 때 신뢰가 무엇이고 무엇을 믿게 되는지 설명하는 예/아니요 질문을 띄웁니다. '예'일 때만 ssh 호출 **한 번**을 `StrictHostKeyChecking=accept-new`로 하고(다른 옵션은 그대로, 테스트가 인자 하나만 다른지 확인), 저장된 키의 `ssh-keygen -l -F` 출력(지문)을 보여 주며 서버에서 직접 확인한 지문과 비교하라고 안내합니다. **바뀐 키는 창에서 받아들이지 않고** 설명만 합니다. `ssh -G`와 `ssh-keygen`도 System32\OpenSSH에서 고정 인자로, `run_bounded`로 실행하며, 해석한 이름은 영문·숫자·`. _ - :`로 검사합니다.
- **백그라운드 시작과 자동 시작.** '저장하고 시작'은 설정을 저장하고 자동 시작을 적용한 뒤, 실행 중인 도우미에 중지 신호를 보내 그 뮤텍스가 사라질 때까지 기다리고(남은 도우미 때문에 새 도우미가 자신을 두 번째로 여기고 끝나는 일을 막음), `CreateProcessW`로 `"<exe>" --background`를 시작합니다. 핸들은 상속하지 않고(그 순간 실행 중인 ssh의 파이프도 넘어가지 않음), 창과 콘솔이 없으며, 허용되면 호출한 쪽의 Job 밖에서, 작업 폴더는 System32입니다. 실행 중인지는 도우미의 뮤텍스를 열어 보고 바로 닫아 판단하고, 창이 그 뮤텍스를 만들지는 않습니다(열어 둔 핸들이 이름을 살려 두면 다음 도우미가 시작하지 않음). 자동 시작 스위치는 끄면 바로 Run 값을 지우고, 켜기는 저장할 때 씁니다. 스위치가 지금 상태를 보여 주도록 Run 값을 읽는 `RegGetValueW`를 더했습니다.
- **바이너리.** `goyo-sync.exe`가 이제 금고 앱과 같은 UI DLL인 user32·gdi32·comdlg32·dwmapi·uxtheme를 가져옵니다(imm32는 없음). `inspect_pe.py`의 sync 프로필은 이 다섯을 허용하고 user32 금지를 뺐으며, advapi32 허용 함수에 `RegGetValueW`를 더했습니다. 소켓·HTTP DLL, crypt32·secur32, OS 암호·난수 함수, `WinExec`·`ShellExecute*`, 서수 import 금지는 그대로입니다. 이 기록 시점 릴리스 빌드의 import는 USER32(57개), KERNEL32(127개), ADVAPI32(`RegDeleteKeyValueW`, `RegGetValueW`, `RegSetKeyValueW`), GDI32(15개), ntdll(5개, 위와 같음), dwmapi(`DwmSetWindowAttribute`), UxTheme(`SetWindowTheme`), COMDLG32(`GetOpenFileNameW`, `GetSaveFileNameW`), `api-ms-win-core-synch-l1-2-0`(3개)입니다. `--self-check`는 창을 숨긴 채 모든 화면을 만들어 UI DLL까지 불러온 뒤 검사하고, DLL 심기 검사는 goyo-sync.exe에 금고 앱과 같은 10개 이름을 심어 보고 통과했습니다. vault 프로필과 goyo-vault.exe의 DLL 목록은 바뀌지 않았습니다.
- **테스트.** 설정 창 테스트 13개를 더했습니다(화면 미리보기 1개는 따로, `--ignored`로만). goyo-sync 테스트는 보안 검토 수정까지 모두 51개입니다. ssh 실행, 레지스트리, 실제 백그라운드 프로세스는 없고 가짜 실행기와 가짜 시스템을 씁니다. 설정 칸 → 글 → `config.rs` 해석 왕복과 칸마다 오류 위치, 설치 명령 고정 문자열과 나쁜 값 거부, 호스트 키 다음 단계(처음·바뀜·다른 종류·확인 불가), 연결 확인과 설치의 모든 실패 분류, 재시작 순서와 목록 상태와 로그 끝, 받기와 지금 동기화, 숨긴 창에서 칸 채우기·금고 추가와 빼기·저장(테스트 폴더의 goyo-sync.conf와 가짜 자동 시작 호출 확인), 설치·처음 연결·바뀐 키·서버에서 받기·로그 보기 흐름, '저장하고 시작' 직후 창을 닫아도 재시작이 끝난 뒤 끝나는지, 잘린 사본이나 마지막 바꾸기 실패가 설치로 보이지 않는지, 다른 스레드가 보낸 명령·`BM_CLICK`·마우스 클릭(저장이 통과할 설정에서)과 대기열 메시지 무시, 두 언어에서 모든 글자가 칸에 맞는지, 영어 화면에 한국어가 없는지.
- **남은 한계.** 처음 연결의 신뢰는 그 순간의 네트워크를 믿는 것이고, 지문 비교가 기준입니다. `ssh-keygen -F`는 기본 known_hosts만 보므로 `UserKnownHostsFile`을 바꾼 설정에서는 지문을 확인하지 못했다고 알리고 끝납니다. 금고 목록의 상태는 2초마다 창의 스레드에서 폴더 목록과 상태 파일을 읽으므로, 연결이 끊긴 네트워크 공유(`\\server\share\…`)에 있는 금고는 그 읽기가 끝날 때까지 창을 잠시 멈추게 할 수 있습니다(ssh 작업은 해당 없음). 창이 앞에 있을 때 대기열로 들어온 키·마우스 입력과 `SendInput`은 사용자 입력과 구별할 수 없습니다(금고 앱과 같은 기존 한계, 같은 사용자 권한의 악성코드는 범위 밖). 설치 명령은 실제 서버의 별도 시험 경로에서 실행해 `PASS`와 0700 권한을 확인했습니다(시험 경로는 지움). 그 밖의 창 흐름은 실제 서버에 연결해 사람이 시험하지 않았습니다. 자동 테스트와 릴리스 빌드의 `--self-check`, PE 검사, DLL 심기 검사, 화면 밖 렌더링으로 본 두 테마·두 언어 화면까지 확인했습니다.

이번 변경도 외부 모델(MCP를 거친 다른 모델) 검토는 받지 않았습니다. 설계·검토 에이전트에는 공개 소스와 가짜 데이터만 썼고, 실제 서버 주소·계정·금고는 쓰지 않았습니다.

## 0.9.0 변경: 열쇠 교체 (기본 빌드)

0.9.0의 기본 빌드(릴리스 ZIP)는 보안 키 기능 없이, 비밀번호 변경을 **데이터 키 교체**로 바꾸고 다른 PC의 열쇠 파일을 받는 기능('새 열쇠 파일 받기')과 PC마다의 열쇠 기록을 더합니다. 보안 키(P+G) 설계와 열쇠 파일 동기화의 위협 분석과 잔여 위험은 아래 '0.9.0 변경: 보안 키(실험)와 열쇠 파일 동기화(실험)'에 있습니다. 새 의존성은 없고, HKDF는 기존 `hmac`·`sha2`로 구현해 RFC 5869 시험 벡터와 `--self-check`로 확인합니다.

**무엇이 바뀌나.** 비밀번호를 바꾸면 무작위 256비트 데이터 키를 새로 만들어 금고를 다시 암호화하고, 새 열쇠 파일(`GOYOKE03`)은 최근 63개와 처음 데이터 키를 담습니다(예전 백업 복원용. 처음 키는 ID 키로 v1 항목 ID와 확인 코드에 계속 씀). 열쇠 파일의 상태(수정 번호, 상태 태그)와 현재 키 ID를 금고 파일 머리글(`GOYOVA03`/`GOYOVA04`)에도 적어, 키를 유도하기 전에 어느 키의 사본인지 구분합니다. 새 열쇠 파일의 본문 키는 비밀번호 키와 파일 앞부분 해시에서 HKDF로 만들고(`C_body` 확인값으로 커밋), 키 ID마다 그 데이터 키로 만든 chain 값을 붙여 누가 썼는지 확인합니다. 금고 AEAD는 0.8과 같이 무작위 데이터 키 아래의 XChaCha20-Poly1305입니다.

**위협별 결과.**

|공격자|결과|
|---|---|
|열쇠 파일(n = 0, `GOYOKE01/02/03`)|0.8과 같이 오프라인 Argon2 추측. `GOYOKE03`은 서버로 가지 않습니다.|
|예전 열쇠 사본과 그 비밀번호|열쇠를 바꾼 뒤 저장한 내용은 열지 못합니다. 그가 예전 키로 올린 사본은 새 열쇠 파일을 받은 PC가 합치지 않고 덮어쓰고(카운터는 2^16 창 안에서만 세고 `seen`은 올리지 않음), 현재 키 ID를 단 위조는 AEAD에서 실패해 손상으로 처리됩니다. 바꾸기 전의 모든 것(서버 기록, 백업)은 계속 읽습니다. 열쇠 교체가 보호하는 것은 그 뒤에 저장하는 내용뿐이라 문서에 그렇게 적었습니다.|
|금고 폴더나 열쇠 USB에 쓸 수 있고, 예전의 진짜 열쇠·금고 파일 짝을 가진 사람|짝을 되돌려 놓을 수 있습니다. 열린 두 파일만으로는 알 수 없지만 이 PC의 열쇠 기록이 알아봅니다: 기록의 이력에 있는 예전 상태는 '예전 열쇠 파일' 경고와 함께 열되 열쇠 변경·합치기·올리기·서버 사본 덮어쓰기를 멈추고, 이력에 없는 같거나 낮은 수정 번호, 확정 상태의 현재 키 ID가 없는 더 높은 수정 번호(예전 열쇠 파일로 새로 만든 것), 2^16 넘게 큰 수정 번호, 기록한 제거가 빠진 파일은 비밀번호를 묻기 전에 거부합니다. 예전 키로 저장된 금고 파일만 넣으면 이 PC가 마지막으로 쓴 키(`vkey`)일 때만 묻고 그 밖에는 거부하며, 그 카운터가 2^40을 넘으면 열지 않습니다.|
|털린 서버, 비밀번호 없음|0.8과 같습니다. 모르는 키의 사본, 예전 키로 인증되지 않는 사본, 현재 키로 더 새 상태나 같은 수정 번호의 다른 상태인 사본은 **멈춤**(합치지도 덮어쓰지도 않음, 기록하지 않고 열 때마다 다시 판단). 0.8은 인증되지 않는 사본을 모두 이 PC 상태로 덮었지만, 이제 그 복구는 현재 키 사본에만 합니다(더 새로운 열쇠 교체의 사본을 예전 키로 덮지 않도록). 그래서 위조된 사본으로 멈추게 할 수는 있습니다(서비스 거부). 멈춤 알림은 위조 가능성을 함께 말합니다.|

|같은 사용자 권한의 악성코드|범위 밖입니다. 열쇠 기록도 인증되지 않아 바꿀 수 있습니다.|

**검사 순서와 오라클.** 열쇠 기록 비교, 머리글 문법, "이 열쇠 파일에 없는 열쇠", 보안 키 파일 거부, 예전 키 금고 파일의 확인은 모두 Argon2 전에 공개된 바이트로만 하고, 실패 횟수와 대기 시간에 넣지 않으며 비밀번호에 대해 아무것도 말하지 않습니다. 비밀번호가 틀리면 어느 경우든 같은 `인증 실패`이고, 이 PC의 열쇠 기록이 그 열쇠 파일에 대해 아는 것(끊긴 변경, 이 PC에서 바꾼 비밀번호)만 덧붙입니다.

**충돌 안전성.** 변경은 메모리에서 새 열쇠 파일과 금고 파일을 만들어 다시 열어 본 뒤에만 쓰고, 열쇠 기록의 보류 줄 → 예전 키의 금고 파일(그 SHA-256이 새 열쇠 파일의 `resume`) → 새 열쇠 파일(다시 읽어 확인) → 새 키의 금고 파일 → 확정 순으로 씁니다. 어느 순간에 꺼져도 디스크의 열쇠 파일은 디스크의 금고 파일을 엽니다. 다음 잠금 해제는 보류 줄로 이 PC의 변경을 알아보고 마저 끝내거나 버리고 알립니다. 열쇠 파일이 저장되었는지 알 수 없으면 앱이 그 파일을 메모리에 들고 저장을 거부하며 열쇠 백업으로 저장하게 한 뒤 잠급니다. FAT·exFAT의 교체 틈은 임시 파일을 남기고 앱이 잠그며, 다음 잠금 해제가 되돌립니다. 각 지점에서 끊는 시험(crash injection)을 lib 시험으로 돌립니다.

**사람이 정하는 것.**
- **이 열쇠 파일이 맞습니다:** 예전 열쇠 파일 경고를 확정합니다. 비밀번호(와 OTP)를 다시 확인하고, 위험 질문(기본 '아니요')을 먼저 묻습니다. 그 뒤로 이 PC는 그보다 나중의 열쇠 변경을 기억하지 않습니다. 복원한 금고에서는 나오지 않습니다. 동기화하는 금고면, 서버 사본이 더 나중의 열쇠로 저장되어 있을 때 그 뒤 동기화가 다시 멈추고 그 사본을 이 PC가 올렸다면 서버 사본 덮어쓰기를 쓰라고 질문과 결과에 적습니다.
- **서버 사본을 이 PC 상태로 덮어쓰기:** 어느 PC도 풀 수 없는 멈춤(열쇠를 바꾼 PC가 열쇠 파일 없이 사라짐, 또는 분실한 PC의 동기화 키로 올린 쓰레기)을 위한 마지막 수단입니다. 비밀번호 재확인, 그 사본의 수정 번호·키 ID·서버 버전을 보여 주는 위험 질문, 그리고 올리기 직전 그 버전·바이트가 그대로인지 다시 확인합니다. 그 세션의 그 사본(버전과 바이트)에만 적용되고 기록하지 않습니다. 덮인 사본은 서버 기록에 남습니다. 열쇠를 바꾼 PC가 살아 있다면 그 PC가 이 사본을 예전 키 사본으로 보고 다시 덮어 데이터를 잃지 않지만, 잘못 쓰면 그 PC의 정당한 변경을 한동안 덮습니다. 예전 열쇠 파일 경고 중에는 나오지 않습니다(그때 멈춘 사본은 대개 이 PC 자신의 새 키 사본).
- **끝나지 않은 열쇠 변경 버리기:** 다른 위치의 열쇠 파일에 저장되었을 수 있는 변경을, 비밀번호 재확인과 위험 질문 뒤에 잊습니다.

**복원한 금고.** '백업 파일로 되살리기'로 연 금고에서는 지금 열쇠 파일로 복원했어도 열쇠를 바꾸거나 새 열쇠 파일을 받지 않습니다. 원래 금고 파일과 같은 열쇠 파일·같은 금고 ID를 쓰므로, 복원한 쪽에서 바꾸면 원래 금고 파일이 예전 키로 남아 열기 전에 거부되고(바꿔 넣은 예전 금고 파일과 같은 문구) '복원'으로만 열리기 때문입니다. 복원한 파일을 계속 쓰려면 잠근 뒤 로그인으로 엽니다.

**이 PC의 열쇠 기록의 한계.** `%LOCALAPPDATA%\GoyoVault\goyo-vault.keys`는 인증되지 않은 두 번째 기준이라, 공격자가 쓸 수 없는 곳(금고 폴더·열쇠 USB와 다른 곳)에 있을 때만 보호합니다. 비밀은 없지만 금고 ID, 수정 번호, 열쇠를 바꾼 횟수와 그 키 ID 앞부분, 진행 중인 변경의 열쇠 파일 경로를 담습니다. 기록이 없는 PC(지웠거나 그 금고를 0.9.0 열쇠 파일로 연 적이 없음)는 되돌림을 알아보지 못하고, 예전 키의 금고 파일도 먼저 묻기만 합니다. 기본 빌드의 마지막 수단은 이 파일을 지우는 것이라, 그때 모든 금고의 기록을 잃습니다(README). 더 새로운 버전이 쓴 기록은 고치지 않고, 쓸 수 없으면 세션 동안 메모리에 둡니다. 열기 전 비교 때 이 파일을 읽지 못했으면(다른 프로그램이 열고 있음) 기록이 없는 것으로 비교하지만, 잠금 해제가 잠근 뒤 다시 읽은 줄이 그때와 다르면 열지 않고 다시 열게 하며, 열쇠 변경은 확정 상태보다 낮은 상태(같은 수정 번호에서 그 상태의 현재 키를 담지 않은 다른 상태 포함)를 쓰지 않습니다.

**공개되는 메타데이터.** 금고 파일 머리글의 키 ID, 수정 번호, 상태 태그가 공개되어, 서버는 열쇠를 바꾼 횟수와 대략의 시각을 압니다. 열쇠 파일의 `written` 시각과 `pw_id`(비밀번호를 바꿀 때마다 새 무작위 값)도 공개입니다. 열쇠 확인 코드(64비트)는 현재 데이터 키로만 계산됩니다. 확인 코드는 KF2 금고에서 열쇠 상태도 포함합니다.

**한도.** 데이터 키는 64개까지 담고(ID 키는 버리지 않음), 그보다 오래된 키의 백업은 그때의 열쇠 사본으로 엽니다. 수정 번호는 2^48−1까지이고, 공개 수정 번호가 이 PC가 증명할 수 있는 것보다 2^16 넘게 크면 받지 않아, 위조된 수정 번호로 PC를 끝까지 밀어 올릴 수 없습니다(`panic = "abort"`·overflow 검사 아래 덧셈은 모두 검사). 제거 기록은 480개까지이고 지우지 않습니다.

**흐름 안의 입력 창.** '새 열쇠 파일 받기'는 다른 파일의 비밀번호와 미리보기를 한 흐름 안의 입력 창으로 묻습니다. 이 창은 금고 창이 소유한 모달 창으로, 다른 스레드가 보낸 명령·입력을 버리고(확인 창과 같은 규칙), 대기열에 넣은 가짜 클릭·명령은 메시지 필터가 막으며, 화면 캡처에서 빠지고, 비밀번호 칸에 앱의 입력 보호(다른 프로그램의 읽기 차단, 암호 입력 범위)를 겁니다. 하나라도 걸 수 없으면 '취소'로 답합니다. 잠금(자동 잠금, Win+L, 절전 등)은 창을 닫고 흐름을 끝냅니다. 흐름 동안에는 미사용 잠금이 10분 이상으로 늘고(꺼짐은 그대로), 다른 앱에 머무는 30초 잠금도 같은 한도를 따릅니다. 흐름의 재인증(비밀번호와 OTP 한 번)은 그 흐름 안에서만 살고 끝나면 지웁니다.

**시험.** 각 열쇠 변경 단계에서 끊는 시험, 열쇠 기록의 분류·보류 줄·임시 파일 복구, 서버 사본 판정의 모든 행(두 PC, 세 PC), 받기의 각 경우와 거부, 한 흐름의 받기(OTP 한 번, 틀린 비밀번호 다시 묻기, 취소·'아니요'·잠금이면 아무것도 쓰지 않음), 다른 스레드가 입력 창에 보내는 클릭·입력·읽기가 무시되는 것을 자동 시험으로 확인합니다. 실제 FAT/exFAT USB를 뽑는 시험은 하지 않았습니다.

## 0.9.0 변경: 보안 키(실험)와 열쇠 파일 동기화(실험)

보안 키(FIDO2 hmac-secret)와 열쇠 파일 동기화는 Cargo 기능 `security-key`(기본 꺼짐) 뒤에만 있습니다. 릴리스 ZIP(`package_release.py`)은 기본 빌드이고, 기본 기능이 켜진 `Cargo.toml`이면 패키징을 거부합니다. 기본 빌드에는 WebAuthn 코드, 가짜 인증기, 시험용 훅이 없고, 보안 키 열쇠 파일은 매직만 보고 비밀번호를 묻기 전에 거부합니다(위 '0.9.0 변경: 열쇠 교체'와 [SECURITY_KEY.md](SECURITY_KEY.md) 마지막 절). **실제 보안 키로는 아무것도 확인하지 않았습니다**(아래 '실제 키 점검표'). 모든 시험은 Windows의 WebAuthn 동작을 흉내 내는 가짜 인증기로 했습니다. 사용법은 [SECURITY_KEY.md](SECURITY_KEY.md), 형식은 [FORMAT.md](FORMAT.md)의 '보안 키 열쇠 파일'에 있습니다.

새 의존성은 없습니다. 공개 키 암호도 쓰지 않습니다(X25519·ECIES 없음). 모든 구성은 기존 `hmac`·`sha2`로 만든 HKDF-SHA256, Argon2id, XChaCha20-Poly1305이고, HKDF는 RFC 5869 시험 벡터, hmac-secret salt는 고정 시험 벡터로 `--self-check`에서도 확인합니다(보안 키 빌드: `salt self-test: PASS`).

### 설계 요약 (P+G)

- **두 비밀.** 키세트 비밀 S(무작위 32바이트)는 등록한 키의 hmac-secret 출력으로만 꺼냅니다. 데이터 키 묶음(본문)은 Argon2id(비밀번호) **와** S로 만든 키로 잠급니다. 비밀번호만으로 확인할 수 있는 값이 없으므로, 보안 키 없이 비밀번호를 오프라인으로 추측하는 비용은 2^256입니다. S를 알고 나면(그 파일에 S 포장이 있는 키의 응답 하나, PIN 모드면 PIN도) 0.8의 '열쇠 파일만 가진 경우'와 같은 Argon2 속도의 추측이 남습니다.
- **짝(P).** 함께 터치한 두 키 o, t 사이에 전달 열쇠 `IK(t←o)`(t의 하드웨어 출력에서 유도, 두 키의 seed를 모두 묶음)를 만들고, o만 여는 짝 기록 `PR(o, t)`에 넣습니다. 쓰는 PC는 터치한 키에는 그 키 자신의 값으로, 터치하지 않은 키에는 승인 키 a의 짝 기록에서 꺼낸 `IK(·←a)`로 새 S를 포장합니다. **P-INV:** `IK(t←o)`는 o나 t의 하드웨어만 만들거나 열 수 있습니다. 그래서 비밀번호 변경, 키 추가, 키 제거가 **모든 키와 짝을 맺은 키 하나, 터치 한 번** 으로 되고, 키를 옮길 필요가 없습니다.
- **쓸 때마다 새 S.** 모든 쓰기가 S를 새로 뽑고, 뺀 키에는 S 포장도 짝 기록도 주지 않습니다. 뺀 키 X는 `IK(·←X)`와 `IK(X←·)`만 알고, 그 뒤의 어떤 S 포장도 그 열쇠로 잠기지 않습니다(X는 승인 키도 받는 키도 아님). 그래서 뺀 뒤에 쓴 파일은 X로 열리지 않습니다.
- **승인 키 묶기.** 모든 쓰기는 승인 키를 머리글에 적고, 승인 키는 그 파일에서 살아 있어야 하며, 키는 자기 자신의 제거를 승인할 수 없습니다. 그래서 **어떤 파일도 자기 작성자를 뺄 수 없습니다.**
- **공개 검사(터치 전).** P3: 받는 파일은 이 PC의 모든 제거 기록을 담아야 함. P4: 이 PC가 뺀 키가 승인한 파일은 거부. 칸 고정: 이 PC가 아는 키의 번호·등록 정보는 바뀌면 G1. 짝 기록 고정: 이 PC가 가진 짝 기록은 이 PC가 손상을 확인한 것만 바뀔 수 있음.
- **관문(G).** 다른 PC는 키 구성이나 정책 변경을 관문 뒤에서만 받습니다. G2(제거만): 변경에 대해 아무것도 보이기 전에 사용자가 이 PC 자신의 목록에서 잃어버린 키를 고르고, 실제 제거 집합과 정확히 같을 때만 통과합니다. 한 번만이고, 틀리면 R을 밝히지 않고 G1만 남깁니다. G1(추가, 정책 변경, 처음 보는 키의 제거, 처음 받는 열쇠 파일과 USB 사본): 바꾼 PC에 보이는 64비트 열쇠 확인 코드를 입력합니다. 코드는 새 데이터 키로 계산하므로 뺀 키를 가진 사람은 계산하거나 맞혀 볼 수 없습니다.
- **관문을 없앨 수 없는 이유.** (1) 작성에 키, 비밀번호, 서버가 볼 수 있는 상태, 난수만 쓴다면 '한 키로 제거', '사용자 실수 없이는 뺀 키 쪽 변경을 받지 않음', '조용히 받기'를 모두 만족할 수 없습니다. 사용자가 ℓ을 잃고 a로 뺀 세계와, a를 잃고 ℓ로 뺀 세계는 뒤처진 PC에서 똑같이 보이기 때문입니다. 그래서 서버가 줄 수 없고 뺀 키를 가진 사람이 예측할 수 없는 정보(고른 키, 열쇠 확인 코드, 제거 때 바꾼 비밀번호)가 필요합니다. G2가 맞는 것은 어떤 파일도 자기 작성자를 뺄 수 없기 때문입니다. (2) 적대적인 서버가 어떤 PC를 예전 상태에 묶어 두는 것(동결)은 어떤 설계로도 막을 수 없습니다. (3) 대칭 암호만으로 한 키 제거가 뺀 키에 대해 비밀을 지키려면, 분실 전에 남는 키 사이에 뺀 키가 열 수 없는 짝 비밀이 있어야 합니다(짝 기록).
- **열쇠 확인 코드**는 (`epoch`, 상태 태그)를 현재 데이터 키로 묶은 HMAC입니다(공개 정보로 계산 불가).
- **이 PC의 열쇠 기록**은 보안 키 금고에 필수입니다(쓸 수 없으면 열쇠 변경과 금고 올리기를 멈춤). 보안 키 금고로 기록한 금고에 비밀번호만으로 여는 열쇠 파일이 오면, 기본 빌드와 보안 키 빌드 모두 거부합니다.
- **검토 목록.** 분실로 키를 뺀 뒤, 분실 날짜 하루 전부터 동기화로 들어온 변경을 보여 주고, 확인할 때까지 금고 내용을 올리지 않습니다(열쇠 파일은 올라감). 합치기 기록 `goyo-vault.merges`에서 읽습니다.

### 누가 무엇을 할 수 있나

X = 뺀 키. X를 가진 사람은 X가 열었던 모든 것(PIN을 알면 X의 응답, 비밀번호, 서버 기록의 예전 열쇠 파일, 그러니 예전의 모든 S와 데이터 키, `IK(·←X)`와 `IK(X←·)`)을 안다고 봅니다. '뒤처진 PC'는 X의 제거를 아직 받거나 쓰지 않은 PC입니다.

|공격자가 가진 것|결과|
|---|---|
|열쇠 파일(n = 0, `GOYOKE01/02/03`)|0.8과 같은 오프라인 Argon2 추측. `GOYOKE03`은 어떤 경로로도 서버에 가지 않음|
|열쇠 파일(n ≥ 1, `GOYOKH01`/`GOYOKS01`. PC, USB, `GOYOKS01`이면 서버)|오프라인 추측 불가|
|열쇠 파일 + 비밀번호|등록하고 일시 정지되지 않은 키(PIN 모드면 PIN도)가 필요|
|보안 키를 켜기 전의 비밀번호만 쓰는 열쇠 파일(0.8 파일, 그 백업, 예전 `GOYOKE03`)|그 파일의 비밀번호를 오프라인으로 추측. 켤 때 비밀번호를 그대로 두었다면, 맞힌 비밀번호와 지금 열쇠 파일로 남는 장벽은 등록한 키(와 PIN)뿐. 그래서 켜기와 합치기가 '비밀번호도 바꾸기'를 먼저 권하고 그대로 두면 알림|
|등록한 키, 열쇠 파일 없음|열쇠 파일(자격 증명 ID, seed, S 포장)과 비밀번호가 필요. 열쇠 파일 동기화에서는 서버가 열쇠 파일을 가지므로 PIN 모드가 필수|
|PIN 모드의 키를 PIN 없이 훔침|없음: credProtect 3이 PIN 없는 조회를 거부하고 8번 틀리면 잠김(credProtect 3 등록은 YubiKey 5C NFC에서 확인, PIN 없는 조회의 거부는 미확인, 점검표 8)|
|열쇠 파일 + 등록한 키, PIN 없는 모드(`GOYOKH01`만)|터치 한 번으로 그 키의 응답을 얻고, 그 키에 S 포장이 있는 지금과 이후 모든 파일의 S를 앎. 그 뒤 Argon2 속도 추측. 출시 전 시험 빌드의 파일에만 해당: Windows가 등록 때 키에 PIN을 정하게 하고 그 뒤 매번 PIN을 물으므로(실제 키로 확인) 이 빌드는 PIN 모드로만 등록하고 씀|
|빌린 키에 한 번 터치(evil maid)|PIN 없는 모드(출시 전 시험 빌드의 파일만): 그 키가 빠졌다가 다시 등록되거나 '모든 키 새로 잠그기'를 할 때까지 그 키의 복제. 비밀번호 변경이나 다른 키 제거로는 쫓아내지 못함. PIN 모드: PIN도 필요하고, 있으면 같은 복제. 모든 키가 같은 PIN이면 잃어버린 키와 PIN을 가진 사람이 같은 장소의 다른 키를 한 번 터치로 복제할 수 있음(그래서 키마다 다른 PIN을 권하고, 분실 흐름이 같은 PIN의 키를 '복제됐을 수 있음'으로 표시). 복제는 살아 있는 키처럼 열고 쓸 수 있고 G2도 통과함. G1만 막음. 복제는 다른 키의 짝 기록을 엉터리로 써서 그 키를 조용히 막을 수도 있음(두 키가 함께 있을 때 다시 짝 맺기로 고침)|
|뺀 키를 가진 사람, 서버 통제 없음|제거 뒤에 쓴 사본은 열리지 않음(P-INV). 제거 전의 모든 것(서버 기록, 예전 열쇠 파일)은 읽음. 그가 예전 데이터 키로 올린 사본은 새 키를 가진 PC가 덮어씀. 뒤처진 PC에는 예전 데이터 키로 사본을 올려 합치게 하고 그 PC가 올리는 것을 읽을 수 있음: 열쇠 파일이 PC에만 있는 금고는 그 PC가 USB로 제거를 받을 때까지, 열쇠 파일 동기화 금고는 정직한 서버의 금고 기준이 그런 사본을 거부하고, 끊음(끄기나 훔친 키의 CUTKEY) 뒤에는 `GOYOKS01` PC가 금고 채널을 멈춤. 끊음 위로 그가 승인한 파일을 올려 그 멈춤을 풀 수도 없음(정직한 서버가 `k/tombs`로 확인). 그 PC에서 '잃어버린 키 제거'를 하면 끝남|
|같은 사람 + 서버 통제, 최신 PC 상대|**아무것도 받지 않음.** 그가 만든 파일은 모두 X를 승인 키로 적고 X를 살려 두므로 최신 PC가 터치 전에 거부(P4). 다른 승인 키를 적은 파일은 이 PC가 더한 제거 기록이 빠지거나 다시 담겨 거부(P3)되거나, 갈라짐으로 멈추며, 어느 쪽이든 터치한 키로 열리지 않음(k나 v의 하드웨어가 필요). 예전 진짜 파일을 다시 보내도 P3와 수정 번호 규칙에 걸림. 뒤처진 PC를 거쳐 세탁한 갈래도 X를 빼 둔 합치기로만 받을 수 있음(이 PC가 직접 한 제거는 되돌리지 않음)|
|같은 사람, 뒤처진 PC 상대(동결)|사용자가 그 PC에서 무언가 할 때까지 동결과 같음: 그 PC의 새 저장은 X가 아는 데이터 키로 되어 읽히고, 서버를 통해 바꿔 넣을 수 있음(검토 목록이 제거 뒤에 보여 줌). 그가 만든 키 구성·정책 변경은 관문에서 멈춤: G2는 사용자가 X를 고르므로 통과 못 함(X가 만든 파일은 X를 빼지 못함), G1은 진짜 상태의 코드를 계산할 수 없음. 모르는 비밀번호로 바꾼 위조 '비밀번호 변경'은 받을 수 없고 분실 흐름을 막지도 않음. 비밀번호를 그대로 둔 위조는 서버나 받기로 오면 거부. 키 구성도 정책도 바꾸지 않는 변경(짝 기록, 합치기)은 조용히 받을 수 있지만 X는 이미 그 PC를 읽으므로 더 얻는 것이 없음. 진짜 제거가 도착하면 되돌림이 아니라 갈라짐으로 보임|
|같은 사람, 새 PC 상대|위조가 사용자 자신의 키와 비밀번호로 열리므로 G1만 막음. G1은 USB 사본을 포함한 모든 처음 받는 열쇠 파일에 필수. 확인할 다른 PC가 없으면 사용자가 믿고 받을 수밖에 없고(위험 질문으로 알림), 제거 때 비밀번호를 바꾸지 않았다면 위조가 받아들여짐|
|그 PC가 살아 있다고 아는 키(잃어버렸지만 그 PC가 아직 제거를 받지 않은 키 포함) + PIN + 비밀번호 + 서버에 열쇠 파일을 올릴 수 있음, '열쇠 변경 자동 적용 (이 서버를 믿음)'을 켠 PC 상대|관문(G2·G1)이 없어집니다. 그가 이 PC의 현재 데이터 키에서 이어 쓴 후속 파일(예: 다른 키 빼기, 키 추가, 키 새로 잠그기)은 공개 검사를 모두 통과하면 그 PC의 다음 잠금 해제나 [받기…]에서 묻지 않고 설치되고, 그 PC는 그가 아는 데이터 키로 바뀌어 그 뒤의 저장이 읽힙니다(R43). 그대로인 것: 공개 검사 전부(P3·P4·칸과 짝 기록 고정·E1·E5·수정 번호 창·rule D·열쇠 기록의 되돌림과 갈라짐 거부)라서 이 PC가 뺀 키가 승인한 파일, 제거 기록이 빠진 파일, 예전 파일은 여전히 터치 전에 거부. 열 때의 터치와 비밀번호, 제거 뒤 검토, 꺼진 G2(신뢰한 받기는 `clears=2`를 쓰지 않음). 쓰지 않는 곳: USB 받기, 새 PC(TOFU), 갈라진 파일(모든 옵션). 백그라운드에서 받지 않음(잠금 해제·[받기…]·실패한 잠금 해제 뒤 서버 열쇠 파일로 열기에서만). 설정은 PC마다·금고마다, 이 PC의 인증되지 않은 열쇠 기록(`auto=on`)에만 있고 기본 꺼짐, 켤 때 위험 질문(기본 '아니요'). 라이브러리는 그 판단을 서버 채널의 지금 후보(이 세션의 열쇠 보기에 있는 바로 그 상태)에만 주고, 쓰기 직전에 다시 판단. 서버만 있거나 하드웨어+PIN+비밀번호만 있으면 바뀌는 것 없음|
|비밀번호를 아는 적대적 동기화 서버, 하드웨어 없음|S 포장·짝 기록을 열지 못해 S를 모름. 어느 PC도 여는 본문을 만들지 못해 위조 열쇠 파일·데이터 키를 넣지 못함. 오프라인 추측 불가. 코드 계산 불가. 할 수 있는 것: 숨기기·지우기·망가뜨리기(멈춤, 손실 없음), 되돌리기(이 PC의 기준 아래로는 설치하지 않음), 수정 번호 부풀리기(인증 안 된 수정 번호는 이 PC의 최대보다 2^16 넘게 크면 무시하고 멈춤, 관문 없이 받는 파일은 마지막으로 쓰거나 확인한 수정 번호보다 2^8 넘게 클 수 없음), 갈라짐 경보 띄우기|
|`--key-sync`가 있는 PC의 동기화 SSH 키를 훔침(비밀번호·하드웨어 없음)|그 줄이 적은 금고의 열쇠 이름 공간에 대해 적대적 서버와 같지만 정직한 서버 스크립트가 제한함: PUTKEY 한 번에 수정 번호를 최대 2^16 올리고, 그러면 금고 기준이 예전 업로드를 거부. CUTKEY로 현재 세대를 끝냄(모든 PC에 '서버에 없음', `GOYOKS01` PC는 다시 올릴 때까지 금고 채널을 멈춤). 결과는 멈춤이나 서비스 거부이고 위조 열쇠 파일이 아님. 줄에 적히지 않은 금고에는 `k/`도 기준도 생기지 않음. 그래서 잃어버린 PC의 `authorized_keys` 줄을 바로 지우고 사람마다 서버 계정을 따로 쓰라고 안내|
|금고 폴더나 열쇠 USB에 쓸 수 있고 예전 진짜 짝을 가진 사람|짝을 되돌려 놓을 수 있음. 열쇠 기록이 알아봄: 제거한 키를 다시 담거나 그 키가 승인한 열쇠 파일, 기록한 제거가 빠진 파일은 어떤 수정 번호에서도 거부. 기록의 이력에 있는 예전 상태는 '예전 열쇠 파일' 경고로 열쇠 변경과 올리기를 멈춤. 확정 상태에서 이어지지 않은 더 새 파일은 갈라짐으로 거부. 동기화 폴더에 쓸 수 있으면 요청 파일을 심어 도우미가 CUT·PRUNE을 보내게 할 수 있음(R33: 동기화 방해와 서버 기록 삭제, 어느 PC도 여는 열쇠 파일은 아님)|
|적대적 서버 + 등록한 키와 PIN(정식 사용자)|정식 사용자가 할 수 있는 모든 것, 경쟁하는 열쇠 변경 포함. CAS, 갈라짐 멈춤, 관문이 드러냄|
|네트워크 공격자|0.8과 같음(`StrictHostKeyChecking=yes`). 첫 연결의 중간자는 적대적 서버가 됨|
|같은 사용자 권한의 악성코드|범위 밖. PIN은 Windows 창에 입력하고 키 응답은 Windows를 거침. 잠금 해제 중의 악성코드는 터치한 키를 복제함|
|미래의 양자 컴퓨터|공개 키 암호가 없으므로 뺀 키를 가진 사람이 더 얻는 것 없음|

**어떤 설계로도 다른 PC에서 아무것도 하지 않은 채 제거가 그 PC에 닿게 할 수는 없습니다.** 제거는 그것을 쓴 PC에서 바로 끝납니다. 다른 PC는 사용자가 그곳에서 무언가 하는 순간부터 보호됩니다: 관문(고르기 한 번이나 코드 입력)으로 받거나, 자기 키로 직접 제거를 씁니다(터치 한 번). 그 전까지는 위의 동결 상태입니다.

### 오라클과 변조

- **비밀번호만으로 확인할 수 있는 값이 없습니다.** 공개 값(매직, ID, 수정 번호, 칸, seed, 자격 증명 ID, 시각, 분실 날짜, 제거 기록, nonce, salt, resume)은 키가 걸려 있지 않고, `ks_id`는 S에서, 키 ID와 chain은 데이터 키에서, 짝 기록과 S 포장의 `C`와 암호문은 하드웨어 출력에서, `C_body`와 본문은 `pw_key` **와** S에서 나옵니다. 검증값, MAC, 확인 바이트, 비밀번호 칸, 복구 칸이 없습니다.
- **틀린 비밀번호와 틀린 키 응답은 같은 단계에서 같은 `인증 실패`로 끝납니다**(자동 시험). 두 실패 경로의 시간 차이는 48바이트 AEAD 하나 이내로 맞췄습니다. Argon2나 WebAuthn이 상수 시간이라고 주장하지는 않습니다.
- **변조:** S 포장을 다른 금고·수정 번호·파일에서 옮겨 오기, 전한 키 바꾸기, 짝 기록 옮기기·고치기·더하기·빼기·순서 바꾸기, 승인 키·표시·변경 종류·시각·분실 날짜 바꾸기, 칸·수·flags·정책·제거 기록·`pw_id`·매직 바꾸기, seal block 바꾸기는 모두 커밋 값이나 AEAD, `[0, H)`를 묶은 S 포장, `[0, B)`를 묶은 본문에서 실패합니다. PIN 표시를 낮춰도 칸 flags가 `[0, H)` 안에 있고, PIN 모드 키는 PIN 없는 조회에 다른 출력을 주거나 거부합니다. `GOYOKH01` ↔ `GOYOKS01`, 보안 키 ↔ `GOYOKE03` 바꿔 붙이기도 실패합니다. 다른 PC가 읽을 파일에서 알려진 키의 번호나 날짜를 바꾸면 터치 전에 칸 고정이 거부하거나 G1을 요구합니다.
- **S가 0인 보안 키 파일 없음.** 그런 파일은 비밀번호만의 본문 키를 쓰게 되므로 세 곳에서 막습니다: 봉인과 `Secret::random`이 S ≠ 0을 확인, 열 때 S = 0이면 `인증 실패`, 엄격한 검사·관문 2·서버가 `ks_id = KS_ID_ZERO(금고 ID)`를 거부.
- **키 커밋.** 본문은 `C_body`를 AEAD 전에 상수 시간으로 비교합니다. 짝 기록과 S 포장도 커밋 값 `C`를 가집니다. 금고 AEAD는 0.8처럼 무작위 데이터 키 아래의 Poly1305이고 커밋하지 않습니다.
- **어서션 서명은 검증하지 않습니다.** 공개 키를 저장하지 않고(공개 키 암호 없음) 복호화 자체가 키 응답에 달려 있어, 서명 검증은 보호를 더하지 않습니다. 대신 응답의 hmac-secret 출력이 정확히 32바이트이고 0이 아니며, 허용 목록의 자격 증명이고, UV가 저장한 대로이고, BE·BS가 0이며 연결 방식이 USB/NFC인지(가능한 Windows에서) 확인하고, 아니면 거부합니다. UV와 salt는 고정이고 시험으로 확인합니다.

### 열쇠 파일 동기화의 조건과 관문

열쇠 파일 동기화는 별도 검토의 16가지 조건을 모두 지키는 선택 기능입니다(기본 꺼짐, 금고마다). 요점:
- **매직이 곧 동의.** 올릴 수 있는 것은 `GOYOKS01`뿐이고, 비밀번호만으로 여는 형식은 그 매직을 가질 수 없습니다. 끈 뒤에는 다른 매직(`GOYOKH01`, `GOYOKE03`)을 쓰므로 다시 올라가지 않습니다. `goyo-sync.conf`에는 스위치가 없습니다.
- **PIN 필수, USB/NFC만.** 모든 칸이 PIN 칸(UV + credProtect 3, `bRequireCredProtect`)이어야 켜지고, Windows가 연결 방식을 알려 주지 않으면 켤 수 없습니다. Windows가 이것을 실제로 강제하지 못하면 기능을 제공하지 않습니다(점검표).
- **관문 1(금고 앱):** 이번 세션에서 연 키 응답으로 열었거나 이번 세션이 쓰고 다시 읽어 확인한 `GOYOKS01` 바이트만, PIN 모드·모든 칸 PIN인지 확인한 뒤 별도 포장(`GOYOSKO2`)으로 내보냅니다. 디스크를 다시 읽지 않습니다. **관문 2(도우미)와 관문 3(서버)** 은 문법만 봅니다: 분리된 op와 이름 공간, 정확한 매직, 고정한 금고 ID, 엄격한 검사, 크기 한도, 수정 번호 범위. 금고 PUT은 금고 매직만, 열쇠 PUT은 `GOYOKS01`만 받습니다.
- **서버:** 최신과 바로 앞 열쇠 파일만 두고 예전 것은 내보내지 않습니다. 기록 번호 CAS, 금고마다 커널 잠금 하나(`flock`) 안에서만 열쇠 작업, 끄기는 세대를 끝내는 끊음 기록, 손상된 맨 위 기록은 끊음으로 읽어 내보내는 수정 번호가 줄지 않음, 금고 기준(KEY_BEHIND)은 맨 위 열쇠 파일의 수정 번호·키 ID·상태 태그에 맞는 금고 업로드만 받음. 정직한 서버는 제거 기록과 승인 키도 확인합니다. 금고 기준은 인증되지 않은 금고 머리글을 읽으므로 뒤처진 **정직한** PC의 업로드만 멈춥니다. 머리글을 꾸민 업로드는 막지 못하며, 그런 사본은 받는 PC의 복호화와 검사가 막습니다. 이 모두는 **정직한 서버** 에 대한 것입니다. 해킹된 서버는 올라간 모든 것을 보관한다고 가정합니다.
- **받기는 사람이 있을 때만.** 서버의 열쇠 파일은 사용자가 비밀번호와 터치로 확인하는 순간에만 설치합니다: 로그인 자체(precheck가 읽은 그 바이트만, 잠금 해제가 이 PC의 현재 데이터 키로 이어짐(rule D)을 확인한 뒤 관문을 묻고, 로그인의 터치와 그 로그인의 증명 `UnlockProof`로 재인증해 OTP를 다시 묻지 않음), 로그인이 실패한 뒤 'S-TRY-SERVER-KEY'(받을 파일을 같은 비밀번호·터치로 열고, 그 안의 이 PC 데이터 키로 이어짐과 이 PC 금고 파일이 그 키로 열림을 확인한 뒤에야 관문 답을 판단하고, 받은 파일이 설치되어야만 세션을 돌려줌), 그리고 '받기…'. 관문(G2·G1)은 무엇이 바뀌었는지 보이기 전에 묻습니다. 부트스트랩(TOFU)에서는 로그인이 아무것도 받지 않습니다. 도우미는 열쇠를 묻지 않고, 백그라운드에서 받지 않습니다. 관문을 기다리는 동안 그 PC는 올리지도 합치지도 않습니다. 잠금 해제의 허용 목록에는 이 PC의 열쇠 파일에 있는 키만 넣습니다. 서버 파일에만 있는 키는 Windows 창을 취소한 뒤 사용자가 고른 별도 의식(S-TRY-OTHERKEY)에서만 쓰며, 그 길에서는 이 PC의 열쇠 파일을 시험하지 않았으므로 E5 대신 G1이 막습니다(그 키는 이 PC에 새 키이므로 늘 G1).
- **새 PC와 잃어버린 열쇠 파일:** 모든 처음 받는 열쇠 파일(USB 사본 포함)은 첫 편집 전에 G1이 필요합니다. USB 첫 사본을 권합니다. 서버에서 시작할 때는 goyo-sync의 '이 PC로 가져오기'가 금고 파일을 사용자가 고른 폴더에 새 파일로 두고(이미 있는 파일이나 동기화 폴더 위에는 쓰지 않음), 서버의 열쇠 파일은 그 동기화 폴더의 `incoming.goyokeysync`에만 둡니다. 고요 금고의 '서버에서 가져온 금고' 화면이 그것을 읽기 전용으로 엽니다(그 금고 파일은 읽기 전에 잠급니다). G1(또는 '코드 없이 받기 (이 서버를 믿음)…'의 위험 경고에 예)과 저장 단계 전에는 동기화 폴더 밖에 아무것도 쓰지 않습니다(열쇠 파일, 금고 파일, 열쇠 기록의 `t` 모두). 그 뒤 `tofu_save`가 열쇠 파일을 먼저 쓰고(동기화 폴더 안이나 이미 있는 파일 위에는 쓰지 않음, 끊긴 저장이 같은 바이트로 남긴 파일만 받아들임) 금고 파일을 **제자리에** 다시 씁니다. 이 제자리 쓰기는 가져온 금고에만 있는 예외이고, 다른 모든 '백업 파일로 되살리기'는 여전히 원본과 다른 새 파일에만 씁니다(NOT_DISTINCT). '백업 파일로 되살리기'는 동기화 폴더의 열쇠 보기를 열쇠 파일로 받지 않습니다. 저장 창은 코드가 맞았을 때만 "진짜입니다"라고 하고, 코드 없이 믿은 경우는 확인하지 않았다고 말합니다. 이 PC가 전에 연 금고를 쓸 수 있는 열쇠 파일과 함께 고르면 그 화면으로 가지 않고 평소 로그인으로 엽니다. 이 PC에 금고 파일이 있으면 그것이 기준이라 더 오래된 서버 열쇠 파일은 열지 않고, 이 PC의 열쇠 기록과 맞지 않는(갈라진·예전·관문이 필요한) 파일도 열지 않습니다(설계보다 엄격함: 그런 경우는 이 PC의 열쇠 파일로 연 뒤 받음).
- **같은 상태에서 한 두 제거의 합치기(종류 9):** 서버에 늦게 올린 PC만, 두 파일이 모두 같은 데이터 키에서 한 제거뿐이고(셋 이상의 PC는 이미 이 PC의 이전 상태를 담은 합치기 결과) 관문이 필요 없을 때(R = Δ = T_new = ∅, 정책·칸 변경 없음, `gated + EPOCH_SILENT` 안) 잠금 해제의 터치와 비밀번호로 합칩니다. 로그인은 그 파일이 이 PC의 `pw_id`를 갖고 잠금 해제한 키가 그 파일에서 살아 있을 때만 묻지 않고 합치며, 그 밖에는 [받기]로만(다른 키·다른 비밀번호를 물음) 합칩니다. 그래서 이 PC의 공개 바이트로 만든 위조 제거 파일은 로그인마다 질문을 띄우지 못합니다. 열리지 않은 파일은 아무것도 쓰지 않고 '위조된 연결'로 거부하며, 앱이 실행되는 동안 다시 열어 보지 않습니다. 결과는 새 데이터 키와 새 S로 쓴 합치기이며, 상대 PC에서는 관문 없는 후속 파일입니다.
- **다른 PC가 없어 이 PC 상태로 올리기:** G1이 필요한(코드를 입력해야 하는) 기다리는 변경이나 갈라짐에만, 그리고 그 변경이 이 PC의 키를 빼지 않고(R = ∅) 이 PC가 모르는 키의 제거 기록이 없을 때(T_new = ∅), `gated + EPOCH_SILENT` 안에서만 나옵니다. 그 파일은 열지도 설치하지도 않고, 이 PC의 키 구성과 데이터 키로 그보다 높은 수정 번호에 다시 씁니다(제거 기록은 합집합, 새 S). 그 파일의 키 ID는 인증되지 않았으므로, 서버 금고 사본은 머리글의 키 ID **와** 상태(수정 번호·태그)가 그 파일과 같을 때만 덮어쓰고(`sup`, 잠금 해제마다), 다른 상태의 사본이 동기화를 멈추고 있으면 아무것도 하지 않고 '서버 사본을 이 PC 상태로 덮어쓰기…'를 먼저 하라고 합니다. 열쇠 파일을 PC에만 두던 PC에서는 그 파일이 이 PC 데이터 키로 이어진 `GOYOKS01` 후속일 때만 나오고, 열쇠 파일 동기화 동의와 전송 방식 확인 뒤 이 PC도 열쇠 파일 동기화를 켭니다(그 데이터 키는 이미 그 파일에 들어 있으므로 새로 노출되는 것은 없음).
- **알림과 강제 명령 줄:** 열쇠를 바꾼 PC의 '모든 PC가 받았는지' 알림은 이 PC의 열쇠 기록(`p`)에만 있어 인증되지 않습니다(R8). goyo-sync 설정 창의 '강제 명령 줄…'은 목록의 금고 가운데 열쇠 파일 동기화를 쓰는 금고의 ID로 줄을 보여 줄 뿐 아무것도 저장하거나 서버에 보내지 않습니다. 그 판단에 쓰는 금고 파일 머리와 동기화 폴더의 파일은 인증되지 않으므로, 이 PC의 그 폴더에 쓸 수 있는 사람은 줄에 금고 ID를 하나 더 넣게 할 수 있습니다. 서버 쪽 신호(도우미가 받아 둔 서버 사본의 flags bit1, 서버가 가진 열쇠 파일, `nokeys`)도 판단에 들어가므로, 동기화 SSH 키를 훔친 사람이 `--key-sync` 없는 줄로 flags bit1을 단 사본을 올리면(열쇠 기록이 없는 동안 서버는 받음) 다른 PC의 줄에 그 금고 ID가 들어가게 할 수도 있습니다. 그래서 창은 서버 쪽 신호로만 넣은 금고를 따로 적고 직접 켠 금고인지 확인하라고 합니다. 넣는 ID는 늘 이 PC의 금고 머리나 도우미가 고정한 ID이므로 낯선 금고 ID는 들어가지 않습니다. 어느 경우든 사용자가 그 줄을 서버에 넣을 때만 효과가 있고, 아래 R18의 노출(업로드를 막을 수 있음)이 그 금고로 넓어질 뿐입니다.
- **끄기 순서:** 동의하는 순간부터 열쇠 업로드를 쓰지 않음 → 요청·보기 파일 지움 → '서버에서 지우기' 의도를 열쇠 기록의 `ks = off.<n>`으로 회전의 첫 단계(S0)에 씀 → 데이터 키를 바꿔 올릴 수 없는 매직으로 → 서버 삭제(CUTKEY)는 도우미가 다음에 보냄('대기 중', 응답 뒤 '서버가 삭제했다고 응답함', '완료'라고는 하지 않음) → 다른 PC는 멈추고 USB로 받음. 끄기가 S2 전에 끊기면 끄기 전체가 되돌려집니다. 더 쓰지 않는 키는 그 금고의 등록만 지우고, FIDO 초기화는 다른 곳에 쓰지 않는 키만 권합니다.
- **기록 정리:** 분실 제거 뒤 서버의 변경 전 금고 기록을 지울지 묻습니다(정직한 서버에서만 의미).
- **문서에 적은 약속:** 서버는 비밀번호와 PIN이 걸린 등록 키가 둘 다 없으면 풀 수 없다. 서버나 동기화 SSH 키가 뚫리면 남는 장벽은 그 둘뿐이다.

**검토 조건에서 문구가 다른 곳(목표는 지킴).**
- 조건 2·4는 모든 칸 키를 `HKDF(Argon2id(pw) ‖ hmac 출력, 머리글 해시)`로 하라고 합니다. 한 키 비밀번호 변경·추가·제거(터치하지 않은 키에 전달 열쇠로 포장)를 위해 S 포장 키는 하드웨어 출력만으로 만들고, 대신 금고 ID, 수정 번호, 두 credhash, 머리글 `[0, H)` 전체의 해시를 묶으며, 본문은 `pw_key ‖ S`로 그 앞 모든 바이트를 묶습니다. 비밀번호만으로 확인할 수 있는 값이 없고 모든 변조가 실패하며 두 실패가 같다는 목표는 지킵니다. 대가는 R2(한 번 얻은 키 응답이 오래감)입니다.
- 조건 7의 '같은 수정 번호에 다른 바이트 = 갈라짐'은 상태(수정 번호 + 태그)로 판단합니다. 받은 파일을 다시 봉인하면 같은 상태에 다른 바이트가 정상적으로 생깁니다.
- 조건 9의 'chain MAC'은 받는 PC의 현재 데이터 키 기준이며, 공개 검사와 관문도 통과해야 합니다. '사람이 있을 때'는 로그인이나 '받기…'의 재인증입니다.
- 조건 10의 '모든 PC에서 코드 비교'는 받기 전에 하는 고르기(G2)나 코드 입력(G1)으로 바꿨습니다(눈으로 비교보다 강함). 갈라진 파일의 '다른 PC 쪽 사용'은, 이 PC가 다른 파일에서 **받은** 제거를 G1과 위험 확인 뒤에 되돌릴 수 있습니다. 이 PC에서 사용자가 직접 한 제거는 되돌리지 않습니다.
- 조건 11: 새 PC는 G1(코드 입력), USB 사본도 같음.
- 조건 13: 기록 정리 질문은 열쇠 파일 동기화 금고에서만.
- 조건 15: 서버 삭제 자체는 비동기(도우미)이고 대기 중으로 보입니다.
- 조건 8: 멈춘 서버 사본을 '서버 사본을 이 PC 상태로 덮어쓰기'로 넘을 수 있습니다(비밀번호·터치·위험 질문, 덮인 사본은 서버 기록에 남음).

### 공개되는 메타데이터와 한도

- 금고 파일 머리글(서버도 봄): 키 ID, 수정 번호, 상태 태그, 보안 키·열쇠 파일 동기화 여부, 그러니 열쇠를 바꾼 횟수와 대략의 시각. `GOYOKS01` 파일(서버가 가짐): 칸 수, 자격 증명 ID, 등록 시각, seed, 변경 종류, 승인 키 번호, 터치·일시 정지 표시, 짝 기록 수, 쓴 시각, 보고한 분실 날짜.
- 데이터 키는 64개(최근 63개와 처음 키)까지 담습니다. 62번 넘게 뒤처진 PC는 이어진 파일을 확인하지 못해 관문 뒤 합치기로 받습니다. 제거 기록은 480개까지이고 지우지 않습니다.
- 수정 번호는 2^48−1까지이고 덧셈은 모두 검사합니다(`panic = "abort"`·overflow 검사). 인증 안 된 수정 번호는 2^16(`EPOCH_WINDOW`), 관문 없이 받는 파일은 2^8(`EPOCH_SILENT`)까지만 셉니다. 그래서 조용한 건너뛰기와 심은 파일이 PC를 정직한 서버의 창 밖이나 한도 끝으로 밀 수 없습니다.

### Windows의 WebAuthn

- `webauthn.dll`은 보안 키가 있는 금고에서만 System32에서(`LOAD_LIBRARY_SEARCH_SYSTEM32`) 불러오고, 정적 import는 없습니다(`inspect_pe.py`가 확인). 불러오면 그 DLL이 쓰는 System32 DLL(combase, oleaut32, rpcrt4, windows.storage, advapi32, sechost, msvcrt, ntmarta, cryptngc, winsta, bcryptprimitives, dpapi, bcrypt, crypt32)이 프로세스에 들어옵니다. 금고의 암호화는 이들을 부르지 않습니다.
- 터치·PIN 창은 Windows의 별도 프로세스라 화면 캡처 차단 밖입니다. PIN과 키 응답은 Windows와 RPC 버퍼를 거치며 지울 수 없습니다.
- 한 번의 인증 흐름(재인증)은 그 흐름 동안(최대 30분)만 살고 승인 키의 응답을 메모리에 둡니다. 화면 잠금, 절전, 닫기는 바로 잠그고 지웁니다. 흐름 동안 미사용 잠금은 10분으로 늘어납니다.

### 남은 위험

- **R1 실제 하드웨어는 일부만 확인.** YubiKey 5C NFC, Windows 11 26200, API 9에서 확인한 것: hmac-secret 값이 터치마다, USB와 NFC에서 같음, `pbSecond`, credProtect 3(`bRequireCredProtect`), BE/BS가 늘 0, PIN이 있는 키는 uv=discouraged여도 UV를 함(SECURITY_KEY.md 점검표). 남은 것: 재부팅·PIN 변경·수개월 뒤에도 같은지, PIN 없는 조회가 실제로 막히는지, 다른 펌웨어·다른 제조사의 키, 휴대폰·Windows Hello 거부. 기능은 기본으로 꺼져 있습니다.
- **R2 한 번 얻은 키 응답은 오래갑니다**(seed가 등록 때 고정). 그 키가 빠졌다가 다시 등록되거나 '모든 키 새로 잠그기'를 할 때까지 복제이며 G2를 통과합니다. G1만 막습니다.
- **R4 동결.** 위와 같습니다. 제거 때 비밀번호를 바꿨다면, 열쇠 파일 동기화를 켠 금고에서는 다른 PC를 새 비밀번호로 열 때 서버의 새 열쇠 파일로 열리므로(S-TRY-SERVER-KEY), 동결된 PC에서는 새 비밀번호가 어디서도 먹히지 않아 드러납니다. 비밀번호를 바꾸지 않았다면 신호는, 제거 뒤 다른 PC에 관문 알림('서버에 확인할 열쇠 변경 있음' 등)이나 열쇠 파일이 PC에만 있는 금고의 '다른 PC에서 이 금고의 열쇠를 바꿔 동기화를 멈췄습니다'가 나오지 않는 것입니다. 그러면 그 PC에서 '잃어버린 키 제거'를 합니다(SECURITY_KEY.md '동결의 한계').
- **R5 확인할 다른 PC가 없는 새 PC·재해 복구**는 믿고 받을 수밖에 없습니다.
- **R6 기록.** 제거 전에 저장한 모든 것은 서버 기록과 예전 열쇠 파일로 계속 읽힙니다. 기록 정리, CUTKEY, 금고 기준은 정직한 서버에만 효과가 있습니다.
- **R8 열쇠 기록은 인증되지 않고 PC마다 있습니다.** 지우면 관문이 늘지만(모든 보안 키 금고가 처음 보는 파일), 기다리는 검토는 합치기 기록 때문에 남습니다.
- **R18 훔친 `--key-sync` 동기화 키**는 그 줄의 금고에서 열쇠 파일 동기화를 막을 수 있습니다(멈춤, 위조 아님). 관리자가 `data/<id>/k/`를 지워야 할 수 있습니다.
- **R22 관문과 화면이 옳아야 합니다.** 고르기 전에 변경·크기·코드를 보여 주기, 건너뛰기 단추, 받은 파일에서 가져온 번호·이름, 누적이 아닌 단계별 R, 실패한 고르기 뒤 R 공개, 두 번째 고르기 중 하나라도 있으면 위조 제거의 구멍이 다시 열립니다. 각 항목에 변이 시험이 있습니다.
- **R23 사용자 실수.** 잃어버린 키를 덜 고르면 두 키를 함께 가진 사람의 변경이 통과할 수 있고, 다른 화면의 코드를 입력해도 그렇습니다.
- **R43 열쇠 변경 자동 적용 (이 서버를 믿음).** 켠 PC에서는 R23이 '고르기를 맞힐 수 있는 위조자'에서 '서버에 올릴 수 있고 살아 있는 키 하나와 그 PIN, 비밀번호를 가진 사람'으로 넓어집니다. 그런 사람이 쓴 이어진 후속 파일을 그 PC가 다음 잠금 해제에 묻지 않고 설치해, 그가 아는 데이터 키로 바뀝니다. 키 분실 직후(다른 PC가 제거를 받기 전)가 바로 이 경우이므로, SECURITY_KEY.md는 제거 뒤 켠 PC마다 열쇠 확인 코드를 비교하고 다르거나 갈라지면 그 PC에서도 제거하라고 안내합니다. 설정은 인증되지 않은 열쇠 기록에 있으므로 같은 사용자 권한의 코드가 켤 수 있습니다(R8, 그런 코드는 범위 밖). 기본 꺼짐, PC·금고마다, 위험 질문 뒤에만 켜짐.
- **R24 짝 맺기 방문 전의 예비 키**는 만나지 못한 키를 대신하지 못하고, 그 사이 두 번째 분실에 홀로 남을 수 있습니다. **R25** 한 장소의 키를 모두 잃으면 키가 그곳에 갈 때까지 그 PC는 열 수 없습니다.
- **R26 분실을 알아채기 전** 그 키를 가진 사람(PIN·비밀번호까지)은 정식 사용자입니다. **R29 검토 목록은 도움일 뿐입니다**(이 PC의 합치기만, 인증 안 됨, 한도 초과 시 일부 빠짐을 알림, 읽지 않고 확인할 수 있음).
- **R27 서비스 거부와 알림 피로.** 데이터는 잃지 않습니다(멈춤이지 덮어쓰기가 아님). **R30** 서버는 위조 제거 하나로 그 PC의 G2를 꺼서 G1만 남게 할 수 있습니다.
- **R31** 정식 사용자(또는 동결 중의 뺀 키)가 쓴 이어진 파일은 예전 데이터 키를 덜 담을 수 있습니다(가용성만, 예전 백업은 그때의 열쇠 사본으로).
- **R32** 기다리는 G1 변경 옆에 쓴 분실 제거는 이 PC를 바로 보호하지만, 그 코드를 입력할 수 없으면 서버에 올라가지 못할 수 있습니다.
- **R33 동기화 폴더의 요청 파일은 인증되지 않습니다.** 그 폴더에 쓸 수 있는 사람은 그 PC의 도우미가 CUTKEY나 PRUNE을 보내게 할 수 있습니다(가용성과 서버 기록. 어느 PC도 여는 열쇠 파일은 아님).
- **R34 끄기는 세대 전체를 끝냅니다.** 끄는 PC가 아직 보지 않은 다른 PC의 변경도 서버에서 지워지고, 두 PC는 USB로 한 번씩 주고받습니다.
- **R35·R36 금고 잠금**은 금고마다의 가용성 지점이고(멈춘 보유자가 그 금고의 열쇠 작업과, `k/`가 있으면 PUT을 막음, 20초 뒤 `busy`), 저장소의 `flock`에 기댑니다(Windows의 `msvcrt.locking`은 selftest용).
- **R37** 열쇠 요청이 대기·실패·거부된 동안 새 키 상태의 금고 업로드는 보내졌다가 KEY_BEHIND로 거부됩니다('열쇠 파일 갱신 필요').
- **R38 손상된 맨 위 기록은 끊음으로 읽힙니다**(모든 PC가 '서버에 없음', 다시 올릴 때까지 `GOYOKS01` PC의 금고 채널 멈춤). **R39** 서버를 본 적 없이 한 끄기는 잠금 해제된 세션이 서버를 처음 볼 때까지 삭제를 보내지 않습니다.
- **R40** 관리자의 `rm -r k/`나 백업에서 되살린 서버는 기록 번호를 되돌립니다. 그 금고를 동기화하는 PC가 없을 때만 하라고 안내합니다. **R41** 열쇠 보기 파일의 `gen`과 `floor`는 인증되지 않습니다. **R42** 끊긴 끄기는 되돌려지므로 다시 꺼야 합니다.
- **기본 빌드와 보안 키 파일(R10).** 기본 빌드는 매직만 보고 결정하고, 문법 검사는 문구를 고르는 데만 씁니다. 검사기는 두 빌드에서 같은 코드이고 변이·잘림 시험을 거칩니다.

### 검증한 것과 하지 않은 것

- **자동 시험(가짜 인증기):** 암호 구성의 시험 벡터, 엄격한 검사(뒤집기·잘림·변이), 두 실패의 같음, 모든 열쇠 변경의 충돌 주입(각 쓰기 지점에서 끊음), 관문(정확한 집합, 한 번만, 누적, 다시 시작, '나중에', '받지 않기'), 뺀 키를 가진 사람의 위조 흉내(최신 PC·뒤처진 PC·로그인 때), 서버 채널의 종단 시험(실제 서버 스크립트를 로컬 프로세스로, 적대적 서버 포함), 화면 흐름과 화면 미리보기(두 언어, 두 테마).
- **변이 시험:** `scripts/mutate.py`가 규칙 하나씩을 뺀 사본에서 그 규칙을 지키는 시험이 실패하는지 확인합니다(2~6단계, 279행). 이번 단계에서는 `--check`(모든 행의 코드 조각이 정확히 한 번 있는지)만 다시 실행했습니다.
- **서버 selftest는 Windows에서만 실행했습니다.** Linux 전용 경로(`flock`, `O_NOFOLLOW`, 저장소 잠금 확인 13번 행)는 코드를 읽어 확인했을 뿐 Linux에서 실행하지 않았습니다. 설치할 때 서버에서 selftest를 실행하세요.
- **실제 보안 키로 한 것은 없습니다.** 아래 점검표 전체가 남아 있습니다.
- 이 기능은 외부 모델 검토를 받지 않았습니다. 설계는 여러 차례의 내부 적대 검토(위조, 충돌, 구현 관점)를 거쳤습니다.

### 실제 키 점검표 (결과: 아직 없음)

보안 키를 기본으로 켜거나 열쇠 파일 동기화를 '실험'에서 빼기 전에 실제 키로 통과해야 하는 항목입니다. **하나도 실행하지 않았습니다.** 실패가 하나라도 있으면 기능은 기본으로 꺼진 채 남고, PIN 강제·USB/NFC 전용·키 응답 그대로 받기를 Windows가 지키지 못하면 열쇠 파일 동기화는 제공하지 않습니다. 항목 목록(1-23, 19a, 19b)은 [SECURITY_KEY.md](SECURITY_KEY.md#실제-보안-키-점검표)에 있습니다: hmac-secret 출력의 결정성, 검색 불가 자격 증명, PRF 플래그, API 버전, RP ID, UV 동작, PIN 강제, credProtect, 키별 salt, 두 salt 한 번에, 중복 등록 오류, 오류 코드, 등록 3번 연속, 연결 방식과 BE/BS, Windows 창과 타이머, 스레드·DLL 정리, FIDO 초기화, 자격 증명 자리, 실제 키 4개 제거·새로 잠그기, 여러 터치, credProtect 유지, exFAT 전원 차단, 실제 PC 두 대, 열쇠 파일 동기화 종단, 실제 창의 소요 시간.

## 남은 검증 한계와 의도한 동작

실제 비밀·사용자 클립보드를 사용하는 UI 자동화는 수행하지 않았습니다. 숨겨진 자체 테스트 창과 가짜 값으로 검증했습니다. 사용자 클립보드를 실제로 덮어쓰는 통합 테스트, 모든 캡처 프로그램·IME·셸 확장, FAT/exFAT 전원 차단, 장치별 물리 난수 검증은 수행하지 않았습니다. 실제 한국어 IME를 통한 제목/경로 입력은 수동 확인하지 않았으며, 암호 입력 범위 때문에 한글 입력이 제한될 수 있음을 README에 명시했습니다.

클립보드 점유가 풀리지 않으면 종료가 대기할 수 있습니다. 이는 비밀이 남은 채 자동 종료하지 않기 위한 선택입니다. 기본 설정에서는 다른 앱에 30초 넘게 머무르면 잠그며, 편집 중인 미저장 내용도 이때 지웁니다. 파일창도 미사용 잠금 대상입니다. 자동 잠금을 늘리거나 끄면 자리를 비운 사이의 노출은 사용자가 Windows 화면 잠금으로 막아야 합니다. 운영체제 메모리 사본·관리자/커널 공격·경로 메타데이터·암호화 임시 파일·오래된 백업/열쇠의 효력은 README에 설명한 한계가 유지됩니다.

Windows 설정 검증 근거: [정적 DLL 검색 플래그](https://learn.microsoft.com/en-us/cpp/build/reference/dependentloadflag?view=msvc-170), [파일 선택창 플래그](https://learn.microsoft.com/en-us/windows/win32/api/commdlg/ns-commdlg-openfilenamew), [클립보드 시퀀스](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber), [입력 컨트롤 스타일](https://learn.microsoft.com/en-us/windows/win32/controls/edit-control-styles).

입력기 설정 근거: [SetInputScope](https://learn.microsoft.com/en-us/windows/win32/api/inputscope/nf-inputscope-setinputscope), [ImmAssociateContextEx](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontextex). 암호 입력 범위는 OS 서비스에 대한 힌트이며 완전한 격리 보장이 아닙니다.

## 외부 검토로 전달하는 정보

사용자가 요청한 Opus 5.5 검토에는 소스코드, Cargo 설정, 설계 문서와 가짜 테스트 데이터만 전달합니다. 실제 금고·열쇠·비밀번호·OTP, 환경 변수, 서비스 인증정보는 전달하지 않습니다.
