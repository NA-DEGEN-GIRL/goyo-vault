# Goyo 파일 형식

수치는 별도 표기 없으면 little endian. 사용자 지정 KDF 비용은 받지 않아 악성 헤더의 메모리/CPU 비용 확대를 막습니다. 최대 금고 파일 8 MiB, 항목 1000개, 이름 256바이트, 종류 64바이트, 비밀·메모 각각 UTF-8 8192바이트. NUL 및 불완전 UTF-8은 거부합니다.

## 열쇠 파일: OTP 사용 148바이트, 미사용 128바이트

|위치|길이|내용|
|---|---:|---|
|0|8|`GOYOKE01`(OTP 사용) 또는 `GOYOKE02`(OTP 미사용)|
|8|16|무작위 금고 ID|
|24|32|무작위 Argon2 salt|
|56|24|무작위 XChaCha nonce|
|80|68 또는 48|암호문 + 16바이트 태그|

AAD는 앞의 80바이트 전체(매직 포함). 암호화 키는 Argon2id v0x13(password, salt), m=262144 KiB, t=3, p=1, 출력 32바이트. 평문은 `GOYOKE01`이 데이터 키 32바이트 + TOTP 비밀키 20바이트, `GOYOKE02`가 데이터 키 32바이트입니다. 매직과 파일 길이가 정확히 짝을 이루지 않으면 거부하고, 매직이 AAD에 들어 있어 한 종류를 다른 종류로 바꿔 붙이면 인증에 실패합니다. 0.5.0 이전 버전은 `GOYOKE01`만 읽습니다. 파일명·디스크 경로는 암호화 키에 포함하지 않아 USB 이동과 다른 PC 복원이 가능합니다.

OTP 사용 여부는 금고를 만들 때 정합니다. 화면은 평문 매직으로 OTP 칸을 보일지만 정하고, 실제 OTP 확인 여부는 복호화한 열쇠 파일의 종류로 결정합니다. OTP는 암호화 키에 참여하지 않습니다. OTP 비밀키는 열쇠 파일 안에 있으므로, 두 파일과 비밀번호를 가진 사람은 OTP 없이 복호화할 수 있습니다.

열쇠 파일 형식은 0.8.0에서 바뀌지 않았습니다. 동기화로 올라가지도 않습니다.

## 금고/백업 파일

|위치|길이|내용|
|---|---:|---|
|0|8|`GOYOVA01`(동기화 없음) 또는 `GOYOVA02`(동기화를 켠 금고)|
|8|16|대응 열쇠의 금고 ID|
|24|24|매 저장마다 새 무작위 nonce|
|48|가변|암호문 및 16바이트 태그|

AAD는 앞의 48바이트 전체. 키는 열쇠 파일에서 복호화한 데이터 키입니다. 매직이 AAD에 들어 있어, `GOYOVA02` 파일의 매직을 `GOYOVA01`로 바꾸면 인증에 실패합니다. 가장 작은 파일은 `GOYOVA01` 76바이트, `GOYOVA02` 96바이트이고 가장 큰 파일은 8 MiB입니다. 후행 데이터는 거부합니다.

`GOYOVA` 뒤에 `03` 이상의 두 자리 숫자가 오면 복호화 전에 "더 새로운 버전에서 만든 금고 형식입니다. 고요 금고를 업데이트하세요."로 거부합니다. 매직은 공개 정보라 이 구분으로 새는 것은 없습니다.

### GOYOVA01 평문

마지막 승인 OTP step(u64, OTP 미사용 금고는 0), 항목 수(u32), 각 항목의 이름/종류/비밀/메모 순서이며 각 문자열은 u32 바이트 길이 + UTF-8입니다. OTP를 쓰는 금고는 잠금 해제 시 OTP step을 먼저 저장한 후 항목을 노출합니다. OTP 미사용 금고는 잠금 해제만으로는 금고 파일을 다시 쓰지 않습니다.

### GOYOVA02 평문

사용자가 그 금고의 동기화에 동의한 뒤에만 씁니다. 동기화를 켜지 않은 금고는 0.8.0 이상에서도 계속 `GOYOVA01`로 저장합니다. 동기화 폴더와 연결된 금고는 잠금 해제 때 받아 둔 서버 사본을 OTP 확인 전에 합치고, 그 결과가 달라졌으면 OTP를 통과한 뒤 저장합니다. 그래서 OTP를 쓰지 않는 금고도 이때는 잠금 해제로 금고 파일을 다시 쓸 수 있습니다.

|위치|길이|내용|
|---:|---:|---|
|0|8|`last`: 마지막 승인 OTP step(OTP 미사용 금고는 0)|
|8|8|`generation`: 내용 변경 횟수(모든 PC가 함께 쓰는 Lamport 카운터)|
|16|8|`seen`: 이 PC가 합친, 인증된 서버 사본의 가장 큰 `generation`. 이 PC에만 의미가 있고 다른 PC의 값은 합칠 때 무시합니다.|
|24|4|항목 수 `n` (1000 이하)|
|28|…|`n` × 항목: `id`(16) · `parent`(16, 새 항목은 0) · 이름 · 종류 · 비밀 · 메모. 문자열은 u32 길이 + UTF-8, 제한은 v1과 같습니다.|
|…|4|삭제 기록 수 `m` (65,536 이하)|
|…|16·m|삭제 기록(tombstone) ID, 기록한 순서대로|

다음은 모두 `인증 실패`로 거부합니다: 0인 항목 ID 또는 삭제 기록, 중복 항목 ID, 중복 삭제 기록, 삭제 기록에도 있는 항목 ID, 한도를 넘는 개수, 빈 이름·빈 비밀정보·NUL·길이 초과 문자열, 후행 데이터. 저장할 때도 같은 규칙을 먼저 검사해, 다시 읽을 수 없는 파일은 쓰지 않습니다. 저장 크기는 `28 + Σ(48 + 문자열 길이 합) + 4 + 16·m + 64`이며 8 MiB를 넘으면 "금고 용량 제한(8 MiB)을 초과했습니다."로 거부합니다.

### 항목 ID

- **새 항목:** 하드웨어 난수 16바이트. 0이거나 이미 있는 ID·삭제 기록이면 다시 뽑습니다.
- **수정:** 새 무작위 ID를 받고 `parent`는 이전 ID가 됩니다. 이전 ID는 삭제 기록에 들어갑니다. 내용이 같으면 아무것도 바뀌지 않습니다.
- **삭제:** ID를 삭제 기록에 넣습니다.
- 추가·수정·삭제마다 `generation`이 1 오릅니다. OTP step(`last`)만 바뀌는 잠금 해제와 비밀번호 변경은 `generation`을 바꾸지 않습니다.
- 삭제 기록은 지우지 않습니다. 하나라도 잊으면 다른 PC의 오래된 사본이 그 항목을 되살리기 때문입니다. 65,536개가 차면 "삭제·수정 기록이 한도(65,536개)에 도달했습니다."로 수정·삭제를 거부합니다. `GOYOVA01` 금고는 삭제 기록을 메모리에만 두고 저장하지 않습니다.

**v1 항목의 ID.** `GOYOVA01`에는 ID가 없으므로 읽을 때마다, 그리고 동기화를 켤 때 같은 방법으로 계산합니다.

```
k  = 같은 파일에서 앞에 나온 항목 중 네 문자열이 모두 같은 항목의 수
id = HMAC-SHA256(데이터 키,
                 "goyo v1 entry\0" || 금고 ID(16) || k:u32 ||
                 len(이름):u32 || 이름 || len(종류):u32 || 종류 ||
                 len(비밀):u32 || 비밀 || len(메모):u32 || 메모)[0..16]
id가 16바이트 모두 0이면 id[0] = 1
parent = 0
```

데이터 키로 계산하므로 ID로 내용을 짐작할 수 없습니다. 같은 v1 금고의 사본을 두 PC에서 따로 동기화 형식으로 바꿔도 ID가 같아, 합칠 때 중복이 생기지 않습니다. 동기화를 켜면 `generation = 1`, `seen = 0`, 삭제 기록은 비운 상태로 시작합니다.

**같은 ID, 다른 내용.** 정상 클라이언트는 만들지 않지만(오류가 있는 클라이언트나 데이터 키를 가진 사람만 가능), 생기면 모든 PC가 같은 결과를 내도록 정합니다. 네 문자열(이름, 종류, 비밀, 메모 순서)을 바이트 순으로 비교해 작은 쪽이 ID를 갖습니다. 다른 쪽은

```
id2 = HMAC-SHA256(데이터 키, "goyo dup\0" || id(16) || 옮기는 쪽의 네 문자열을 위와 같은 len:u32 || bytes 형식으로)[0..16]
id2가 모두 0이면 id2[0] = 1
```

로 옮기고 `parent`는 떠난 ID(여기서는 `id`)로 둡니다. `id2`에서도 같은 규칙을 따릅니다. `id2`가 삭제 기록에 있으면 그 글은 남지 않고, 비어 있으면 그 자리에 들어가고, 같은 글이 있으면 그 하나로 남고, 다른 글이 있으면 다시 작은 쪽이 남고 다른 쪽이 `id2`에서 같은 식으로 만든 다음 ID로 옮깁니다. 그래서 각 글은 자기 사슬(`id` → `id2` → …)에서 더 작은 글이 차지하지 않은 첫 ID에 놓이고, 도착 순서와 관계없이 모든 PC가 같은 결과를 냅니다. 한 번의 합치기에서 이렇게 옮기는 횟수가 4,000번(항목 한도의 4배)을 넘으면 한도 초과로 보고 아무것도 바꾸지 않습니다.

이 PC의 글이 다른 ID로 옮겨 남으면 충돌(두 버전을 모두 남김)로, 어디에도 남지 않으면 삭제로 알립니다. 합치기 전 사본을 만들지 정할 때는 더 넓게 셉니다. 이 PC의 항목 가운데 결과에서 같은 ID에 같은 글로 남지 않은 것은 모두(지워짐, 다른 PC에서 고침, 다른 글에 밀려남. 다른 ID로 옮겨 남은 것도) 사라진 항목입니다(아래 `pre-merge-*` 파일).

### 합치기

동기화된 서버 사본은 금고 앱이 인증(AEAD)한 뒤에만 합칩니다.

```
삭제 기록 T = 이 PC의 기록(순서 유지) + 서버 사본에만 있는 기록(순서 유지)
항목       = (이 PC의 항목 ∪ 서버 사본의 항목) 중 ID가 T에 없는 것.
             이 PC의 순서를 지키고, 서버 사본에만 있던 항목을 뒤에 붙임
last       = max(이 PC의 last, min(서버의 last, 현재 step + 1))
올릴 필요   = 결과의 항목 ID 집합 또는 삭제 기록 집합이 서버 사본과 다름 (last는 보지 않음),
             또는 결과가 서버 사본의 어떤 ID에 다른 글을 가짐
generation = max(양쪽), 올릴 필요가 있으면 + 1
seen       = max(이 PC의 seen, 서버 사본의 generation)
되돌림 경고 = 서버 사본의 generation < 이 PC의 seen
```

합치기는 삭제 기록을 새로 만들지 않습니다. 그래서 오래되거나 되돌린 서버 사본은 변경을 늦출 수는 있어도 이 PC의 항목을 지우거나 되돌릴 수 없습니다. 결과가 1000개, 8 MiB, 삭제 기록 65,536개를 넘으면 아무것도 바꾸지 않습니다. 같은 부모(삭제된 ID)를 가진 살아 있는 항목이 둘 이상이면 두 PC에서 함께 고친 것으로, 그중 하나가 방금 도착했을 때 한 번 알립니다. 알림은 항목 이름 없이 개수만 보입니다.

### 확인 코드

```
HMAC-SHA256(데이터 키,
            "goyo sync check\0" ||
            살아 있는 항목마다, ID 오름차순으로: id(16) || SHA-256(네 문자열을 len:u32 || bytes 형식으로) ||
            0xFF × 16 ||
            삭제 기록 ID들(오름차순))의 앞 8바이트
```

`XXXX-XXXX-XXXX-XXXX`(대문자 16진수)로 표시합니다. 항목의 글까지 들어가므로 두 PC의 코드가 같으면 같은 내용입니다. 항목 순서, OTP step(동기화하지 않음), `generation`·`seen`은 넣지 않습니다. 데이터 키로 계산하므로 코드로 내용을 알 수 없고, 64비트라 다른 내용을 같은 코드로 맞추려면 데이터 키를 가진 사람도 약 2^64번 계산해야 합니다.

### 호환성

**동기화를 켠 금고와 그 백업은 0.8.0 이상에서만 열립니다.**

|읽는 버전|`GOYOVA01`|`GOYOVA02`|
|---|---|---|
|0.7.x 이하|읽음|`인증 실패`로 거부(이전 버전은 바꿀 수 없음)|
|0.8.0 이상|읽음. 동기화를 켜지 않은 금고는 계속 `GOYOVA01`로 저장|읽음. 한 번 `GOYOVA02`가 된 금고는 계속 `GOYOVA02`로 저장|

백업과 복원은 형식, ID, 삭제 기록, `generation`, `seen`을 그대로 유지합니다. `GOYOVA02`를 `GOYOVA01`로 되돌리는 기능은 없습니다.

## 동기화 폴더 `<금고 파일 이름>.sync\`

예: `vault.goyo.sync\`. 도우미(`goyo-sync.exe`)만 이 폴더를 만들고, 금고 앱은 이 폴더가 링크·정션이 아닌 실제 폴더(재분석 지점 속성 없음)이고 열쇠 파일이 그 안에 없을 때만 씁니다. 모든 파일은 쓰는 쪽이 하나뿐이고, 빈 `helper.lock`을 빼면 같은 폴더의 임시 파일을 기록·동기화한 뒤 `MoveFileExW`로 이름을 바꿔 넣습니다. 제자리에 덮어쓰지 않습니다.

|파일|쓰는 쪽|형식|최대|
|---|---|---|---|
|`outgoing.goyosync`|금고 앱 (올라간 것이 확인되면 앱이 지움)|`GOYOSOU1`(8) · `base` u64 · `GOYOVA02` 파일|16 B + 8 MiB|
|`incoming.goyosync`|도우미|`GOYOSIN1`(8) · `version` u64(1 이상) · 서버가 보낸 `GOYOVA02` 파일 그대로|16 B + 8 MiB|
|`status`|도우미 (금고 앱은 표시에만 씀)|ASCII, 아래|512 B|
|`helper.state`|도우미|ASCII, 아래|4 KiB|
|`helper.lock`|도우미|빈 파일. 한 번의 동기화 동안 바이트 범위 잠금. 링크가 아닌 단일 링크 일반 파일이어야 함|–|
|`pre-merge-<유닉스 시각 10자리>.goyo`|금고 앱|합치기로 많이 사라지기 전 상태의 `GOYOVA02` 파일. 한 세션 안의 손실을 더해, 마지막 사본 뒤로 5개 이상 또는 2개 이상이면서 그 합치기 전 항목 수의 20% 이상이면 그 손실들 가운데 첫 번째 전 상태를 씀. 최근 3개는 항상, 그 밖에는 30일이 안 된 것만, 모두 합쳐 최근 20개까지|8 MiB|
|`<이름>.<pid>-<나노초>-<번호>.goyotmp`|`<이름>`을 쓰는 쪽|임시 파일(숫자는 16진수). 합치기 전 사본은 `<이름>.<32자리 16진수>.goyotmp`. 각자 자기 파일 이름으로 시작하는 것만 지움|–|

`base`는 이 상태를 만들 때 합친 서버 버전입니다(아직 없으면 0). 도우미는 이 값을 그대로 compare-and-swap의 기대 버전으로 씁니다. 금고 앱은 항상 금고 파일을 먼저 저장한 뒤 `outgoing`을 씁니다. `outgoing`이 이미 같은 `base`에서 만든 같은 상태(항목·ID·글·삭제 기록. OTP 기록과 카운터는 보지 않음)를 담고 있으면 다시 쓰지 않으므로, 업로드를 받지 않는 서버에도 잠금 해제가 새 업로드를 만들지 않습니다.

`status` (각 줄 LF로 끝남, 순서 고정, 모르는 값은 '알 수 없음'):

```
goyo-sync-status 1
heartbeat=<유닉스 초. 최소 60초마다 다시 씀>
contact=<마지막으로 유효한 서버 응답을 받은 유닉스 초, 없으면 0>
state=ok|idle|offline|auth|hostkey|nossh|server|refused|config|update
```

금고 앱은 숫자와 정해진 단어만 읽고, 도우미가 쓴 글을 화면에 보이지 않습니다. heartbeat가 180초보다 오래되었거나 파일이 없으면 '도우미 꺼짐'입니다.

`helper.state` (정확히 이 형식이 아니면 버리고 `incoming`과 `outgoing`에서 다시 계산):

```
goyo-sync-state 1
id=<32자리 16진수>|-        고정한 금고 ID
server=<u64>                incoming에 든 서버 버전(0 = 없음)
head=<64자리 16진수>|-      그 사본의 SHA-256
done=<64자리 16진수>|-      마지막으로 처리한 outgoing 파일 전체의 SHA-256
rejected=<64자리 16진수>|-  마지막으로 거부된 outgoing 파일의 SHA-256
```

**변경 감지.** 두 프로그램 모두 `outgoing`·`incoming`의 변경을 디렉터리 목록(파일 길이, 만든 시각, 고친 시각)만으로 알아채고, 바뀌었을 때만 엽니다. 열린 핸들이 하나라도 있으면 `MoveFileExW` 교체가 실패하기 때문입니다. 교체하면 새 파일이 되어 만든 시각이 바뀝니다. 512바이트 이하인 `status`만은 금고 앱이 10초마다 잠깐 읽고, 그때 도우미의 교체가 실패하면 도우미가 다시 씁니다. 도우미는 `vault.goyo`와 열쇠 파일을 열지 않고, 금고가 있는 폴더의 목록만 읽습니다.

**올리기 전 검사(도우미).** `outgoing.goyosync`를 링크를 따라가지 않고 열어, 재분석 지점·하드 링크 2개 이상·크기 범위 밖·`GOYOSOU1`이 아님·안쪽이 `GOYOVA02`가 아님·고정한 금고 ID가 아님 중 하나라도 해당하면 ssh를 실행하지 않습니다.

## 서버 통신 (goyo-sync.exe ⇄ goyo-sync-server.py)

ssh 호출 한 번에 요청 하나입니다. 도우미는 `System32\OpenSSH\ssh.exe ... -- <host> <python> -I <remote> serve`를 실행하고, 모든 가변 데이터는 표준 입력의 프레임으로만 보냅니다. 요청 프레임 뒤에 입력을 닫고(EOF), 서버는 응답 프레임 하나를 쓰고 끝냅니다.

**요청** (`<8sB16sQI32s`, 69바이트) 뒤에 `blob_len`바이트, 그리고 EOF:

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOSRQ1`|
|8|1|op: 1 HELLO, 2 GET, 3 PUT, 4 LIST, 5 FETCH|
|9|16|금고 ID. HELLO·LIST는 0, 나머지는 0이 아니어야 함|
|25|8|HELLO: 프로토콜 1 · GET: 가진 버전(`have`) · PUT: 기대 버전(`expected`) · LIST: 0 · FETCH: 버전 N(0 = 최신)|
|33|4|`blob_len`: HELLO 512, PUT 8 MiB 이하, 나머지 0|
|37|32|HELLO·PUT: blob의 SHA-256 · GET: 가진 사본의 SHA-256(없으면 0) · LIST·FETCH: 0|

**응답** (`<8sBQI32s`, 53바이트) 뒤에 `blob_len`바이트, 그리고 EOF:

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOSRS1`|
|8|1|상태: 0 OK, 1 NOT_MODIFIED, 2 CONFLICT, 3 EMPTY, 4 NOT_FOUND, 10 BAD_REQUEST, 11 BAD_BLOB, 12 TOO_LARGE, 13 LIMIT, 20 SERVER_ERROR|
|9|8|버전(아래)|
|17|4|`blob_len`|
|21|32|blob이 있으면 그 SHA-256, 없으면 0(클라이언트는 빈 데이터의 SHA-256도 받음)|

|op|허용하는 응답|
|---|---|
|HELLO|OK(1, 요청의 512바이트 00..FF ×2를 그대로). 왕복에서 한 바이트라도 바뀌면 오류|
|GET|OK(최신 버전, 금고 파일) · NOT_MODIFIED(`have`, 최신이 `have`이고 SHA도 같을 때만) · EMPTY(0)|
|PUT|OK(`expected + 1`) · CONFLICT(최신 버전, 최신 금고 파일) · EMPTY(0, 서버에 사본이 없고 `expected`가 0이 아닐 때) · BAD_BLOB · TOO_LARGE · LIMIT(금고 64개, 버전 번호 끝, 저장 뒤 디스크 여유 256 MiB 미만)|
|LIST|OK(줄 수, ASCII `<금고 ID 32자리 소문자 16진수> <최신 버전> <크기> <유닉스 초>\n` 줄들, 64 KiB 이하). 버전이 없는 금고는 `<ID> 0 0 0`|
|FETCH|OK(실제 버전 번호, 금고 파일) · NOT_FOUND|
|모든 op|BAD_REQUEST, SERVER_ERROR (blob 없음)|

오류 상태의 버전은 0이고 blob이 없습니다. 클라이언트는 응답 앞의 64 KiB까지를 로그인 셸 출력으로 보고 건너뛰며(로그에 기록), 그 밖에는 `blob_len`이 남은 바이트 수와 정확히 같고, SHA-256이 맞고, blob이 허용된 곳에만 있고, 금고 파일이면 `GOYOVA02`·같은 금고 ID·96바이트~8 MiB여야 받습니다. `GOYOVA03` 이상이면 `state=update`, 나머지는 프로토콜 오류(`state=server`)로 처리하고 `incoming`을 건드리지 않습니다. 업로드와 다른 금고 파일을 담은 PUT의 CONFLICT도, 버전이 요청의 `expected`와 같거나 이미 받은 사본을 다른 번호(1 제외)로 보낸 것이면 정직한 서버가 보내지 않는 응답이라 `state=server`로 처리합니다. 이때는 `incoming`을 다시 쓰지 않고 그 업로드를 끝난 것으로 보지 않으며, 기다림이 끝날 때 가장 새 `outgoing`만 다시 보냅니다.

**서버의 PUT.** 96바이트 미만, SHA 불일치, `GOYOVA02`가 아님, 헤더의 금고 ID가 요청과 다름이면 BAD_BLOB이고 아무것도 쓰지 않습니다. 8 MiB를 넘는 `blob_len`은 읽지 않고 TOO_LARGE로 답합니다. 통과하면 저장한 뒤에도 서버 디스크에 256 MiB 이상 남는지 확인하고(남지 않으면 LIMIT이고 아무것도 쓰지 않습니다. `os.statvfs`가 있는 시스템), 임시 파일을 쓰고 fsync한 뒤 `os.link`로 다음 버전 이름에 연결합니다. 같은 이름이 이미 있으면 링크가 실패하므로, 같은 `expected`로 동시에 올린 두 요청 중 정확히 하나만 성공하고 다른 쪽은 CONFLICT를 받습니다. HEAD 파일은 없고 버전 연결에는 잠금을 쓰지 않습니다. 새 금고 폴더를 만들 때만 저장소 폴더에 `flock`을 걸고 그 안에서 금고 수를 다시 세므로, 동시에 처음 올려도 64개를 넘지 않습니다(POSIX). 디렉터리 fsync가 끝난 뒤에만 OK를 보냅니다.

**서버 저장 구조** (`<스크립트 폴더>/data`, umask 077):

```
data/<금고 ID 32자리 소문자 16진수>/v/000000000001.goyo …   바꾸지 않는 버전 파일, 최신 = 가장 큰 번호
data/<금고 ID 32자리 소문자 16진수>/tmp-<pid>-<ns>-<번호>    진행 중인 PUT
data/slot-0 … data/slot-7                                   동시 접속 자리 잠금 파일(빈 파일, POSIX. 첫 접속 때 data 폴더와 함께 생김)
```

폴더 이름은 요청의 ID 16바이트에서 만들며 클라이언트가 보낸 글자를 경로에 쓰지 않습니다. 최근 200개 버전만 남기고, 금고는 64개까지입니다. PUT이 성공할 때마다 모든 금고 폴더에서 한 시간 넘은 임시 파일을 지웁니다. 한 저장소에서 동시에 처리하는 접속은 8개까지이고(`flock`, POSIX), 그 이상은 요청을 읽지 않고 바로 SERVER_ERROR로 답합니다(stderr `busy`). 시간 제한(SIGALRM이 있는 시스템): 요청 헤더 69바이트(PUT이 아니면 요청 전체)는 30초 안에 와야 하고, PUT은 헤더 뒤 600초 안에 금고 파일과 EOF가 와야 합니다. 요청을 다 읽은 뒤의 디스크 작업에는 제한을 걸지 않아, 신호로 끊겨 임시 파일이 남는 일이 없습니다. 응답을 보낼 때는 60초이고, blob이 든 응답(금고 파일, 목록, HELLO의 512바이트)은 600초입니다. 저장소 폴더가 링크면 거부합니다.

파일 매직·ID·salt·nonce·암호문 길이는 공개 정보입니다. 파일 길이와 파일 존재 여부를 숨기지 않습니다. 모든 문자열과 OTP 비밀키, 데이터 키는 디스크에서 암호화됩니다. 동기화 서버는 금고 ID, 파일 크기, 내용이 바뀐 시각, 버전 수, 접속한 IP, 그리고 도우미가 `interval`마다 접속하므로 각 PC가 켜져 있는 시간을 압니다.

OTP는 RFC 6238 HMAC-SHA1, 6자리, 30초, 현재 step ±1 범위이며 저장된 마지막 step보다 커야 합니다. SHA-1은 Google Authenticator 상호운용을 위한 HMAC 용도로만 사용합니다. 인증 태그·암호화에는 SHA-1을 사용하지 않습니다.
