# Goyo 파일 형식

수치는 별도 표기 없으면 little endian. 사용자 지정 KDF 비용은 받지 않아 악성 헤더의 메모리/CPU 비용 확대를 막습니다. 최대 금고 파일 8 MiB, 항목 1000개, 이름 256바이트, 종류 64바이트, 비밀·메모 각각 UTF-8 8192바이트. NUL 및 불완전 UTF-8은 거부합니다.

## 열쇠 파일: OTP 사용 148바이트, 미사용 128바이트

|위치|길이|내용|
|---|---:|---|
|0|8|`GOYOKE01`(OTP 사용) 또는 `GOYOKE02`(OTP 미사용)|
|8|16|무작위 금고 ID|
|24|32|무작위 Argon2 salt|
|56|24|무작위 XChaCha nonce|
|80|68 또는 48|암호문 + 16바이트 태그|

AAD는 앞의 80바이트 전체(매직 포함). 암호화 키는 Argon2id v0x13(password, salt), m=262144 KiB, t=3, p=1, 출력 32바이트. 평문은 `GOYOKE01`이 데이터 키 32바이트 + TOTP 비밀키 20바이트, `GOYOKE02`가 데이터 키 32바이트입니다. 매직과 파일 길이가 정확히 짝을 이루지 않으면 거부하고, 매직이 AAD에 들어 있어 한 종류를 다른 종류로 바꿔 붙이면 인증에 실패합니다. 0.5.0 이전 버전은 `GOYOKE01`만 읽습니다. 파일명·디스크 경로는 암호화 키에 포함하지 않아 USB 이동과 다른 PC 복원이 가능합니다.

OTP 사용 여부는 금고를 만들 때 정합니다. 화면은 평문 매직으로 OTP 칸을 보일지만 정하고, 실제 OTP 확인 여부는 복호화한 열쇠 파일의 종류로 결정합니다. OTP는 암호화 키에 참여하지 않습니다. OTP 비밀키는 열쇠 파일 안에 있으므로, 두 파일과 비밀번호를 가진 사람은 OTP 없이 복호화할 수 있습니다.

이 두 형식은 0.8.0과 바이트까지 같습니다. 보안 키 없이 만든 새 금고와 0.9.0에서 열쇠(데이터 키)를 바꾼 적 없는 금고는 계속 이 형식이라 0.8에서도 열립니다. 열쇠 파일은 어떤 형식이든 동기화로 올라가지 않습니다.

## 열쇠 파일 매직 (0.9.0)

열쇠 파일은 32,768바이트까지만 읽고, 길이나 내용을 보기 전에 첫 8바이트로 먼저 나눕니다.

|매직|형식|이 빌드(보안 키 기능이 없는 기본 빌드, 릴리스 ZIP)|
|---|---|---|
|`GOYOKE01` / `GOYOKE02`|0.8 형식(위). 데이터 키 하나, 정확히 148/128바이트|읽고 씀(새 금고). 처음 열쇠를 바꾸면(비밀번호 변경, 새 열쇠 파일 받기) `GOYOKE03`이 됨|
|`GOYOKE03`|KF2, 비밀번호만(아래)|읽고 씀. 비밀번호 변경과 '새 열쇠 파일 받기'가 쓰는 형식|
|`GOYOKH` 또는 `GOYOKS` 뒤에 아무 두 바이트(`GOYOKH01` 보안 키, `GOYOKS01` 보안 키와 열쇠 파일 동기화)|KF2, 보안 키. 보안 키 빌드 전용(실험, [SECURITY_KEY.md](SECURITY_KEY.md))|매직만 보고 거부: "이 열쇠 파일은 보안 키(YubiKey 등)가 있어야 열립니다…". 길이·문법 검사, 키 유도, 실패 횟수, 다시 시도 대기 없이 결정하고 '비밀번호가 틀렸다'고 하지 않습니다. 형식 검사를 통과하는 `GOYOKH01`/`GOYOKS01`이 아니면(잘린 사본, 32 KiB보다 큰 파일, `GOYOKH02` 같은 더 새로운 번호) "파일이 손상되었거나 더 새로운 버전에서 만든 파일일 수도 있습니다."를 덧붙입니다. 손상 여부를 판단할 수 없으므로 임시 파일(`.goyotmp`)로 바꿔 넣지 않습니다.|
|그 밖의 `GOYOK` + 대문자 한 글자 + 두 자리 숫자 중, 그 글자에서 이 빌드가 아는 번호보다 큰 것(`GOYOKE04`, `GOYOKX01` 등)|더 새로운 버전의 형식|"더 새로운 버전에서 만든 열쇠 파일입니다. 고요 금고를 업데이트하세요." 손상된 파일이 아니므로 임시 파일로 바꿔 넣지 않습니다.|
|그 밖의 모든 것(`GOYOKE00` 포함)|–|`인증 실패`|

보안 키 빌드(`--features security-key`, 실험)는 `GOYOKH01`/`GOYOKS01`을 읽고 쓰며, 그 밖의 `GOYOKH`·`GOYOKS` 번호는 위 '더 새로운 버전의 형식'으로 다룹니다(아래 [보안 키 열쇠 파일](#보안-키-열쇠-파일-goyokh01goyoks01)).

## 열쇠 파일 `GOYOKE03` (KF2, 비밀번호만)

KF2는 `GOYOKE03`, `GOYOKH01`, `GOYOKS01`이 함께 쓰는 형식이고 검사기도 하나입니다. 아래는 보안 키가 없는 `GOYOKE03`의 모양입니다(보안 키 칸 `n = 0`, 짝 기록 `p = 0`, S 포장 없음). 보안 키 파일의 칸은 아래 [보안 키 열쇠 파일](#보안-키-열쇠-파일-goyokh01goyoks01)에 있습니다.

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOKE03`|
|8|16|금고 ID|
|24|8|`epoch`: 열쇠 변경 번호, 1 ~ 2^48−1|
|32|1|flags: bit0 = 본문에 TOTP 비밀키가 있음(OTP 금고). 다른 비트는 0|
|33|1|`k`: 데이터 키 수, 1 ~ 64|
|34|1|`n`: 보안 키 칸 수, `GOYOKE03`은 0|
|35|1|`next`: 다음 보안 키 번호, 1 이상(보안 키를 껐다 켜도 번호를 다시 쓰지 않음)|
|36|2|`r`: 제거 기록(tombstone) 수, u16, 0 ~ 480|
|38|1|변경 종류: 2 비밀번호 변경(0.8 열쇠 파일의 변환 포함), 9 두 열쇠 파일 합치기, 10 보안 키 끄기. 기본 빌드는 2와 9를 씁니다(모든 종류는 아래 '보안 키 열쇠 파일')|
|39|1|승인한 키의 칸 번호, `GOYOKE03`은 `0xFF`|
|40|2|이번에 터치한 키·일시 정지한 키 표시, `GOYOKE03`은 0, 0|
|42|1|`p`: 짝 기록 수, `GOYOKE03`은 0|
|43|5|예약, 0|
|48|16|`ks_id`, `GOYOKE03`은 0|
|64|16|`pw_id`: 비밀번호를 바꿀 때마다 새로 뽑는 무작위 값, 0이 아님|
|80|8|`written`: 쓴 시각(유닉스 초, 표시용)|
|88|8|`loss`: 분실 날짜(표시용, 보안 키 기능이 씀)|
|96|16·k|키 ID: [0] = 현재 데이터 키 … [k−1] = ID 키(처음 데이터 키)|
|…|24·r|제거 기록: credhash(16) ‖ `removed` u64(비트 0-47 = 제거한 epoch, 1 ~ `epoch`. 비트 48-63 = 분실 표시)|
|W|88|seal block: `resume`(32) ‖ Argon2id salt(32) ‖ 본문 nonce(24)|
|B = W + 88|32|`C_body`(본문 키 확인값)|
|B + 32|32k + 20·otp + 16|본문 암호문 + 태그: 데이터 키 k개(키 ID 순서) ‖ [TOTP 비밀키 20바이트]|
|E|32·k|각 데이터 키의 chain 값, 키 ID 순서|

`W = 96 + 16k + 24r`. 크기는 `k = 1`에 OTP가 없으면 312바이트, 있으면 332바이트, 0.8 금고의 첫 비밀번호 변경 뒤(`k = 2`, OTP 없음) 392바이트입니다. 데이터 키는 최근 63개와 처음 키(ID 키)까지 64개를 담습니다. ID 키는 버리지 않고, `GOYOVA01`/`GOYOVA02` 파일과 v1 항목 ID, 확인 코드가 이 키를 씁니다.

```
pw_key     = Argon2id v0x13(password, salt), m=262144 KiB, t=3, p=1 (0.8과 같음)
prk        = HKDF-SHA256-Extract(salt = "goyo-vault/v2/body", pw_key ‖ 0(32))
K_body     = HKDF-Expand(prk, "key\0"    ‖ SHA-256(file[0..B)), 32)
C_body     = HKDF-Expand(prk, "commit\0" ‖ SHA-256(file[0..B)), 32)
본문       = XChaCha20-Poly1305(K_body, 본문 nonce, AAD = file[0..B+32))
키 ID      = HKDF-Expand(HKDF-Extract("goyo-vault/v2/key-id", 데이터 키), 금고 ID, 16)
chain_i    = HMAC-SHA256(HKDF-Expand(HKDF-Extract("goyo-vault/v2/chain", 데이터 키 i), 금고 ID, 32),
                         "goyo-vault/v2/chain-msg\0" ‖ SHA-256(file[0..E)))
상태 태그  = SHA-256("goyo-vault/v2/state\0" ‖ SHA-256(file[0..W)))의 앞 16바이트
```

비밀번호가 틀리면 `C_body`가 맞지 않아 본문을 풀어 보지도 않고 `인증 실패`가 됩니다. 연 뒤에는 본문 길이, 각 키 ID가 본문의 데이터 키와 맞는지, 모든 chain 값을 확인하므로 파일의 모든 바이트가 검사됩니다. `resume`은 이 열쇠 변경이 다음에 바꿀 금고 파일의 SHA-256이고(없으면 0), salt·nonce와 함께 사본마다 다를 수 있습니다. 그 앞의 `[0, W)`는 같은 상태의 모든 사본에서 같으므로, 상태 태그와 `epoch`가 같으면 같은 열쇠 상태입니다. 0.8 열쇠 파일은 `epoch` 0과 그 파일에서 정해지는 태그를 씁니다.

**엄격한 검사.** 숫자 범위(`epoch`, `k`, `r`, `next`), 예약 바이트 0, 모르는 flags 비트 0, `pw_id` ≠ 0, 위의 `GOYOKE03` 고정값과 변경 종류, 서로 다른 키 ID, (제거한 epoch, credhash) 순으로 엄격히 오름차순이고 credhash가 겹치지 않는 제거 기록, 그리고 길이가 정확히 위 공식과 같을 것(뒤에 붙은 데이터 없음). 하나라도 어기면 비밀번호를 보기 전에 `인증 실패`입니다.

### 상태 태그와 열쇠 확인 코드

열쇠 파일의 상태는 (`epoch`, 상태 태그)입니다. 같은 상태의 사본은 `[0, W)`가 같으므로 어느 PC에서나 같은 상태가 됩니다. '열쇠 관리'의 **열쇠 확인 코드**는 그 상태를 현재 데이터 키로 묶은 값입니다.

```
prk  = HKDF-SHA256-Extract(salt = "goyo-vault/v2/key-code", 현재 데이터 키)
key  = HKDF-Expand(prk, 금고 ID, 32)
코드 = HMAC-SHA256(key, "goyo key state\0" ‖ epoch:u64 ‖ 상태 태그(16))의 앞 8바이트
표시 = E{epoch} · XXXX-XXXX-XXXX-XXXX (대문자 16진수)
```

현재 데이터 키를 가진 쪽만 계산할 수 있고, 코드로 키를 알아낼 수는 없습니다. 0.8 열쇠 파일에는 코드가 없습니다.

### 열쇠 변경 (0.9.0, 비밀번호 변경)

- **새 데이터 키:** 하드웨어 난수 32바이트. 키 목록은 `[새 키] ‖ 지금까지의 키`이고, 64개를 넘으면 ID 키(마지막)를 뺀 가장 오래된 키부터 버립니다. `pw_id`는 새로 뽑고, `epoch`는 열린 열쇠 파일과 금고 파일이 증명하는 가장 큰 수정 번호 + 1입니다(2^48−1 초과면 거부). 0.8 열쇠 파일의 첫 변경은 그 데이터 키를 ID 키로 두는 `k = 2`의 `GOYOKE03`을 씁니다.
- **쓰기 전 검증(R2, R3):** 새 열쇠 파일을 다른 프로그램처럼 다시 파싱해 쓴 쪽의 키로 열고(같은 머리글 값, 키 ID, 본문, 마지막이 ID 키), 금고 파일도 새 키로 만든 뒤 다시 풀어 같은 내용인지 봅니다. 하나라도 다르면 아무것도 쓰지 않습니다.
- **쓰는 순서:** S0 이 PC의 열쇠 기록에 보류 줄(아래 `goyo-vault.keys`). S1 금고 파일을 지금 키로 다시 저장(V_probe. 새 열쇠 파일의 `resume`이 이 파일의 SHA-256). S2 새 열쇠 파일, 다시 읽어 확인. S3 새 키의 금고 파일(`GOYOVA03`/`GOYOVA04`), 다시 읽어 확인. S4 동기화하는 금고면 `outgoing`. S5 보류 줄을 확정. 모든 파일 쓰기는 같은 폴더의 임시 파일 → 동기화 → 이름 바꾸기입니다.
- **꺼졌을 때(다음 잠금 해제):**

|어디까지|디스크|다음 잠금 해제|
|---|---|---|
|S0 전|K, V|예전 비밀번호로 열림. 아무것도 쓰지 않았음|
|S0 ~ S2의 이름 바꾸기 전|K, V(또는 V_probe), 남은 임시 파일, 보류 줄|예전 비밀번호로 열림. 보류 줄은 버리고 "지난 열쇠 변경이 끝나지 않아 예전 열쇠로 열었습니다". 새 비밀번호로 열려 하면 "열쇠 변경이 중간에 끊긴 흔적이 있습니다…"|
|S2 이름 바꾼 뒤|K′, V_probe|새 비밀번호로 열림. 보류 줄로 이 PC의 변경임을 알아보고, `SHA(V) = resume`이라 조용히 마저 끝냄(V′ 저장, 확정). 예전 비밀번호로 열려 하면 "이 PC에서 한 열쇠 변경은 저장되었습니다…"|
|S2 교체가 끊김(FAT/exFAT)|V_probe, `K.<32자리>.goyotmp`(K′)|규칙 (i): 그 임시 파일이 열리면 이름을 되돌리고 마저 끝냄. 열리지 않으면 "열쇠 변경이 거의 끝난 상태로 열쇠 파일이 임시 파일로 남았습니다…"|
|S3 ~ S5|K′, V_probe 또는 V′(또는 그 임시 파일)|새 비밀번호로 정상. 임시 파일은 규칙 (iii)·(iv)로 복구하거나 지움. 확정되지 않은 보류 줄을 확정|

  꺼지지 않은 실패: S2에서 열쇠 파일이 예전 그대로 읽히면 "열쇠 파일을 저장하지 못했습니다… 아무것도 바뀌지 않았습니다". 무엇이 남았는지 알 수 없으면 새 열쇠 파일을 메모리에 들고 저장하기를 거부하며, '열쇠 백업'으로 그 파일을 저장하게 한 뒤 잠급니다. S1이나 S3의 교체가 끊기면 앱이 잠그고 다음 잠금 해제가 임시 파일을 되돌립니다. S3이 실패하면 열쇠는 바뀐 채로 저장·폴링 때마다 금고 파일을 다시 씁니다.
- **예전 키의 금고 파일:** 열쇠 파일이 담은 예전 키로 저장된 금고 파일은, 마지막 변경의 `resume`이면 조용히, 이 PC가 마지막으로 쓴 키(`vkey`)면 물은 뒤에만 열고 곧바로 현재 키로 다시 저장합니다. 그 밖의 예전 키 금고 파일은 열지 않습니다('복원'은 묻지 않고 새 파일에 씀). 예전 키 파일의 `generation`·`seen`이 2^40을 넘으면 열지 않습니다.

### 새 열쇠 파일 받기 (0.9.0)

다른 PC의 열쇠 파일 O를 이 PC의 K와 비교합니다(비밀번호를 묻기 전, 공개된 바이트만으로).

|경우|조건|결과|
|---|---|---|
|같음|O의 상태 = K의 상태|쓰지 않음|
|오래됨|O가 이 PC가 거쳐 온 예전 상태이고 K가 O의 현재 키를 담음|거부|
|이미 들어 있음|O의 키·제거 기록이 모두 K에 있고 O의 `epoch` ≤ K의 `epoch`|쓰지 않음|
|이어진 새 버전|O가 K의 현재 데이터 키로 chain되어 있고, `epoch`가 K보다 크거나(같으면 현재 키가 다름), 열린 파일들이 증명하는 수정 번호와 이 PC의 열쇠 기록의 확정 상태 이상|O의 `[0, W)`를 바이트 그대로 두고 이 PC의 seal block(`resume`, salt, nonce)으로 다시 봉인. 상태와 열쇠 확인 코드는 O와 같음|
|합치기(종류 9)|그 밖에 검사를 통과한 것(갈라진 파일 등)|새 데이터 키로 새 열쇠 파일. 키 목록 `[새 키] ‖ K의 키(ID 키 제외) ‖ K에 없는 O의 키(O의 ID 키 제외) ‖ [ID 키]`, 64개를 넘으면 가운데 부분의 끝(O의 가장 오래된 키, 그다음 K의 것)부터 버리되 새 키·두 현재 키·ID 키는 남김. 제거 기록은 둘의 합집합. `epoch` = max(K, O, 증명된 수정 번호, 확정 상태) + 1|

- 거부: 다른 금고·다른 OTP 여부·다른 OTP 비밀키·다른 ID 키("이 열쇠 파일은 이 금고의 것이 아닙니다"), 보안 키 파일, 증명된 수정 번호보다 2^16 넘게 큰 `epoch`("수정 번호가 너무 큼"), K의 제거 기록이 빠진 파일("제거 기록이 빠짐". 갈라진 뒤에 이 PC가 한 제거는 예외로 합치기가 유지). 이 PC가 예전 열쇠 파일로 열려 있는 동안에는 확정 상태 자체이거나 그 현재 키를 담은 더 높은 `epoch`의 파일만 받고 합치기는 하지 않습니다. 복원한 금고에서는 받지 않습니다.
- 비밀번호: 이 PC의 비밀번호로 O를 먼저 열어 보고, 안 되면 O의 비밀번호를 묻습니다. 이어진 새 버전은 O의 비밀번호를 그대로 씁니다. 합치기는 O가 K에서 이어졌으면 O의 비밀번호, 갈라졌으면 갈라진 뒤 한쪽만 바꿨을 때 그쪽, 아니면 사용자가 고른 쪽(기본은 O)입니다. 두 비밀번호가 같으면 O의 `pw_id`를 씁니다.
- 쓰는 순서와 꺼졌을 때의 처리는 위 '열쇠 변경'과 같습니다(보류 줄의 `src=adopt`).

## 보안 키 열쇠 파일 `GOYOKH01`/`GOYOKS01`

**보안 키 빌드 전용(실험, [SECURITY_KEY.md](SECURITY_KEY.md)).** 기본 빌드는 이 파일을 매직만 보고 거부합니다(위 표). 보안 키 빌드는 같은 KF2 검사기로 읽습니다. `GOYOKH01`은 PC에만 두는 파일이고 어떤 경로로도 서버에 올라가지 않습니다. `GOYOKS01`은 열쇠 파일 동기화를 켠 파일(PIN 모드 필수)이고, 서버로 올라갈 수 있는 유일한 열쇠 파일입니다(열쇠 요청 PUTKEY로만). 매직은 아래 S 포장과 본문이 함께 인증하므로 두 매직을 바꿔 붙이면 열리지 않습니다.

**머리글에서 달라지는 칸** (위 `GOYOKE03` 표와 같은 위치):

|위치|길이|내용|
|---:|---:|---|
|32|1|flags: bit0 = OTP 금고, bit1 = PIN 모드(모든 칸이 PIN 칸). `GOYOKS01`은 bit1 필수|
|34|1|`n`: 보안 키 칸 수, 1 ~ 8|
|35|1|`next`: 다음 키 번호, 1 ~ 255|
|38|1|변경 종류(아래 표)|
|39|1|이번 쓰기를 승인한 키의 칸 번호(`< n`)|
|40|1|터치 표시: bit i = 칸 i를 이번 쓰기에서 터치함(승인 키 포함)|
|41|1|일시 정지 표시: bit i = 칸 i는 살아 있지만 이 파일에 S 포장이 없음|

키 ID(16·k)와 제거 기록(24·r) 뒤에 다음이 옵니다.

|순서|길이|내용|
|---|---:|---|
|칸 기록, 번호 순|70 + c씩|종류 1(FIDO2 hmac-secret) · flags(bit0 = 등록 때 UV 확인, bit1 = credProtect 3 필수로 등록, 둘 다 = PIN 칸) · 번호(1 ~ 255, '보안 키 N') · 예약 0 · 등록 시각 u64 · `added_epoch` u64(등록한 쓰기의 `epoch`) · `added_by`(승인 키의 credhash 16바이트, 처음 켤 때 0) · seed `s`(32, 등록 때 정하고 '모든 키 새로 잠그기'만 바꿈) · `c` u16(자격 증명 ID 길이, 1 ~ 1023) · 자격 증명 ID|
|짝 기록, (주인, 대상) 순|108씩|주인 칸(1) · 대상 칸(1) · 예약 0(2) · `Wrap(seal_주인, "pair", ctx_pr, IK(대상←주인))`(104). 뜻: 주인이 대상에게 새 S를 전할 수 있음|
|**H**: S 포장, 칸 순|106씩|받는 칸(1) · 전한 칸(1) · `Wrap(base, "s-wrap", ctx_sw, S)`(104). 살아 있고 일시 정지되지 않은 칸마다 하나|
|**W**: seal block|88|`GOYOKE03`과 같음. 그 뒤 `C_body`, 본문, chain도 같음|

`H = 96 + 16k + 24r + Σ(70 + c_i) + 108p`, `W = H + 106w`(w = n − 일시 정지 칸 수). 상태 태그는 `GOYOKE03`처럼 `[0, W)`로 정합니다. 가장 작은 파일은 489바이트(k = 1, n = 1, c = 1, p = 0, OTP 없음), 키 4개가 모두 짝을 맺은 보통 파일(c = 64, k = 1, OTP 없음)은 2,568바이트, 가장 큰 파일(k = 64, r = 480, n = 8, c = 1023, p = 56, OTP)은 32,532바이트입니다.

```
p_j     = "goyo-vault/v2/hmac-salt\0" ‖ 금고 ID ‖ s_j                   키 j의 PRF 입력(금고 ID로 분리)
salt_j  = SHA-256("WebAuthn PRF" ‖ 0x00 ‖ p_j)                          hmac-secret에 그대로 보냄
H_j     = 보안 키 안의 HMAC-SHA256(자격 증명 비밀[UV 여부], salt_j)       어디에도 저장하지 않음
ch_j    = SHA-256("goyo-vault/v2/cred\0" ‖ 자격 증명 ID)의 앞 16바이트  credhash
PRK_j   = HKDF-Extract("goyo-vault/v2/key", H_j)
self_j  = HKDF-Expand(PRK_j, "self\0"      ‖ 금고 ID ‖ ch_j ‖ s_j, 32)
seal_j  = HKDF-Expand(PRK_j, "pair-seal\0" ‖ 금고 ID ‖ ch_j ‖ s_j, 32)
IK(j←i) = HKDF-Expand(PRK_j, "inbox\0"     ‖ 금고 ID ‖ ch_j ‖ s_j ‖ ch_i ‖ s_i, 32)   i가 j에게 S를 전하는 열쇠
Wrap(base, use, ctx, pt):
          prk  = HKDF-Extract("goyo-vault/v2/" ‖ use, base)
          KEK  = HKDF-Expand(prk, "key\0" ‖ ctx, 32),  C = HKDF-Expand(prk, "commit\0" ‖ ctx, 32)
          기록 = nonce(24) ‖ C(32) ‖ XChaCha20-Poly1305(KEK, nonce, AAD = "goyo-vault/v2/" ‖ use ‖ "-aad\0" ‖ ctx, pt)
ctx_pr  = 금고 ID ‖ ch_o ‖ ch_t ‖ s_o ‖ s_t                               짝 기록 PR(o, t)
ctx_sw  = 금고 ID ‖ epoch:u64 ‖ ch_j ‖ ch_v ‖ SHA-256(file[0..H))          S 포장 SW(j via v)
base    = self_j(j를 이번에 터치) 또는 IK(j←v)(v = 승인 키, PR(v, j)가 있어야 함)
ks_id   = HKDF-Expand(HKDF-Extract("goyo-vault/v2/ks-id", S), 금고 ID, 16)
본문 prk = HKDF-Extract("goyo-vault/v2/body", pw_key ‖ S)                 GOYOKE03은 S 대신 0(32바이트)
```

`C`는 AEAD 전에 상수 시간으로 비교하고, 실패는 그 단계를 부른 쪽의 실패와 같습니다(`인증 실패`). 본문 키와 `C_body`, chain, 상태 태그, 열쇠 확인 코드는 `GOYOKE03`과 같고 본문 키만 S를 함께 씁니다. 비밀번호만으로 확인할 수 있는 값(검증값, MAC, 비밀번호 칸, 복구 칸)이 없으므로 등록한 키 없이는 비밀번호를 오프라인으로 추측할 수 없습니다. 모든 S 포장이 `[0, H)` 전체(칸, 짝 기록, 승인 키, 표시, `epoch`, 제거 기록)를 묶고 본문이 `[0, B)`를 묶으므로, 칸이나 짝 기록을 옮기거나 빼거나 순서를 바꾸거나 PIN 표시를 낮추면 열리지 않습니다. **쓸 때마다 S를 새로 뽑습니다**(받은 파일을 같은 수정 번호로 다시 봉인할 때만 그대로). 짝 기록은 두 키가 함께 터치된 쓰기에서만 만들고, 두 키가 살아 있고 seed가 그대로인 동안 그대로 옮겨 적습니다(앞의 칸 번호 두 바이트만 그 파일의 칸 순서를 따름). 전달 열쇠 `IK(t←o)`는 o나 t의 하드웨어만 만들거나 열 수 있어서, 뺀 키는 그 뒤에 쓴 파일의 S를 읽을 수 없습니다.

**제거 기록의 분실 표시.** `removed`의 비트 48-63은 그 키를 '잃어버린 키 제거'로 뺐을 때의 분실 날짜입니다: 0 = 분실 아님(빼기, 보안 키 끄기, 합치기 규칙), 1 = 날짜 모름, d ≥ 2 = 1970-01-01(UTC)부터 `d − 2`일째. 표시는 제거 기록의 일부라 뒤의 모든 파일이 그대로 담고, 합치기는 credhash마다 이른 제거 `epoch`와 0이 아닌 쪽(더 이른 날짜, 1이 가장 이름)의 표시를 남깁니다. 다른 PC는 받은 제거의 이 표시로 '동기화로 들어온 변경 확인'을 할지와 그 날짜를 정합니다(파일의 `loss` 칸은 다음 쓰기에서 0이 되므로).

**엄격한 검사(더하는 것).** 매직별 범위(`GOYOKH01`·`GOYOKS01`은 n ≥ 1, `GOYOKS01`은 PIN 모드이고 모든 칸이 PIN 칸, 변경 종류는 위 표의 매직에만), 칸 번호(1 이상)와 자격 증명 ID·credhash가 겹치지 않고 번호 순, 제거 기록에 있는 자격 증명의 칸 없음, `1 ≤ added_epoch ≤ epoch`, 짝 기록은 (주인, 대상) 순으로 엄격히 오름차순이고 서로 다른 두 칸, 승인 키는 터치한 칸이고 일시 정지되지 않음, 터치한 칸과 일시 정지한 칸은 겹치지 않음, 종류 3은 정확히 한 칸이 이번에 추가되고 그 `added_by`가 승인 키, S 포장은 일시 정지되지 않은 칸마다 정확히 하나이고 '전한 칸'은 받는 칸을 터치했으면 그 칸 자신, 아니면 승인 키이며 그때 (승인 키 → 받는 칸) 짝 기록이 있어야 함, `ks_id` ≠ 0과 `KS_ID_ZERO`. 길이는 공식과 정확히 같아야 합니다.

**받을 때(보안 키 빌드).** 다른 PC의 보안 키 파일은 터치 전에 공개 바이트로 먼저 검사합니다.
- 이 PC의 제거 기록을 모두 담아야 하고(P3), 이 PC가 뺀 키가 승인한 파일은 받지 않습니다(P4). 키는 자기 자신의 제거를 승인할 수 없고 승인 키는 그 파일에서 살아 있어야 하므로, 뺀 키로 만든 파일은 그 키를 뺀 PC에서 터치 전에 거부됩니다.
- 이 PC가 아는 칸의 번호·등록 정보와 짝 기록은 고정입니다. 바뀌었으면 관문이 필요하거나 거부합니다(짝 기록은 이 PC가 손상을 확인한 것만 바뀔 수 있음).
- 키 구성이나 정책(PIN, 매직)을 바꾸는 파일은 관문을 통과해야 받습니다. 제거만 있는 파일은 사용자가 빠진 키를 정확히 고르면(G2), 그 밖(추가, 정책 변경, 이 PC가 모르는 키의 제거, 처음 받는 열쇠 파일)은 바꾼 PC의 열쇠 확인 코드를 입력하면(G1) 통과합니다. 고르기는 한 번만이고, 틀리면 무엇이 바뀌었는지 밝히지 않고 코드만 남습니다.
- 이 PC의 상태에서 이어진 새 버전(이 PC의 현재 데이터 키로 chain됨)은 `[0, W)`를 그대로 두고 다시 봉인합니다. 그 밖은 합치기(종류 9)로 새 S와 새 데이터 키를 씁니다. 관문 없이 받는 파일은 이 PC가 마지막으로 쓰거나 확인한 수정 번호(`gated`)보다 2^8 넘게 위일 수 없고, 넘으면 코드가 필요합니다.
- 같은 잃어버린 키를 두 PC에서 따로 뺀 두 파일도 지금 빌드에서는 한 PC의 '받기…'나 '새 열쇠 파일 받기'로 합칩니다.

## 금고/백업 파일

|위치|길이|내용|
|---|---:|---|
|0|8|`GOYOVA01`(동기화 없음) 또는 `GOYOVA02`(동기화를 켠 금고)|
|8|16|대응 열쇠의 금고 ID|

AAD는 앞의 48바이트 전체. 키는 열쇠 파일에서 복호화한 데이터 키입니다. 매직이 AAD에 들어 있어, `GOYOVA02` 파일의 매직을 `GOYOVA01`로 바꾸면 인증에 실패합니다. 가장 작은 파일은 `GOYOVA01` 76바이트, `GOYOVA02` 96바이트이고 가장 큰 파일은 8 MiB입니다. 후행 데이터는 거부합니다.

`GOYOVA` 뒤에 `05` 이상의 두 자리 숫자가 오면 복호화 전에 "더 새로운 버전에서 만든 금고 형식입니다. 고요 금고를 업데이트하세요."로 거부합니다(0.8은 `03` 이상을 이렇게 거부합니다). 매직은 공개 정보라 이 구분으로 새는 것은 없습니다.

### GOYOVA03/04 머리글 (KF2 열쇠 파일의 금고)

0.8 열쇠 파일(`GOYOKE01`/`GOYOKE02`)로 연 금고는 `GOYOVA01`/`GOYOVA02`로, KF2 열쇠 파일로 연 금고는 `GOYOVA03`(동기화 없음, 평문은 `GOYOVA01`과 같음)이나 `GOYOVA04`(동기화를 켠 금고, 평문은 `GOYOVA02`와 같음)로 저장합니다.

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOVA03` 또는 `GOYOVA04`|
|8|16|금고 ID(위치는 그대로라 도우미·서버의 ID 확인이 같음)|
|24|16|이 파일을 잠근 데이터 키의 키 ID|
|40|8|쓴 쪽 열쇠 파일의 `epoch`(1 ~ 2^48−1)|
|48|16|쓴 쪽 열쇠 파일의 상태 태그|
|64|1|flags: bit0 = 쓴 쪽 열쇠 파일이 보안 키 파일(`GOYOKH01`/`GOYOKS01`), bit1 = `GOYOKS01`. 다른 비트는 0이고 bit1은 bit0과만|
|65|3|예약, 0|
|68|24|nonce|
|92|가변|암호문 + 16바이트 태그. AAD는 앞의 92바이트 전체|

가장 작은 파일은 `GOYOVA03` 120바이트, `GOYOVA04` 140바이트이고 가장 큰 파일은 8 MiB입니다. 머리글이 108바이트(0.8 형식은 64바이트)라 저장 크기 검사는 `평문 + 108 ≤ 8 MiB`입니다. 최소 크기보다 작거나, `epoch`가 0이거나 2^48−1보다 크거나, 모르는 flags 비트·bit0 없는 bit1·0이 아닌 예약 바이트가 있으면 키를 유도하기 전에 "금고 파일의 머리글이 손상되어 열 수 없습니다…"로 거부하고 실패로 세지 않습니다. 머리글의 키 ID·`epoch`·태그·flags는 인증 전에는 어느 키로 풀지와 안내 문구를 고르는 데만 쓰고, 풀린 뒤에 AEAD로 함께 확인됩니다.

**어느 키로 푸나.** `GOYOVA01`/`GOYOVA02`는 ID 키(키 ID 목록의 마지막)로, `GOYOVA03`/`GOYOVA04`는 머리글이 가리키는 키로 풉니다. 그 키가 열쇠 파일의 목록에 없으면 비밀번호를 보기 전에 "이 금고 파일은 이 열쇠 파일에 없는 열쇠로 저장되어 있습니다…"(복원이면 "이 백업은 이 열쇠 파일에 없는 열쇠로 잠겨 있습니다…"), flags bit0이 있으면 "이 금고 파일은 보안 키로 잠긴 열쇠 파일로 저장되었습니다…"로 거부합니다. 0.8 열쇠 파일은 키 ID 목록이 없어 `GOYOVA03`/`GOYOVA04`를 열지 않습니다. 현재 키(목록의 첫 키)로 잠긴 파일은 그대로 열고, 그 머리글의 `epoch`가 열쇠 파일보다 크면 다른 PC에서 열쇠 파일을 바꾼 것이라 알립니다. 예전 키로 잠긴 파일은 열쇠 파일의 마지막 변경이 바꾸기로 한 그 파일(`resume`)이면 조용히, 아니면 사용자에게 물은 뒤에만 열고, 열면 바로 현재 키로 다시 저장합니다. 복원은 목록의 어느 키로 잠긴 백업이든 묻지 않고 받아 현재 키로 새 파일에 씁니다. `GOYOVA01`/`GOYOVA02`가 KF2 열쇠 파일 아래에 있으면 열 때 `GOYOVA03`/`GOYOVA04`로 다시 저장합니다. 8 MiB까지 44바이트가 남지 않은 0.8 금고 파일은 새 머리글로 저장할 수 없으므로, OTP 없는 금고는 저장하지 않은 채 열고 항목을 지우라고 알리며, OTP 금고와 복원은 "이 금고 파일은 이 열쇠 파일의 형식으로 다시 저장하면 용량 제한(8 MiB)을 넘어 열지 않았습니다…"로 거부합니다(실패로 세지 않음).

### GOYOVA01 평문

마지막 승인 OTP step(u64, OTP 미사용 금고는 0), 항목 수(u32), 각 항목의 이름/종류/비밀/메모 순서이며 각 문자열은 u32 바이트 길이 + UTF-8입니다. OTP를 쓰는 금고는 잠금 해제 시 OTP step을 먼저 저장한 후 항목을 노출합니다. OTP 미사용 금고는 잠금 해제만으로는 금고 파일을 다시 쓰지 않습니다.

### GOYOVA02 평문

사용자가 그 금고의 동기화에 동의한 뒤에만 씁니다. 동기화를 켜지 않은 금고는 0.8.0 이상에서도 계속 `GOYOVA01`로 저장합니다. 동기화 폴더와 연결된 금고는 잠금 해제 때 받아 둔 서버 사본을 OTP 확인 전에 합치고, 그 결과가 달라졌으면 OTP를 통과한 뒤 저장합니다. 그래서 OTP를 쓰지 않는 금고도 이때는 잠금 해제로 금고 파일을 다시 쓸 수 있습니다.

|위치|길이|내용|
|---:|---:|---|
|0|8|`last`: 마지막 승인 OTP step(OTP 미사용 금고는 0)|
|8|8|`generation`: 내용 변경 횟수(모든 PC가 함께 쓰는 Lamport 카운터)|
|16|8|`seen`: 이 PC가 합친, 인증된 서버 사본의 가장 큰 `generation`. 이 PC에만 의미가 있고 다른 PC의 값은 합칠 때 무시합니다.|
|24|4|항목 수 `n` (1000 이하)|
|28|…|`n` × 항목: `id`(16) · `parent`(16, 새 항목은 0) · 이름 · 종류 · 비밀 · 메모. 문자열은 u32 길이 + UTF-8, 제한은 v1과 같습니다.|
|…|4|삭제 기록 수 `m` (65,536 이하)|
|…|16·m|삭제 기록(tombstone) ID, 기록한 순서대로|

다음은 모두 `인증 실패`로 거부합니다: 0인 항목 ID 또는 삭제 기록, 중복 항목 ID, 중복 삭제 기록, 삭제 기록에도 있는 항목 ID, 한도를 넘는 개수, 빈 이름·빈 비밀정보·NUL·길이 초과 문자열, 후행 데이터. 저장할 때도 같은 규칙을 먼저 검사해, 다시 읽을 수 없는 파일은 쓰지 않습니다. 저장 크기는 `28 + Σ(48 + 문자열 길이 합) + 4 + 16·m + 64`이며 8 MiB를 넘으면 "금고 용량 제한(8 MiB)을 초과했습니다."로 거부합니다.

### 항목 ID

- **새 항목:** 하드웨어 난수 16바이트. 0이거나 이미 있는 ID·삭제 기록이면 다시 뽑습니다.
- **수정:** 새 무작위 ID를 받고 `parent`는 이전 ID가 됩니다. 이전 ID는 삭제 기록에 들어갑니다. 내용이 같으면 아무것도 바뀌지 않습니다.
- **삭제:** ID를 삭제 기록에 넣습니다.
- 추가·수정·삭제마다 `generation`이 1 오릅니다. OTP step(`last`)만 바뀌는 잠금 해제와 비밀번호 변경은 `generation`을 바꾸지 않습니다.
- 삭제 기록은 지우지 않습니다. 하나라도 잊으면 다른 PC의 오래된 사본이 그 항목을 되살리기 때문입니다. 65,536개가 차면 "삭제·수정 기록이 한도(65,536개)에 도달했습니다."로 수정·삭제를 거부합니다. `GOYOVA01` 금고는 삭제 기록을 메모리에만 두고 저장하지 않습니다.

**v1 항목의 ID.** `GOYOVA01`에는 ID가 없으므로 읽을 때마다, 그리고 동기화를 켤 때 같은 방법으로 계산합니다.

```
k  = 같은 파일에서 앞에 나온 항목 중 네 문자열이 모두 같은 항목의 수
id = HMAC-SHA256(데이터 키,
                 "goyo v1 entry\0" || 금고 ID(16) || k:u32 ||
                 len(이름):u32 || 이름 || len(종류):u32 || 종류 ||
                 len(비밀):u32 || 비밀 || len(메모):u32 || 메모)[0..16]
id가 16바이트 모두 0이면 id[0] = 1
parent = 0
```

데이터 키로 계산하므로 ID로 내용을 짐작할 수 없습니다. 같은 v1 금고의 사본을 두 PC에서 따로 동기화 형식으로 바꿔도 ID가 같아, 합칠 때 중복이 생기지 않습니다. 동기화를 켜면 `generation = 1`, `seen = 0`, 삭제 기록은 비운 상태로 시작합니다.

**같은 ID, 다른 내용.** 정상 클라이언트는 만들지 않지만(오류가 있는 클라이언트나 데이터 키를 가진 사람만 가능), 생기면 모든 PC가 같은 결과를 내도록 정합니다. 네 문자열(이름, 종류, 비밀, 메모 순서)을 바이트 순으로 비교해 작은 쪽이 ID를 갖습니다. 다른 쪽은

```
id2 = HMAC-SHA256(데이터 키, "goyo dup\0" || id(16) || 옮기는 쪽의 네 문자열을 위와 같은 len:u32 || bytes 형식으로)[0..16]
id2가 모두 0이면 id2[0] = 1
```

로 옮기고 `parent`는 떠난 ID(여기서는 `id`)로 둡니다. `id2`에서도 같은 규칙을 따릅니다. `id2`가 삭제 기록에 있으면 그 글은 남지 않고, 비어 있으면 그 자리에 들어가고, 같은 글이 있으면 그 하나로 남고, 다른 글이 있으면 다시 작은 쪽이 남고 다른 쪽이 `id2`에서 같은 식으로 만든 다음 ID로 옮깁니다. 그래서 각 글은 자기 사슬(`id` → `id2` → …)에서 더 작은 글이 차지하지 않은 첫 ID에 놓이고, 도착 순서와 관계없이 모든 PC가 같은 결과를 냅니다. 한 번의 합치기에서 이렇게 옮기는 횟수가 4,000번(항목 한도의 4배)을 넘으면 한도 초과로 보고 아무것도 바꾸지 않습니다.

이 PC의 글이 다른 ID로 옮겨 남으면 충돌(두 버전을 모두 남김)로, 어디에도 남지 않으면 삭제로 알립니다. 합치기 전 사본을 만들지 정할 때는 더 넓게 셉니다. 이 PC의 항목 가운데 결과에서 같은 ID에 같은 글로 남지 않은 것은 모두(지워짐, 다른 PC에서 고침, 다른 글에 밀려남. 다른 ID로 옮겨 남은 것도) 사라진 항목입니다(아래 `pre-merge-*` 파일).

### 합치기

동기화된 서버 사본은 금고 앱이 인증(AEAD)한 뒤에만 합칩니다.

```
삭제 기록 T = 이 PC의 기록(순서 유지) + 서버 사본에만 있는 기록(순서 유지)
항목       = (이 PC의 항목 ∪ 서버 사본의 항목) 중 ID가 T에 없는 것.
             이 PC의 순서를 지키고, 서버 사본에만 있던 항목을 뒤에 붙임
last       = max(이 PC의 last, min(서버의 last, 현재 step + 1))
올릴 필요   = 결과의 항목 ID 집합 또는 삭제 기록 집합이 서버 사본과 다름 (last는 보지 않음),
             또는 결과가 서버 사본의 어떤 ID에 다른 글을 가짐
generation = max(양쪽), 올릴 필요가 있으면 + 1
seen       = max(이 PC의 seen, 서버 사본의 generation)
되돌림 경고 = 서버 사본의 generation < 이 PC의 seen
```

합치기는 삭제 기록을 새로 만들지 않습니다. 그래서 오래되거나 되돌린 서버 사본은 변경을 늦출 수는 있어도 이 PC의 항목을 지우거나 되돌릴 수 없습니다. 결과가 1000개, 8 MiB, 삭제 기록 65,536개를 넘으면 아무것도 바꾸지 않습니다. 같은 부모(삭제된 ID)를 가진 살아 있는 항목이 둘 이상이면 두 PC에서 함께 고친 것으로, 그중 하나가 방금 도착했을 때 한 번 알립니다. 알림은 항목 이름 없이 개수만 보입니다.

### 확인 코드

```
HMAC-SHA256(데이터 키,
            "goyo sync check\0" ||
            살아 있는 항목마다, ID 오름차순으로: id(16) || SHA-256(네 문자열을 len:u32 || bytes 형식으로) ||
            0xFF × 16 ||
            삭제 기록 ID들(오름차순))의 앞 8바이트
```

`XXXX-XXXX-XXXX-XXXX`(대문자 16진수)로 표시합니다. 데이터 키는 ID 키(처음 데이터 키, 키 ID 목록의 마지막)입니다. KF2 열쇠 파일로 연 금고는 삭제 기록 뒤에 `0xFE × 16 ‖ epoch:u64 ‖ 상태 태그(16)`도 넣으므로, 두 PC가 같은 열쇠 파일을 가졌을 때만 같은 코드가 됩니다. 항목의 글까지 들어가므로 두 PC의 코드가 같으면 같은 내용입니다. 항목 순서, OTP step(동기화하지 않음), `generation`·`seen`은 넣지 않습니다. 데이터 키로 계산하므로 코드로 내용을 알 수 없고, 64비트라 다른 내용을 같은 코드로 맞추려면 데이터 키를 가진 사람도 약 2^64번 계산해야 합니다.

### 호환성

**동기화를 켠 금고와 그 백업은 0.8.0 이상에서만, KF2 열쇠 파일로 저장한 금고는 0.9.0 이상에서만 열립니다.**

|읽는 버전|`GOYOVA01`|`GOYOVA02`|`GOYOVA03` / `GOYOVA04`|
|---|---|---|---|
|0.7.x 이하|읽음|`인증 실패`로 거부(이전 버전은 바꿀 수 없음)|`인증 실패`로 거부|
|0.8.x|읽음. 동기화를 켜지 않은 금고는 계속 `GOYOVA01`로 저장|읽음. 한 번 `GOYOVA02`가 된 금고는 계속 `GOYOVA02`로 저장|"더 새로운 버전에서 만든 금고 형식입니다"로 거부|
|0.9.0|0.8과 같음(0.8 열쇠 파일이면 계속 이 형식)|0.8과 같음|읽음. `GOYOVA05` 이상은 새 형식|

백업과 복원은 형식, ID, 삭제 기록, `generation`, `seen`을 그대로 유지합니다. `GOYOVA02`를 `GOYOVA01`로 되돌리는 기능은 없습니다.

## 동기화 폴더 `<금고 파일 이름>.sync\`

예: `vault.goyo.sync\`. 도우미(`goyo-sync.exe`)만 이 폴더를 만들고, 금고 앱은 이 폴더가 링크·정션이 아닌 실제 폴더(재분석 지점 속성 없음)이고 열쇠 파일이 그 안에 없을 때만 씁니다. 모든 파일은 쓰는 쪽이 하나뿐이고, 빈 `helper.lock`을 빼면 같은 폴더의 임시 파일을 기록·동기화한 뒤 `MoveFileExW`로 이름을 바꿔 넣습니다. 제자리에 덮어쓰지 않습니다.

|파일|쓰는 쪽|형식|최대|
|---|---|---|---|
|`outgoing.goyosync`|금고 앱 (올라간 것이 확인되면 앱이 지움)|`GOYOSOU1`(8) · `base` u64 · `GOYOVA02` 또는 `GOYOVA04` 파일|16 B + 8 MiB|
|`incoming.goyosync`|도우미|`GOYOSIN1`(8) · `version` u64(1 이상) · 서버가 보낸 `GOYOVA02` 또는 `GOYOVA04` 파일 그대로|16 B + 8 MiB|
|`status`|도우미 (금고 앱은 표시에만 씀)|ASCII, 아래|512 B|

`base`는 이 상태를 만들 때 합친 서버 버전입니다(아직 없으면 0). 도우미는 이 값을 그대로 compare-and-swap의 기대 버전으로 씁니다. 금고 앱은 항상 금고 파일을 먼저 저장한 뒤 `outgoing`을 씁니다. `outgoing`이 이미 같은 `base`에서 만든 같은 상태(항목·ID·글·삭제 기록. OTP 기록과 카운터는 보지 않음)를 담고 있으면 다시 쓰지 않으므로, 업로드를 받지 않는 서버에도 잠금 해제가 새 업로드를 만들지 않습니다.

`status` (각 줄 LF로 끝남, 순서 고정, 모르는 값은 '알 수 없음'):

```
goyo-sync-status 1
heartbeat=<유닉스 초. 최소 60초마다 다시 씀>
contact=<마지막으로 유효한 서버 응답을 받은 유닉스 초, 없으면 0>
state=ok|idle|offline|auth|hostkey|nossh|server|refused|config|update|oldserver|keyfile|nokeys
[features=keys]
```

`oldserver`(0.9.0)는 서버 스크립트가 0.9.0보다 오래되어 `GOYOVA04` 업로드를 BAD_BLOB으로 거부한 상태, `keyfile`(0.9.0)은 서버가 KEY_BEHIND(아래)로 업로드를 거부한 상태입니다. 0.8 금고 앱은 이 두 단어를 모르는 값으로 읽습니다.

`nokeys`(보안 키 빌드)는 열쇠 파일 동기화를 쓰는 금고인데 이 PC의 서버 연결이 그 금고의 열쇠 요청을 받지 않는 상태(강제 명령에 `--key-sync=<금고 ID>` 없음)입니다. 보안 키 빌드의 도우미는 넷째 줄 `features=keys`를 더 씁니다(기본 빌드의 금고 앱은 이 줄을 무시).

**열쇠 요청 파일(보안 키 빌드).** 열쇠 요청은 금고 앱이 매번 처음부터 다시 계산하는 요청표에서만 나오고, 도우미는 열쇠 상태를 디스크에 남기지 않습니다. 금고 앱은 이번 세션에서 검증한 `GOYOKS01` 바이트만 PUT에 넣습니다(관문 1). 도우미(관문 2)와 서버(관문 3)는 문법만 봅니다: 정확한 `GOYOKS01` 매직, 고정한 금고 ID, 엄격한 검사, 크기, `epoch` 범위. `outgoing.goyokeysync`, `incoming.goyokeysync`, `prune.request`는 **인증되지 않습니다**. 동기화 폴더에 쓸 수 있는 사람은 그 PC의 도우미가 CUT이나 PRUNE을 보내게 할 수 있습니다(동기화 방해와 서버 기록 삭제. 어느 PC도 여는 열쇠 파일은 만들 수 없음). 링크와 파일 크기 규칙은 다른 파일과 같습니다.

금고 앱은 숫자와 정해진 단어만 읽고, 도우미가 쓴 글을 화면에 보이지 않습니다. heartbeat가 180초보다 오래되었거나 파일이 없으면 '도우미 꺼짐'입니다.

`helper.state` (정확히 이 형식이 아니면 버리고 `incoming`과 `outgoing`에서 다시 계산):

```
goyo-sync-state 1
id=<32자리 16진수>|-        고정한 금고 ID
server=<u64>                incoming에 든 서버 버전(0 = 없음)
head=<64자리 16진수>|-      그 사본의 SHA-256
done=<64자리 16진수>|-      마지막으로 처리한 outgoing 파일 전체의 SHA-256
rejected=<64자리 16진수>|-  마지막으로 거부된 outgoing 파일의 SHA-256
```

**변경 감지.** 두 프로그램 모두 `outgoing`·`incoming`의 변경을 디렉터리 목록(파일 길이, 만든 시각, 고친 시각)만으로 알아채고, 바뀌었을 때만 엽니다. 열린 핸들이 하나라도 있으면 `MoveFileExW` 교체가 실패하기 때문입니다. 교체하면 새 파일이 되어 만든 시각이 바뀝니다. 512바이트 이하인 `status`만은 금고 앱이 10초마다 잠깐 읽고, 그때 도우미의 교체가 실패하면 도우미가 다시 씁니다. 도우미는 `vault.goyo`와 열쇠 파일을 열지 않고, 금고가 있는 폴더의 목록만 읽습니다.

**올리기 전 검사(도우미).** `outgoing.goyosync`를 링크를 따라가지 않고 열어, 재분석 지점·하드 링크 2개 이상·크기 범위 밖·`GOYOSOU1`이 아님·안쪽이 `GOYOVA02`(96바이트 이상)나 `GOYOVA04`(140바이트 이상)가 아님·고정한 금고 ID가 아님 중 하나라도 해당하면 ssh를 실행하지 않습니다. 0.8 도우미의 이 검사는 `GOYOVA04`를 받지 않으므로(`state=refused`, 로그 `refused outgoing before upload`), 0.9.0 도우미는 시작할 때마다(`--once`와 '지금 동기화'도 한 번의 실행으로) 거부 기록에 남은 `GOYOVA04` 파일이 이 검사를 통과하면 한 번 다시 올립니다. 그 실행에서 다시 거부되면 그 실행 동안은 보내지 않습니다.

- '동기화됨'은 마지막 사본이 현재 키로 이 PC와 같은 열쇠 상태일 때만 나옵니다.

## 이 PC의 열쇠 기록 `goyo-vault.keys` (0.9.0)

위치는 `%LOCALAPPDATA%\GoyoVault\goyo-vault.keys`이고(디버그 빌드는 `GoyoVault-debug`), PC마다, Windows 사용자마다 따로 있습니다. 금고 폴더나 열쇠 USB만 바꿀 수 있는 사람에 맞서, 이 PC가 본 열쇠 파일 상태를 비밀번호를 묻기 전에 비교하는 두 번째 기준입니다. **비밀은 없습니다**(데이터 키, 비밀번호, 열쇠 확인 코드, 보안 키 seed 없음). 인증되지 않으므로, 이 폴더에 쓸 수 있는 같은 사용자 권한의 코드로부터는 지키지 못합니다.

**형식.** ASCII(0x20~0x7E), 한 줄에 한 기록, LF. 첫 줄 `goyo-vault-keys 4`. 버전 3 파일(0.9.0 개발 중 빌드)도 이 문법으로 읽으므로, 키 ID 등의 앞부분만 적힌 그 줄은 읽을 수 없는 줄이 됩니다(아래 **읽기**). 숫자는 앞자리 0 없는 10진수, 바이트열은 소문자 16진수, 빈 목록과 없는 값은 `-`, 목록은 쉼표로 나눕니다. 금고마다 `vault` 줄 하나(확정 상태)와 `pending` 줄 하나(쓰는 중인 열쇠 변경)까지입니다.

```
vault <금고 ID> epoch= tag= magic= policy= flags= consumed= tombs= slots= hist= merged= pbad= gated= sup= ks= keyid= vkey=
pending <금고 ID> epoch= tag= magic= policy= flags= consumed= tombs= slots= hist= pbad= gated= sup= ks= keyid=
        kind= src= opt= rm= loss= exp= clone= clears= merged= kpath= pw= base=
```

|필드|뜻|
|---|---|
|`epoch`, `tag`|확정한 열쇠 파일의 수정 번호와 상태 태그(16바이트)|
|`magic`|그 열쇠 파일의 매직. `GOYOKH`·`GOYOKS`로 시작하면 이 PC는 그 금고를 보안 키로 연 것으로 보고, 비밀번호만으로 여는 열쇠 파일을 거부합니다|
|`policy`, `slots`, `pbad`, `sup`, `ks`, `flags`의 `t`·`p`|보안 키 빌드가 씁니다(아래). 기본 빌드는 읽고 그대로 둡니다. `ks`가 없는 줄은 `-`로 읽습니다|
|`policy`|(보안 키 빌드) 확정 상태의 flags 바이트(OTP, PIN 모드)|
|`slots`|(보안 키 빌드) 칸마다 `번호:credhash:등록 날짜(yyyymmdd):자격 증명 ID 해시 앞 16바이트:seed 해시 앞 16바이트`. 바뀐 번호나 등록 정보를 알아보는 데 씁니다|
|`pbad`|(보안 키 빌드) 이 PC가 손상을 확인한 짝 기록, `<주인>><대상>`(credhash 앞 4바이트씩)|
|`sup`|(보안 키 빌드) 이 PC의 변경이 대신한 서버 상태, `<키 ID>.<수정 번호>.<태그>`|
|`ks`|(보안 키 빌드) 열쇠 파일 동기화의 의도: `-` 없음, `on.<n>` 켰고 그 업로드가 아직 서버에 보이지 않음(n = 그때 서버 맨 위 기록 번호), `off.<n>` 껐고 기록 n의 세대가 끝나기를 기다림(CUT을 보냄), `off.?` 서버를 본 적 없이 껐음(서버를 처음 볼 때 `off.<n>`으로 정하거나 지움)|
|`flags`의 `t`, `p`|(보안 키 빌드) `t` 이 상태를 이 PC가 믿음(이 PC가 썼거나 관문을 통과), `p` 이 PC가 `GOYOKS01` 파일을 바꿈|
|`flags`의 `b`|이 상태의 열쇠 백업을 했음|
|`consumed`|마지막으로 끝난 열쇠 변경의 `resume`(그 금고 파일이 이미 다시 저장되었음)|
|`tombs`|제거 기록: credhash(16) : 처음 본 상태의 현재 키 ID(16, 모르면 0) : `o`(이 PC에서 뺌) 또는 `t`(받은 파일에 있었음)|
|`hist`|이 PC가 쓰거나 받은 상태, 최근 64개: epoch : 태그(16) : 현재 키 ID(16) : `pw_id`(16) : 승인 키의 credhash(16, 없으면 0) : 변경 종류(0 = 0.8 상태). 갈라진 파일과 함께 가진 상태, 비밀번호를 바꾼 쪽, 이 PC가 가졌던 상태는 모두 전체 값으로 비교합니다(데이터 키를 고를 수 있는 위조자는 키 ID 앞 4바이트를 쉽게 맞춤)|
|`merged`|이 PC가 자기 쓰기에 합친 서버 열쇠 파일(최근 16개)|
|`gated`|이 PC가 쓰거나 확인한 가장 새 상태의 수정 번호. 없으면 `epoch`로 읽음|
|`keyid`|확정 상태의 현재 키 ID(16바이트). 더 높은 수정 번호의 열쇠 파일은 이 키 ID를 목록에 담아야 이어진 것으로 봅니다|
|`vkey`|이 PC가 마지막으로 현재 키로 읽거나 쓴 금고 파일의 키 ID|
|`kind`, `src`|보류 중인 변경의 종류와 그것을 쓴 흐름(`other` 비밀번호 변경과 '열쇠 관리'의 보안 키 변경, `adopt` 새 열쇠 파일 받기. 보안 키 빌드는 `lost` 잃어버린 키 제거, `retire` 키 빼기, `accept` 서버 열쇠 파일 받기, `merge` 합치기, `supersede`, `tofu` 처음 보는 열쇠 파일 확인도 씀)|
|`kpath`|그 변경이 바꾸는 열쇠 파일의 경로(UTF-16LE를 16진수로, 1024자까지)|
|`pw`|그 상태의 비밀번호: `n` 이 흐름에서 새로 정함, `o` 받은 파일의 것, `-` 이 PC의 것|
|`base`|그 보류 줄이 바탕으로 삼은 확정 상태(epoch:태그)|
|`opt`, `rm`, `loss`, `exp`, `clone`, `clears`|(보안 키 빌드) `opt` 갈라진 파일의 선택(1 다른 PC 쪽, 2 둘 다), `rm` 빼는 키 `번호:o` 또는 `번호:t`, `loss` 분실 날짜 `yyyymmdd`나 `unknown`, `exp` PIN·비밀번호 노출 답(`y`·`n`·`u`), `clone` 같은 PIN을 쓰는 키 번호, `clears` 이 변경과 함께 풀리는 것(`g` 기다리던 관문, `2` 실패한 고르기 기록, `s` 대신한 서버 후보)|

`gate`, `review`, `clone`으로 시작하는 줄은 보안 키 빌드가 씁니다. 기본 빌드는 문법만 확인하고 그대로 둡니다.

```
gate <금고 ID> epoch=<n> tag=<32자리> state=pending|dropped|superseded|none g2=on|off since=<유닉스 초>
review <금고 ID> loss=<yyyymmdd>|unknown epoch=<n> state=due|done
clone <금고 ID> <credhash 32자리> <seed 해시 32자리>
```

- `gate`: 관문을 기다리는 서버 열쇠 파일(수정 번호와 태그)과 그 결과(`pending` 기다림, `dropped` 받지 않기, `superseded` 이 PC의 변경이 대신함, `none` 기다리는 것 없음). `g2=off`는 이 금고에서 고르기(G2)가 한 번 틀려 코드(G1)만 남았다는 뜻이고, 관문을 하나 통과하거나 이 PC의 사용자가 열쇠 변경을 하면 다시 켜집니다.
- `review`: 분실로 키를 뺀 뒤의 '동기화로 들어온 변경 확인'. `due`인 동안 금고 내용을 올리지 않습니다. 이미 기다리는 검토가 있으면 더 이른 날짜를 남깁니다.
- `clone`: '복제됐을 수 있음' 표시. 그 키가 빠지거나 seed가 바뀌면('모든 키 새로 잠그기') 지웁니다.

보안 키 금고에서는 이 기록이 필수입니다. 쓸 수 없으면 열쇠 변경과 금고 올리기를 멈춥니다. 보안 키 빌드는 파일 전체를 지우는 대신 이 금고의 줄만 지우는 '이 금고의 기록 지우고 다시 확인…'(비밀번호와 터치로 연 뒤, 그 열쇠 파일을 처음 보는 파일로 G1 확인)을 제공합니다. 그때도 `review` 줄과 아래 합치기 기록은 남습니다.

**쓰기.** 쓸 때마다 같은 폴더의 `goyo-vault.keys.lock`을 잠그고(최대 5초 기다림), 잠근 채 다시 읽고, `goyo-vault.keys.<16자리 16진수>.tmp`에 쓴 뒤 동기화하고 이름을 바꿔 덮습니다. 이름을 바꾸기 전에 끊긴 쓰기는 다음 쓰기가 잠근 채로 처리합니다. `goyo-vault.keys`가 없으면 끝까지 쓴 가장 새 `.tmp`를 되돌리고, 있으면 남은 `.tmp`를 지웁니다. 쓰는 금고의 줄을 맨 앞에 둡니다(줄 순서가 최근 순서). 파일은 1 MiB까지이고, 넘으면 읽지 못한 줄부터, 그다음 맨 뒤 금고의 줄부터 버립니다.

**읽기.** 줄마다 따로 읽습니다. 읽을 수 없는 줄은 그대로 두고 그 금고의 기록이 없는 것으로 봅니다(그 금고의 같은 종류 줄을 새로 쓸 때만 바뀜). 첫 줄이 더 높은 버전이거나 1 MiB를 넘는 파일은 해석하지도 고쳐 쓰지도 않고, 이번 세션 동안만 메모리에 기억합니다. 링크(재분석 지점)나 하드 링크가 2개 이상인 파일은 빈 기록으로 읽고, 다음 쓰기의 이름 바꾸기가 대신합니다. 쓸 수 없으면 비밀번호만으로 여는 금고는 이번 세션 동안 메모리에 두고 저장·폴링 때마다 다시 시도합니다. 비밀번호를 묻기 전에 읽지 못한 파일(다른 프로그램이 열고 있음)은 기록이 없는 것으로 비교하지만, 잠금 해제가 잠근 채 다시 읽은 이 금고의 줄이 그때와 다르면 아무것도 쓰지 않고 열지 않습니다. 다시 열면 다시 비교합니다.

**잠금 해제 때(비밀번호를 묻기 전).** 열쇠 파일 K를 이 금고의 `vault` 줄과 비교합니다.

|경우|결과|
|---|---|
|줄 없음|새로 기록(0.8 열쇠 파일은 쓰지 않음)|
|같은 상태, 또는 `keyid`를 담은 더 높은 `epoch`|정상. 열린 뒤 기록을 앞으로 옮김|
|`hist`에 있는 예전 상태|열되 '예전 열쇠 파일' 경고. 열쇠 변경, 합치기, 올리기를 멈춤('이 열쇠 파일이 맞습니다'로 확정)|
|`hist`에 없는 같거나 낮은 `epoch`, 또는 `keyid`가 없는 더 높은 `epoch`|갈라진 열쇠 파일로 거부|
|`epoch`가 2^16 넘게 큼|거부(위조 의심)|
|확정 상태가 보안 키 매직인데 K는 비밀번호만|거부|
|K에 없는 제거 기록|거부|

보안 키 빌드는 여기에 더합니다: 이 PC가 뺀 키를 다시 담거나 그 키가 승인한 열쇠 파일, 이 PC가 살아 있다고 기록한 키가 제거 기록 없이 빠진 열쇠 파일은 거부합니다. 더 높은 `epoch`에서 키 구성·정책·칸이 바뀌었거나 `gated`보다 2^8 넘게 위인 열쇠 파일은 열리기는 하지만 관문(고르기나 코드)을 통과할 때까지 항목을 고치거나 저장하거나 올리지 않습니다. 이 PC에 줄이 없는 보안 키 열쇠 파일(새 PC, USB 사본, 기록을 지운 PC)은 처음 보는 파일로, 다른 PC의 열쇠 확인 코드를 입력하기 전까지 같습니다.

`pending` 줄은 열쇠 변경의 S0에서 쓰고 S5에서 `vault` 줄로 바꿉니다. S0은 잠근 채 읽은 확정 상태보다 낮은 수정 번호나, 같은 수정 번호에서 그 상태의 현재 키를 담지 않은 다른 상태는 쓰지 않습니다('예전 열쇠 파일'). 다음 잠금 해제는 K가 그 보류 줄의 상태면 이 PC의 변경으로 알아보고 마저 끝내며, 아니면 버리고 알립니다. 보류 줄의 `kpath`가 지금 연 열쇠 파일이 아니고 그 파일을 읽을 수 없으면, 그 파일로 열 때까지 열쇠 변경을 멈춥니다('끝나지 않은 열쇠 변경 버리기…'가 풉니다). 경로는 드라이브 문자까지 비교하므로, USB가 다른 문자로 연결되어 같은 파일을 열어도 이렇게 멈춥니다. 연 파일에 변경이 들어 있었다면 이 PC의 변경으로 알아보았을 것이니, 그때는 버려도 됩니다. 복원은 이 기록을 고쳐 쓰지 않고, 복원한 금고에서는 열쇠를 바꾸거나 새 열쇠 파일을 받지 않습니다(원래 금고 파일이 같은 열쇠 파일을 씀).

이 파일을 지우면 모든 금고의 기록이 사라지고, 다음에 여는 열쇠 파일부터 다시 기준을 잡습니다(README의 '이 PC의 열쇠 기록').

## 합치기 기록 `goyo-vault.merges` (보안 키 빌드)

위치는 열쇠 기록과 같은 폴더의 `goyo-vault.merges\<금고 ID 32자리>.log`입니다. 보안 키 열쇠 파일과 동기화를 함께 쓰는 금고에서만 씁니다. PC마다 따로 있고 동기화되지 않으며, **비밀도 항목 내용도 없습니다**(제목·종류·비밀·메모 없음, 항목 ID는 무작위 16바이트).

```
goyo-vault-merges 3
<유닉스 초> <서버 버전> + <항목 ID>                  다른 PC에서 들어온 새 항목
<유닉스 초> <서버 버전> ~ <항목 ID> <parent ID>      고친 항목(새 ID가 parent를 대신함)
<유닉스 초> <서버 버전> = <항목 ID> <옮긴 ID>|-      이 PC가 가진 ID에 다른 내용이 들어옴(이 PC의 글은 옮겼거나 버림)
<유닉스 초> <서버 버전> - <항목 ID>                  삭제
<유닉스 초> R <yyyymmdd>|unknown                     검토가 생김(분실 날짜)
<유닉스 초> D                                        검토를 마침
<유닉스 초> ! <유닉스 초>                             그 시각 이전의 줄 일부를 한도 때문에 버림
```

- 받은 사본을 합칠 때마다, 합친 금고를 저장하기 **전에** 그 합치기가 들여온 변경을 한 줄씩 씁니다. 쓰지 못하면(입출력 오류, 5초 안에 잠그지 못함) 그 합치기를 버리고 다음 폴링에서 다시 합칩니다. 그래서 출처 줄 없이 저장된 합치기는 없습니다.
- 금고마다 항목 줄 4,000개와 512 KiB까지입니다. 기다리는 검토의 범위 밖의 오래된 줄부터 버리고, 범위 안의 줄을 버려야 하면 `!` 줄을 남겨 검토 화면이 '일부는 이 목록에 없습니다'라고 알립니다.
- 검토는 열쇠 기록의 `review` 줄이 `due`이거나, 이 기록의 마지막 검토 표시가 `R`일 때 기다리는 것으로 봅니다. 그래서 열쇠 기록을 지워도 검토가 풀리지 않습니다. 날짜는 마지막 `D` 뒤의 `R` 줄 중 가장 이른 것입니다.
- 열쇠 기록처럼 같은 폴더의 잠금 파일 아래에서 임시 파일과 이름 바꾸기로 쓰고, 같은 링크·크기 규칙으로 읽으며, 읽을 수 없는 줄은 건너뜁니다. 인증되지 않으므로 이 폴더에 쓸 수 있는 사람은 줄을 지울 수 있습니다.

## 서버 통신 (goyo-sync.exe ⇄ goyo-sync-server.py)

ssh 호출 한 번에 요청 하나입니다. 도우미는 `System32\OpenSSH\ssh.exe ... -- <host> <python> -I <remote> serve`를 실행하고, 모든 가변 데이터는 표준 입력의 프레임으로만 보냅니다. 요청 프레임 뒤에 입력을 닫고(EOF), 서버는 응답 프레임 하나를 쓰고 끝냅니다.

**요청** (`<8sB16sQI32s`, 69바이트) 뒤에 `blob_len`바이트, 그리고 EOF:

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOSRQ1`|
|8|1|op: 1 HELLO, 2 GET, 3 PUT, 4 LIST, 5 FETCH. 열쇠 파일 동기화(보안 키 빌드, 아래): 6 PUTKEY, 7 GETKEY, 8 CUTKEY, 9 PRUNE|
|9|16|금고 ID. HELLO·LIST는 0, 나머지는 0이 아니어야 함|
|25|8|HELLO: 프로토콜 1 · GET: 가진 버전(`have`) · PUT: 기대 버전(`expected`) · LIST: 0 · FETCH: 버전 N(0 = 최신) · PUTKEY: 기반한 기록 번호 · GETKEY: 가진 기록 번호 · CUTKEY: 끝낼 세대의 기록 번호 · PRUNE: 남길 가장 낮은 `epoch`(1 이상)|
|33|4|`blob_len`: HELLO 512, PUT 8 MiB 이하, PUTKEY 32 KiB 이하, 나머지 0|
|37|32|HELLO·PUT·PUTKEY: blob의 SHA-256 · GET·GETKEY: 가진 사본의 SHA-256(없으면 0) · LIST·FETCH·CUTKEY·PRUNE: 0|

**응답** (`<8sBQI32s`, 53바이트) 뒤에 `blob_len`바이트, 그리고 EOF:

|위치|길이|내용|
|---:|---:|---|
|0|8|`GOYOSRS1`|
|8|1|상태: 0 OK, 1 NOT_MODIFIED, 2 CONFLICT, 3 EMPTY, 4 NOT_FOUND, 10 BAD_REQUEST, 11 BAD_BLOB, 12 TOO_LARGE, 13 LIMIT, 14 KEY_BEHIND, 20 SERVER_ERROR|
|9|8|버전(아래)|
|17|4|`blob_len`|
|21|32|blob이 있으면 그 SHA-256, 없으면 0(클라이언트는 빈 데이터의 SHA-256도 받음)|

|op|허용하는 응답|
|---|---|
|HELLO|OK(1, 요청의 512바이트 00..FF ×2를 그대로). 왕복에서 한 바이트라도 바뀌면 오류|
|GET|OK(최신 버전, 금고 파일) · NOT_MODIFIED(`have`, 최신이 `have`이고 SHA도 같을 때만) · EMPTY(0)|
|PUT|OK(`expected + 1`) · CONFLICT(최신 버전, 최신 금고 파일) · EMPTY(0, 서버에 사본이 없고 `expected`가 0이 아닐 때) · BAD_BLOB · TOO_LARGE · LIMIT(금고 64개, 버전 번호 끝, 저장 뒤 디스크 여유 256 MiB 미만) · KEY_BEHIND(0.9.0, PUT에만. 서버에 그 금고의 열쇠 기록 `k/`가 있고 업로드한 금고 파일이 그 기준에 맞지 않음. 아래 '열쇠 파일 동기화의 서버 쪽')|
|LIST|OK(줄 수, ASCII `<금고 ID 32자리 소문자 16진수> <최신 버전> <크기> <유닉스 초>\n` 줄들, 64 KiB 이하). 버전이 없는 금고는 `<ID> 0 0 0`|
|FETCH|OK(실제 버전 번호, 금고 파일) · NOT_FOUND|
|PUTKEY|OK(새 기록 번호, 32바이트 기록 머리글) · CONFLICT(맨 위 기록 번호, 맨 위 기록) · EMPTY(0, 기록이 없고 기반 번호가 0이 아닐 때) · BAD_BLOB · TOO_LARGE · LIMIT|
|GETKEY|OK(맨 위 기록 번호, 맨 위 기록) · NOT_MODIFIED · EMPTY(0)|
|CUTKEY|OK(끊음 기록 번호, 32바이트 끊음 기록)|
|PRUNE|OK(지운 버전 수) · NOT_FOUND(최신 버전의 `epoch`가 그 값보다 낮음)|
|모든 op|BAD_REQUEST, SERVER_ERROR (blob 없음)|

오류 상태의 버전은 0이고 blob이 없습니다. 클라이언트는 응답 앞의 64 KiB까지를 로그인 셸 출력으로 보고 건너뛰며(로그에 기록), 그 밖에는 `blob_len`이 남은 바이트 수와 정확히 같고, SHA-256이 맞고, blob이 허용된 곳에만 있고, 금고 파일이면 `GOYOVA02`(96바이트 이상) 또는 `GOYOVA04`(140바이트 이상)·같은 금고 ID·8 MiB 이하여야 받습니다. `GOYOVA05` 이상이면 `state=update`, 나머지(`GOYOVA03` 포함: 동기화하지 않는 형식)는 프로토콜 오류(`state=server`)로 처리하고 `incoming`을 건드리지 않습니다. 0.9.0 도우미는 `GOYOVA04` 업로드의 BAD_BLOB을 0.9.0보다 오래된 서버 스크립트로 보고 `state=oldserver`로 두며(로그 `server refused GOYOVA04: its goyo-sync script is older than 0.9.0`), KEY_BEHIND는 `state=keyfile`로 둡니다. 둘 다 거부 기록(`rejected`)에 남기지 않고 같은 파일을 10분마다, 그리고 도우미를 다시 시작할 때 다시 올립니다. 업로드와 다른 금고 파일을 담은 PUT의 CONFLICT도, 버전이 요청의 `expected`와 같거나 이미 받은 사본을 다른 번호(1 제외)로 보낸 것이면 정직한 서버가 보내지 않는 응답이라 `state=server`로 처리합니다. 이때는 `incoming`을 다시 쓰지 않고 그 업로드를 끝난 것으로 보지 않으며, 기다림이 끝날 때 가장 새 `outgoing`만 다시 보냅니다.

**서버의 PUT.** SHA 불일치, `GOYOVA02`(96바이트 이상)나 `GOYOVA04`(140바이트 이상)가 아님(열쇠 파일 `GOYOK…`과 `GOYOVA01`·`GOYOVA03`·`GOYOVA05` 이상 포함), 헤더의 금고 ID가 요청과 다름이면 BAD_BLOB이고 아무것도 쓰지 않습니다. 8 MiB를 넘는 `blob_len`은 읽지 않고 TOO_LARGE로 답합니다. 통과하면 저장한 뒤에도 서버 디스크에 256 MiB 이상 남는지 확인하고(남지 않으면 LIMIT이고 아무것도 쓰지 않습니다. `os.statvfs`가 있는 시스템), 임시 파일을 쓰고 fsync한 뒤 `os.link`로 다음 버전 이름에 연결합니다. 같은 이름이 이미 있으면 링크가 실패하므로, 같은 `expected`로 동시에 올린 두 요청 중 정확히 하나만 성공하고 다른 쪽은 CONFLICT를 받습니다. HEAD 파일은 없습니다. 열쇠 기록(`k/`)이 없는 금고는 버전 연결에 잠금을 쓰지 않습니다. `k/`가 있는 금고는 임시 파일을 쓴 뒤 금고 잠금(`data/<id>/lock`) 안에서 열쇠 기록 기준 검사, 최신 버전 확인, 링크를 합니다(아래). 새 금고 폴더를 만들 때만 저장소 폴더에 `flock`을 걸고 그 안에서 금고 수를 다시 세므로, 동시에 처음 올려도 64개를 넘지 않습니다(POSIX). 디렉터리 fsync가 끝난 뒤에만 OK를 보냅니다.

**서버 저장 구조** (`<스크립트 폴더>/data`, umask 077):

```
data/<금고 ID 32자리 소문자 16진수>/v/000000000001.goyo …   바꾸지 않는 버전 파일, 최신 = 가장 큰 번호
data/<금고 ID 32자리 소문자 16진수>/tmp-<pid>-<ns>-<번호>    진행 중인 PUT
data/slot-0 … data/slot-7                                   동시 접속 자리 잠금 파일(빈 파일, POSIX. 첫 접속 때 data 폴더와 함께 생김)
data/<금고 ID>/k/<번호 20자리>-<floor 20자리>.rec              열쇠 기록(열쇠 파일 동기화): 맨 위 기록과, 같은 세대의 바로 앞 열쇠 파일만
data/<금고 ID>/k/tombs                                        끊음으로 끝난 마지막 열쇠 기록의 제거 기록(credhash 16바이트들, 내보내지 않음)
data/<금고 ID>/lock                                           금고 잠금(flock): 열쇠 작업과, k/가 있으면 그 금고의 PUT
```

폴더 이름은 요청의 ID 16바이트에서 만들며 클라이언트가 보낸 글자를 경로에 쓰지 않습니다. 최근 200개 버전만 남기고, 금고는 64개까지입니다. PUT이 성공할 때마다 모든 금고 폴더에서 한 시간 넘은 임시 파일을 지웁니다. 한 저장소에서 동시에 처리하는 접속은 8개까지이고(`flock`, POSIX), 그 이상은 요청을 읽지 않고 바로 SERVER_ERROR로 답합니다(stderr `busy`). 시간 제한(SIGALRM이 있는 시스템): 요청 헤더 69바이트(PUT이 아니면 요청 전체)는 30초 안에 와야 하고, PUT은 헤더 뒤 600초 안에 금고 파일과 EOF가 와야 합니다. 요청을 다 읽은 뒤의 디스크 작업에는 제한을 걸지 않아, 신호로 끊겨 임시 파일이 남는 일이 없습니다. 응답을 보낼 때는 60초이고, blob이 든 응답(금고 파일, 목록, HELLO의 512바이트)은 600초입니다. 저장소 폴더가 링크면 거부합니다.

**열쇠 파일 동기화의 서버 쪽 (보안 키 빌드, `--key-sync`).** 강제 명령이 `serve --key-sync=<금고 ID>[,<금고 ID>…]`(32자리 소문자 16진수, 서로 다름, 64개까지, 공백 없음)일 때만, 그 연결은 거기 적힌 금고에 대해 ops 6-9를 처리합니다. 그 밖의 연결과 금고에는 모든 열쇠 op가 BAD_REQUEST이고 아무것도 만들지 않습니다. 형식이 틀린 인자(빈 `--key-sync` 포함)는 그 줄의 모든 요청을 거부합니다(사용법 오류, 종료 코드 2).

- **기록.** `k/<n>-<floor>.rec`의 내용은 32바이트 머리글 `GOYOSKR1`(8) · 종류 u8(1 열쇠 파일, 2 끊음) · 손상 표시 u8 · 0(6) · `gen` u64 · `floor` u64, 그리고 종류 1이면 올린 `GOYOKS01` 파일 그대로입니다. 열쇠 기록의 `floor`는 그 파일의 `epoch`이고 `gen`은 그 세대를 시작한 끊음의 번호(그 전이면 0)입니다. 끊음은 `gen` = 자기 번호이고 바로 아래 기록의 `floor`를 이어받습니다. 번호는 한 금고 안에서 계속 커지고 다시 쓰지 않습니다.
- **잠금.** 모든 열쇠 op는 금고마다 하나인 커널 잠금(`data/<id>/lock`, POSIX `flock`. Windows의 selftest는 `msvcrt.locking`) 안에서 돕니다. 최대 20초 기다리고, 넘으면 SERVER_ERROR(`busy`)입니다. 그래서 **저장소 폴더가 `flock`을 지원해야 합니다**(Linux 로컬 파일 시스템은 모두, NFS는 흉내). 잠금 안에서 남은 임시 파일과, 맨 위 기록도 그 바로 앞 열쇠 파일도 아닌 기록을 지웁니다.
- **PUTKEY.** 기반 번호가 맨 위 기록 번호와 같을 때만(CAS) 다음 번호로 붙입니다. 새 파일은 정확한 `GOYOKS01` 문법이고 그 금고의 것이어야 하며, `epoch`는 맨 위 `floor`보다 크고 `floor + 2^16` 이하여야 합니다. 정직한 서버는 맨 위 열쇠 기록(끊음 위에서는 `k/tombs`)의 제거 기록이 빠졌거나, 제거된 키가 승인했거나, 제거된 키를 다시 담은 파일도 BAD_BLOB으로 거부합니다.
- **GETKEY**는 맨 위 기록만 보냅니다. 더 예전 기록은 보내지 않습니다.
- **CUTKEY**는 기반 번호가 속한 세대를 끝냅니다: 끊음 기록을 붙이고(그 열쇠 파일은 지워짐) 그 열쇠 파일의 제거 기록을 `k/tombs`에 남깁니다. 맨 위가 그보다 큰 번호의 끊음이거나 더 나중 세대의 열쇠 기록이면 아무것도 하지 않습니다. `k/`가 없으면 만들어서라도 끊음을 남깁니다.
- **손상된 맨 위 기록**은 그 이름의 번호와 `floor`를 가진 끊음으로 읽습니다(손상 표시 1). 그래서 내보내는 `epoch`는 줄지 않습니다. 손상이 아닌 읽기 오류는 SERVER_ERROR입니다.
- **금고 기준(KEY_BEHIND).** 금고 폴더에 `k/`가 있으면, `--key-sync`가 있든 없든 모든 연결의 PUT이 잠금 안에서 확인합니다: 맨 위가 열쇠 기록이면 업로드는 그 파일의 `epoch`, 현재 키 ID, 상태 태그를 머리글에 가진 `GOYOVA04`여야 하고, 맨 위가 끊음이면 아무 `GOYOVA04`나 됩니다. 기록이 없는 `k/`는 기준이 없습니다. 맞지 않으면 KEY_BEHIND이고 아무것도 쓰지 않습니다. `k/`가 없는 금고(열쇠 파일 동기화를 쓰지 않는 금고)에는 잠금 파일도 기준도 없습니다.
- **PRUNE**은 머리글의 `epoch`가 주어진 값보다 낮은 버전(`GOYOVA02`는 0)을 지우되 최신 버전은 지우지 않습니다. 잠금을 쓰지 않고 `k/`를 읽지 않습니다.
- `data/<id>/k/`는 **그 금고를 동기화하는 PC가 하나도 없을 때만** 지우세요. 기록 번호가 처음부터 다시 시작하면, 응답을 잃은 PC가 예전 요청을 다시 보내 빈 자리에 올릴 수 있습니다.

열쇠 기록의 공개 정보: 서버는 `GOYOKS01` 파일 전체를 가지므로 수정 번호, 변경 종류, 승인 키, 터치·일시 정지 표시, 키·제거 기록·짝 기록 수, 등록 시각, 자격 증명 ID, 쓴 시각, 보고한 분실 날짜를 압니다. 비밀번호와 등록한 키(와 PIN) 없이는 열 수 없습니다(위 '보안 키 열쇠 파일').

파일 매직·ID·salt·nonce·암호문 길이는 공개 정보입니다. 파일 길이와 파일 존재 여부를 숨기지 않습니다. 모든 문자열과 OTP 비밀키, 데이터 키는 디스크에서 암호화됩니다. 동기화 서버는 금고 ID, 파일 크기, 내용이 바뀐 시각, 버전 수, 접속한 IP, 그리고 도우미가 `interval`마다 접속하므로 각 PC가 켜져 있는 시간을 압니다.

OTP는 RFC 6238 HMAC-SHA1, 6자리, 30초, 현재 step ±1 범위이며 저장된 마지막 step보다 커야 합니다. SHA-1은 Google Authenticator 상호운용을 위한 HMAC 용도로만 사용합니다. 인증 태그·암호화에는 SHA-1을 사용하지 않습니다.
