# Android 앱

`android/` 폴더는 고요 금고의 Android 앱입니다. 1단계는 **PC에서 만든 금고를 휴대폰에서 여는 것**입니다: 금고 파일과 열쇠 파일을 앱으로 가져오고, 비밀번호와 YubiKey(NFC 또는 USB-C)로 열고, 항목을 보고 복사하고 고칩니다. 3단계는 **Tailscale로만 하는 동기화**입니다(아래 '동기화'). 0.12.0과 합친 뒤로는 항목의 **OTP 시크릿**(아래 'OTP 시크릿')도 보고 고칩니다. 4단계(앱 0.4.0)는 **PC와 같은 시작 화면과 흐름**입니다: 서버에서 가져오기(권장), 새 금고 만들기, 파일에서 가져오기, 관문 화면(G1 코드, G2 잃어버린 키), 다른 기기의 열쇠 변경 받기, 열쇠 관리의 기본(키 목록, 키 추가, 열쇠 확인 코드, 열쇠 백업). 아래 '4단계'를 보세요. 화면은 한국어만 있습니다(영어는 나중에).

암호와 파일 형식은 PC와 **같은 Rust 코드**(`goyo_vault` 라이브러리)가 처리합니다. Kotlin 쪽은 화면, 파일 가져오기, YubiKey와의 통신만 합니다. 키, 파생 키, 금고의 평문은 Rust 밖으로 나가지 않고, 화면에 보이는 항목의 글자만 나갑니다.

## 구성

| 위치 | 내용 |
| --- | --- |
| `src/posix.rs`, `src/crypto.rs` 등 | 라이브러리의 Linux/Android 구현: 커널 난수(getrandom), rename(2)+fsync 저장, O_NOFOLLOW 읽기, (st_dev, st_ino) 파일 식별, flock 잠금, `vault::set_anchor_root` |
| `android/rust` | JNI 다리(`libgoyo_android.so`, `app.goyovault.Native`). `jni` 크레이트는 여기에만 씁니다 |
| `src/syncengine.rs`, `src/syncengine/` | goyo-sync.exe에서 옮긴 동기화 엔진. Windows 도우미와 휴대폰이 같이 씁니다 |
| `android/rust/src/ssh.rs`, `tailnet.rs`, `hostkey.rs`, `line.rs`, `syncrun.rs` | 휴대폰의 SSH 전송(russh, ring), Tailscale 주소 검사, 호스트 키 고정, 서버 줄, 설정과 엔진 실행 |
| `android/rust/src/entry_otp.rs`, `android/app/.../Otp.kt` | 항목의 OTP: 코드와 남은 초(Rust에서 계산), 편집기의 OTP 칸 해석, QR 모듈(라이브러리의 `qr` 인코더); 화면의 코드·복사·QR |
| `android/app/.../Sync.kt`, `SyncKey.kt` | 동기화 시점(열 때, 저장 뒤, 지금 동기화, 15분 WorkManager), 키 저장소로 감싼 클라이언트 키 |
| `android/rust/src/fetch.rs`, `jni_keys.rs` | 4단계: 서버의 금고 목록(LIST, 열쇠 파일은 GETKEY), 금고 가져오기(FETCH)와 서버 열쇠 파일을 열쇠 보기(`incoming.goyokeysync`)로 저장, 관문·열쇠 관리·서버에서 가져온 금고의 JNI |
| `android/rust/src/reg.rs`, `flows.rs`, `take.rs` | 4단계: YubiKey 등록(MakeCredential 요청과 응답 검사), 새 금고·키 추가 흐름, 잠금 해제 때 다른 기기의 열쇠 변경 받기 |
| `android/app/.../StartUi.kt`, `ServerUi.kt`, `KeysUi.kt`, `Server.kt`, `Ask.kt` | 4단계: 시작 화면(환영·잠금 해제·서버에서 가져온 금고·열쇠 파일 필요), 새 금고 만들기, 서버에서 가져오기·동기화 설정, 열쇠 관리와 확인 배너, 흐름 중간의 질문 창 |
| `android/app` | 앱(Kotlin, Jetpack Compose, minSdk 28, compile/target 36, `app.goyovault`). YubiKey는 Yubico의 yubikit-android 3.1.0 |
| `android/rust/examples/make_test_vault.rs` | 기기 시험용 **시험 금고**(비밀번호만, 가짜 항목)를 PC에서 만드는 프로그램 |

yubikit-android는 3.1.0을 씁니다. 3.2.0부터는 compileSdk 37이 필요해서 compile 36에 맞췄습니다.

## 빌드

준비물(이 PC에 이미 있음):

- JDK 21 (`JAVA_HOME`), Android SDK (platform 36, build-tools, platform-tools)
- NDK `30.0.16248370` (`ANDROID_NDK_HOME`, 없으면 SDK의 `ndk/30.0.16248370`)
- `rustup target add aarch64-linux-android`, `cargo install cargo-ndk`
- `android/local.properties`에 `sdk.dir=...` (git에 올리지 않습니다)

```powershell
$env:JAVA_HOME = "$env:LOCALAPPDATA\Programs\jdk-21"
cd android
.\gradlew.bat assembleDebug
adb install -r app\build\outputs\apk\debug\app-debug.apk
```

`assembleDebug`가 먼저 `cargo ndk -t arm64-v8a --platform 28 build --release`로 `android/rust`(와 그 안의 금고 라이브러리)를 빌드해 `app/build/rustJniLibs`에 넣습니다. Argon2id(256 MiB)는 최적화 없이는 너무 느려서 디버그 APK도 Rust는 release로 빌드합니다. arm64-v8a(64비트 ARM) 휴대폰만 지원합니다.

PC 쪽 점검 `python -X utf8 scripts/run_checks.py`는 NDK, cargo-ndk, aarch64 타깃이 있으면 라이브러리를 Android용으로도 검사합니다(clippy, 두 판). 없으면 "NOTE: Android lib check skipped: ..."를 찍고 넘어갑니다.

### 기기에서 자동 시험

1. 라이브러리 시험 전체를 휴대폰에서 돌리기(선택):

   ```powershell
   cargo ndk -t arm64-v8a --platform 28 test --lib --no-run
   adb push target\aarch64-linux-android\debug\deps\goyo_vault-<해시> /data/local/tmp/goyo-lib-tests
   adb shell "mkdir -p /data/local/tmp/goyo-tests && cd /data/local/tmp/goyo-tests && TMPDIR=/data/local/tmp/goyo-tests /data/local/tmp/goyo-lib-tests"
   ```

   Windows에서만 생기는 상황을 흉내 내는 13개 시험(열린 핸들이 교체를 막음, 읽기 전용 속성, Windows 경로, Android가 막는 하드 링크)은 Unix에서 `ignored`로 나옵니다. 나머지는 모두 통과해야 합니다(1단계 마지막 실행: 261 통과, 13 ignored).

2. 앱 안(앱의 샌드박스와 SELinux 영역)에서 JNI와 라이브러리 시험:

   ```powershell
   cd android\rust
   cargo run --release --example make_test_vault   # app\build\testVault 에 시험 금고
   cd ..
   .\gradlew.bat connectedDebugAndroidTest
   ```

   시험 금고를 열고, 틀린 비밀번호를 거부하고, 항목을 읽고, 추가(OTP 시크릿이 든 항목 포함)·삭제·저장한 뒤 다시 엽니다. OTP는 이름, 코드(6자리, 남은 1~30초), QR 모듈 크기, 시크릿 복사 값, 빈 OTP 칸으로 고쳐도 시크릿이 남는 것, 잘못된 시크릿의 거부, 다시 연 뒤에도 남는 것을 봅니다. 시험 금고의 비밀번호는 코드에 적힌 가짜 값이고, 만드는 프로그램은 PC의 열쇠 기록(`%LOCALAPPDATA%\GoyoVault`)을 건드리지 않습니다. `connectedDebugAndroidTest`는 끝나면 앱을 지우므로, 다시 `adb install -r`로 설치하세요(가져온 금고도 지워집니다).

## 직접 해 볼 것 (실제 YubiKey)

YubiKey가 필요한 부분은 자동 시험으로 확인하지 못했습니다. 아래 순서로 확인해 주세요. **진짜 금고 말고 시험 금고로** 하세요.

1. **PC에서 시험 금고 만들기.** `goyo-vault.exe`의 '만들기'에서 새 파일 이름(예: `android-test.goyo`, `android-test.goyokey`)과 가짜 비밀번호를 정하고 **보안 키로도 잠그기**를 켜서 YubiKey를 등록합니다(PIN 포함, 가능하면 2개). 가짜 항목을 두어 개 넣습니다.
2. **PC에서 열쇠 확인 코드 적어 두기.** '열쇠 관리'에 보이는 `E… · XXXX-XXXX-XXXX-XXXX`입니다. 휴대폰에서 처음 열면 이 코드를 물을 수 있습니다(아래 6).
3. **휴대폰으로 복사.** USB 케이블(파일 전송)로 두 파일을 휴대폰의 `Download` 등에 복사합니다. 클라우드 드라이브나 메신저는 쓰지 마세요.
4. **가져오기.** 환영 화면의 **파일에서 가져오기** → 금고 파일(.goyo) → 열쇠 파일(.goyokey) 순서로 고릅니다. 두 파일은 앱만 읽을 수 있는 곳에 **복사**됩니다. 가져온 뒤 `Download`의 사본은 지우세요.
5. **NFC로 열기.** 비밀번호와 YubiKey PIN을 입력하고 **열기** → "YubiKey를 대거나 꽂으세요"가 나오면 키를 휴대폰 뒷면(NFC 위치)에 대고 끝날 때까지 떼지 마세요. 몇 초 뒤(Argon2) 목록이 나오면 성공입니다.
   **USB-C로 열기.** 같은 순서로 하되 키를 꽂습니다. Android가 USB 접근을 물으면 허용하고, 키가 깜박이면 금속 부분을 만집니다.
6. **처음 연 금고는 읽기 전용.** 보안 키가 있는 금고를 이 휴대폰에서 처음 열면, PC처럼 "이 기기에서 처음 연 금고라 지금은 읽기만 됩니다"가 나옵니다(TOFU). 2에서 적은 코드를 입력하면 고칠 수 있게 됩니다. 확인할 PC가 없을 때만 **코드 없이 이 열쇠 파일 믿기…**를 쓰세요.
7. **확인할 것:** 틀린 PIN(남은 횟수 주의, 한두 번만), 등록하지 않은 다른 YubiKey, 틀린 비밀번호가 각각 알맞은 메시지로 거부되는지. 항목 **복사** 뒤 30초가 지나면 클립보드가 비는지. 홈 버튼을 누르거나 화면을 끄면 바로 잠기는지, 3분 동안 손대지 않으면 잠기는지. 최근 앱 화면과 스크린샷에 내용이 나오지 않는지.

**주의: 동기화를 설정하지 않으면**(아래 '동기화') 휴대폰에서 고친 항목은 휴대폰에만 있고 PC로 가지 않습니다. 그때 PC에서 다시 가져오면 휴대폰의 변경은 사라집니다. PC에서 열쇠를 바꾸면(키 추가·제거, 비밀번호 변경) 두 파일을 다시 가져오세요(열쇠 파일 동기화를 쓰는 금고에서 관문이 필요 없는 변경은 동기화로 받습니다). 다시 가져오면 그 금고의 동기화 폴더는 새로 시작합니다.

앱이 아직 하지 않는 것(4단계 뒤): 키 제거·짝 맺기·모든 키 새로 잠그기·비밀번호 변경·보안 키 켜기/끄기·열쇠 파일 동기화 켜기/끄기, 예전 금고 파일 확인(S-OLDER), 금고 백업과 되살리기, 여러 금고. 이런 상태는 "PC의 고요 금고에서 먼저 연 뒤 다시 가져오세요" 또는 "PC에서 먼저 처리하세요"로 거부하거나 안내합니다.

## OTP 시크릿 (고요 금고 0.12.0)

PC의 0.12.0처럼 항목마다 선택적인 TOTP 시크릿을 둘 수 있습니다(형식은 [FORMAT.md](FORMAT.md)의 'OTP 시크릿', `GOYOVA05`~`08`). 시크릿은 항목의 다른 칸과 함께 금고 파일 안에서 암호화되고, 해석·코드 계산·QR 만들기는 모두 PC와 같은 Rust 코드(`goyo_vault::otp`, `goyo_vault::qr`)가 합니다.

- **항목 화면.** OTP가 있는 항목은 'OTP · 발급자 · 계정'(SHA1·6자리·30초가 아니면 그 설정도)과 지금 코드, "N초 뒤 바뀜"을 보여 줍니다. 코드는 1초마다 Rust에서 기기 시계로 다시 계산합니다(`Native.otpCode`). Kotlin에는 코드와 남은 초만 오고 시크릿은 오지 않습니다.
- **[복사]**: 코드를 '민감' 표시로 복사하고 15초 뒤 클립보드에서 지웁니다.
- **[QR 보기]**: 항목의 otpauth 주소(`Otp::uri`, 계정이 비면 항목 이름)를 라이브러리의 QR 인코더로 만든 모듈을 받아 비트맵(모듈당 1픽셀, 여백 4모듈, 필터 없이 확대)으로 그립니다. 다른 기기의 인증 앱으로 스캔하는 용도입니다. 60초 뒤, [QR 숨기기], 항목을 떠날 때, 잠글 때(앱이 뒤로 가면 잠김) 사라지고, 사라질 때 비트맵 픽셀을 흰색으로 덮습니다. 받은 모듈 배열은 그린 뒤 0으로 지웁니다. `FLAG_SECURE`로 스크린샷과 최근 앱 미리보기에 나오지 않습니다.
- **[시크릿 복사]**: 확인 창에서 '복사'를 누를 때만 Base32 시크릿을 Rust에서 받아 복사하고(15초 뒤 지움) 바이트 배열을 0으로 지웁니다. PC의 '복사 허용'에 해당하는 한 번의 확인입니다.
- **편집기.** 'OTP 시크릿 (선택) · 키 또는 otpauth 주소' 칸(비밀번호 칸처럼 가림)에 사이트가 준 Base32 키나 `otpauth://totp/…` 주소 전체를 넣습니다. 해석과 검사(PC와 같은 거부 문구)는 Rust가 합니다. 이미 OTP가 있는 항목을 고칠 때는 **시크릿을 편집기로 보내지 않습니다**: 칸이 비어 있으면 그대로 두고, 새 키나 주소를 넣으면 바꾸고, 'OTP 시크릿 지우기'를 켜면 지웁니다. 발급자·계정 이름 칸은 따로 없고 otpauth 주소의 이름을 씁니다(이름을 바꾸려면 PC에서).
- **동기화.** OTP가 든 금고는 `GOYOVA06`(보안 키 금고는 `08`)으로 올라갑니다. 서버 스크립트가 0.12.0보다 오래되면 PC처럼 '서버 스크립트 오래됨'으로 보류하니 PC에서 '서버에 설치·업데이트'를 하세요. 0.11.0 이하의 PC는 OTP가 든 금고를 "더 새로운 버전" 금고로 거부합니다.

## 4단계: PC와 같은 시작 화면과 흐름 (앱 0.4.0)

1~3단계 앱은 PC와 전혀 다르게 "금고 가져오기"(금고 파일과 열쇠 파일을 휴대폰으로 복사)로만 시작할 수 있었습니다. 4단계는 PC의 시작 화면과 같은 말로 시작하고, 무엇보다 **서버에서 가져오기**로 휴대폰만으로(PC에서는 한 번의 확인만) 금고를 받아 옵니다. 판단(열쇠 파일 검사, 관문, TOFU, 등록 검사, 열쇠 변경)은 모두 PC와 같은 Rust 라이브러리가 하고, Kotlin은 화면과 YubiKey 통신만 합니다.

### 시작 화면

휴대폰에 무엇이 있는지에 따라 PC처럼 시작 화면이 정해집니다.

| 휴대폰에 있는 것 | 시작 화면 |
| --- | --- |
| 금고 없음 | **환영**: [서버에서 가져오기](맨 위, 권장) · [새 금고 만들기] · [파일에서 가져오기](예전의 두 파일 가져오기) |
| 금고 파일과 열쇠 파일 | **금고 열기**(PC의 로그인): 비밀번호, 보안 키가 있으면 YubiKey PIN 칸과 "이 열쇠 파일은 보안 키가 필요합니다(등록 N개)…", [잠금 해제], 동기화 표시, [동기화 설정], [이 휴대폰에서 금고 지우기…] |
| 서버에서 가져온 금고 파일과 서버의 열쇠 파일(확인 전) | **서버에서 가져온 금고**(PC의 같은 화면): ①②③ 안내, 비밀번호·PIN, [다음 · 보안 키 터치], [열쇠 파일이 있으면 그것으로 열기 (파일에서 가져오기)] |
| 금고 파일만(서버에 열쇠 파일 없음) | **열쇠 파일이 필요합니다**: [열쇠 파일 가져오기 (파일에서 가져오기)], 동기화 설정이 있으면 [서버에서 열쇠 파일 받기] |

`FLAG_SECURE`, 자동 완성 제외, 앱이 뒤로 가면 잠그기, 3분 뒤 잠그기는 그대로입니다. 서버에서 가져오기와 새 금고 만들기 화면은 잠가도(예: [공유…]로 다른 앱에 갔다 와도) 그 화면에 남습니다(열린 금고가 없으므로). 휴대폰에는 금고가 하나만 있으므로, 다른 금고로 바꾸려면 [이 휴대폰에서 금고 지우기…](확인 창)를 먼저 합니다(PC와 서버의 파일은 그대로).

### 서버에서 가져오기 (권장)

PC의 goyo-sync '이 PC로 가져오기' + 고요 금고의 '서버에서 가져온 금고' 화면 + 열쇠 파일 동기화의 첫 받기를 휴대폰에서 합니다. 한 화면에 차례대로 있습니다.

1. **① 서버**: Tailscale 이름(`…ts.net`)이나 100.x 주소, 사용자 이름, 포트(22), 고급 설정(스크립트 경로 `.local/share/goyo-sync/goyo-sync-server.py`, `python3`, PC의 기본값과 같음). [저장].
2. **② 이 휴대폰의 키를 서버에 넣기**: [키 만들기](키 저장소로 감싼 ed25519, 3단계와 같음) → 서버 줄(강제 명령 + 공개 키)이 보이고 [줄 복사], [공유…](Android 공유 창: 메신저·메일·Tailscale 파일 보내기 등으로 PC에 보냄. 공개 키라 비밀이 아닙니다). **PC에서 할 일은 이것 하나뿐입니다**: 줄을 PC의 클립보드에 복사한 채 goyo-sync 설정 창(goyo-sync.exe를 그냥 실행)의 **Android 기기 추가…** → 창이 보여 주는 줄을 확인하고 '예'(3단계 '휴대폰에서 설정' 4와 같음). 이 창은 **그 PC의 목록에 있는 금고 ID**를 `--key-sync=`에 넣으므로, 열쇠 파일 동기화를 켠 금고는 그 PC의 goyo-sync 목록에 있어야 휴대폰이 열쇠 파일을 받을 수 있습니다.
   - QR 코드는 만들지 않았습니다: PC 쪽에 QR을 읽는 기능이 없습니다(goyo-sync는 클립보드를 읽음).
3. **③ 연결 확인**: 처음이면 서버의 호스트 키 지문 창("처음 연결하는 서버")이 나오고, 서버에서 직접 확인한 지문과 같을 때만 [같습니다, 받기]. 다시 [연결 확인] → `연결 정상 · 서버에 금고 N개`.
4. **④ 서버의 금고**: [목록 불러오기] → 금고마다 `금고 TAG`, `서버 버전 · 크기 · 열쇠: 서버에 있음 / 서버에 없음 (PC에서 파일로) / 이 휴대폰 줄에 허용 안 됨 / 알 수 없음`, 금고 ID. 열쇠 파일은 PC 창처럼 처음 4개만 물어봅니다(GETKEY, 아무것도 쓰지 않음). 금고를 누르면 확인 창 → [가져오기].
   - 가져오기는 PC의 `--fetch`와 같은 검사를 거칩니다: 프레임 SHA-256, `GOYOVA0n` 머리글, **요청한 금고 ID와 같은 ID**, 크기 제한(서버 응답 해독 `Response::decode`, 그리고 파일로 쓰기 전에 머리글의 ID를 한 번 더). 금고 파일은 새 파일로만 만들고(이미 있으면 거부), 동기화 폴더가 남아 있어도 거부합니다(PC 규칙과 같음).
   - 이어서 서버의 열쇠 파일을 GETKEY로 받아, 열쇠 파일이 아니라 **동기화 폴더의 열쇠 보기**(`vault.goyo.sync/incoming.goyokeysync`, 줄 0, 답한 요청 없음)로만 저장합니다(PC의 `fetch_key`와 같음). 이 기록은 아무것도 믿지 않고 라이브러리의 검사에만 넘깁니다.
   - 결과: 열쇠 파일까지 받았으면 **서버에서 가져온 금고** 화면으로, 서버에 열쇠 파일이 없거나(열쇠 파일 동기화를 쓰지 않는 금고) 줄이 허용하지 않으면 **열쇠 파일이 필요합니다** 화면으로 갑니다(무엇 때문인지 메시지로 알려 줌).
5. **서버에서 가져온 금고**: 비밀번호와 PIN → [다음 · 보안 키 터치] → YubiKey. 라이브러리의 `prepare_restore_fetched`(금고 파일이 바닥, 이 휴대폰의 열쇠 기록이 붙잡는 파일은 거부, 동기화 폴더 밖에는 아무것도 쓰지 않음) → `restore_with`. 열린 목록 위에 **서버에서 가져온 열쇠 파일 확인** 배너가 나옵니다:
   - **다른 PC의 열쇠 확인 코드**(그 PC의 '열쇠 관리', `E… · XXXX-XXXX-XXXX-XXXX`) → [코드 확인]: `tofu_check` 후 `tofu_save`가 열쇠 파일을 앱 저장소(`vault/vault.goyokey`)에 쓰고 다시 읽어 확인하고, 열쇠 기록(앵커)에 확인을 남기고, 동기화를 시작합니다.
   - 코드를 볼 PC가 없을 때만 **[코드 없이 받기 (이 서버를 믿음)…]**(PC의 S-TOFU-NOPC 확인 창과 같은 경고).
   - 이 휴대폰이 그 상태를 이미 확인했으면 [저장하기]만 나옵니다.
   - 확인 전에는 PC처럼 항목을 고치거나 올리지 않습니다(읽기 전용).
6. **동기화 자동 설정**: 같은 서버 설정과 키로 그 금고의 동기화가 바로 이어집니다(15분 백그라운드 작업도 등록). 서버에서 가져온 금고는 이미 동기화 형식이라 다시 묻지 않습니다. 이 휴대폰의 줄도 이제 그 금고 ID를 `--key-sync=`에 넣어 보여 줍니다.

서버에 열쇠 파일이 없으면: "서버에 이 금고의 열쇠 파일이 없습니다(열쇠 파일 동기화를 쓰지 않는 금고). 열쇠 파일은 PC에서 파일로 가져와야 합니다" → [열쇠 파일 가져오기]로 PC의 `.goyokey`만 고릅니다(USB 케이블로 옮긴 파일; 메신저·클라우드는 쓰지 마세요). 그 뒤 금고 열기 화면에서 열면 1단계처럼 처음 연 금고(TOFU)라 PC의 코드를 묻습니다.

### 새 금고 만들기

PC의 '만들기'와 같은 규칙입니다: 비밀번호(12자 이상, 예측 가능한 조각만으로 된 것 거부: 라이브러리의 `password_policy`)와 확인, **보안 키로도 잠그기**(기본 켜짐; 끄면 경고). 켜면:

- 키마다 MakeCredential 1번 + 확인 GetAssertion 1번(PC 0.11.0과 같은 "확인 1번"). 요청은 라이브러리의 `fido::Registration`이 정합니다: RP `goyo-vault.invalid`/`Goyo Vault`, 새 사용자 ID, 이름 `goyo-<TAG>-<N>-<STAMP>`·`Goyo Vault <TAG> key <N> <STAMP>`, PIN(UV) 필수, credProtect 3 필수, 상주(resident) 자격 증명, ES256/EdDSA, 이미 등록한 키 제외 목록. yubikit으로 그대로 보냅니다.
- 키의 응답(인증자 데이터)은 **Rust가** 읽습니다: 자격 증명 ID는 인증자 데이터에서 꺼내고(Kotlin이 주는 값을 쓰지 않음), 확장 출력이 `hmac-secret: true`와 `credProtect: 3`인지 확인합니다(PC에서 Windows의 `bRequireCredProtect`가 하는 일). 그다음 PC와 같은 `check_credential`(rpIdHash, UP, BE/BS 거부, USB/NFC 전송)과 확인 GetAssertion의 `check_assertion`.
- PIN은 앱의 칸에 입력합니다. PIN이 없는 키는 입력한 PIN으로 정합니다(PC에서 Windows 창이 첫 등록 때 PIN을 정하게 하는 것과 같음).
- 첫 키 다음에 PC의 S-SPARE("예비 키를 지금 등록할까요? (강력 권장)…", 첫 번에는 "키마다 다른 PIN을 쓰세요"도)를 다음 키의 PIN 칸과 함께 묻고, 1개로 끝내면 S-NOSPARE를 묻습니다. 함께 등록한 키끼리 짝을 맺습니다(`finish_with_keys`, PIN 모드). 8개까지.
- 만든 뒤 열쇠 백업을 권합니다: [열쇠 백업…] → 라이브러리의 `backup_key`가 앱 전용 임시 파일(`noBackupFilesDir`)에 쓰고 다시 읽어 확인하고 열쇠 기록에 백업했음을 남김 → Android 저장 창(SAF)에서 고른 곳에 복사 → 임시 파일 삭제. **저장 창이 열리는 동안 앱이 뒤로 가므로 금고를 잠급니다**(그 뒤 다시 여세요).

만든 금고는 휴대폰에만 있습니다. PC에서도 쓰려면 동기화 설정 후 금고를 열면 동기화를 켤지 묻고(3단계), PC에서는 goyo-sync의 '이 PC로 가져오기'로 받습니다(열쇠 파일은 백업한 파일을 USB로, 또는 PC에서 열쇠 파일 동기화를 쓰려면 PC가 필요).

### 관문 (G1 코드, G2 잃어버린 키)

1~3단계는 관문이 필요한 열쇠 파일을 "PC에서 먼저 처리하세요"로 거부했습니다. 4단계는 PC처럼 처리합니다.

- **잠금 해제 때 바뀐 열쇠 파일**(관문 대기 모드): 거부하지 않고 읽기 전용으로 엽니다(PC의 [나중에] 뒤와 같음). 목록 위의 **바뀐 열쇠 파일 확인** 배너가 G2(이 휴대폰이 확인해 둔 상태의 키만 보여 주는 잃어버린 키 고르기: "보안 키 N · 날짜 등록 · 이번에 연 키") 또는 G1(다른 PC의 열쇠 확인 코드)을 묻고, 라이브러리의 `pass_login_gate`가 판단합니다. 잘못 고르면 G2가 꺼지고 이후로는 코드만 받습니다(PC와 같음). 잘못된 코드는 다시 입력할 수 있습니다.
- **다른 기기의 열쇠 변경 받기**(잠금 해제 때): 잠금 해제가 라이브러리의 `login_proved`로 바뀌었습니다. 서버의 열쇠 기록(precheck가 찍어 둔 것)이 이 휴대폰 열쇠 파일의 바로 다음 버전이면(`login_candidate`, 갈라짐 없음) 목록 위에 **다른 기기의 열쇠 변경** 배너가 나옵니다: 관문이 없거나 '열쇠 변경 자동 적용'이면 [받기…]만, 아니면 G1 코드나 G2 고르기 → [다음]. 그다음 잠금 해제의 비밀번호와 터치로 다시 인증(`reauth_from_unlock`)하고, 그 터치의 키로 서버 열쇠 파일을 열고(비밀번호가 바뀌었으면 "그 기기에서 바꾼 새 비밀번호"를 묻고), 미리보기(`adopt_preview_with`, 관문을 바로 그 파일에 대해 판단)의 내용("바뀌는 것: 보안 키 N 추가, 비밀번호 변경됨…, 받은 뒤의 열쇠 확인 코드")을 보여 주고 [받기]면 `adopt`로 씁니다. [나중에]는 아무것도 받지 않고 다음 잠금 해제 때 다시 묻습니다(그동안 동기화는 PC처럼 멈춤).
  - 휴대폰이 아직 묻지 못하는 미리보기(보안 키가 모두 빠지는 결과, 열쇠 파일 동기화 켜기·끄기, 일시 정지되는 키, 양쪽 비밀번호 변경, 이 휴대폰 비밀번호 쓰기 선택)와 갈라진 열쇠 파일, 지금 연 키로 열 수 없는 새 열쇠 파일은 아무것도 쓰지 않고 "PC에서 먼저 받은 뒤 휴대폰에서 다시 여세요"를 보여 줍니다.
  - 동기화 알림 '다른 기기에서 바꾼 열쇠 파일이 서버에 있습니다'는 이제 "금고를 잠근 뒤 다시 열면 받을지 묻습니다"라고 안내합니다.
  - 1~3단계의 잠금 해제(`login_with`)는 서버의 열쇠 변경을 받지 않았습니다(문서는 "다음 잠금 해제의 터치로 받습니다"라고 했지만 실제로는 받지 않았음). 4단계에서 고쳤습니다.

### 열쇠 관리 (기본)

목록 화면의 [열쇠 관리]:

- 상태 줄("보안 키: 켜짐 · PIN 사용 · N개 등록"), 키마다 "보안 키 N · 날짜 등록 · 이번에 연 키 · 모든 키와 짝 / 짝 맺기 필요 / 일시 정지…", "다른 키를 모두 대신할 수 있는 키".
- **열쇠 확인 코드**(`E… · XXXX-XXXX-XXXX-XXXX`, 확인 전에는 보여 주지 않음)와 PC의 설명.
- **[키 추가]**: 현재 비밀번호, 등록된 YubiKey의 PIN, 새 YubiKey의 PIN → 먼저 열쇠 변경을 막는 것이 있으면 그 질문(PC의 관문 질문, 기본 아니요) → **다른 키를 모두 대신할 수 있는 키**로 확인(Reauth: 비밀번호 + 터치) → "새 YubiKey를 준비하세요(꽂아 둔 키는 먼저 빼세요)" → 새 키 등록(위와 같은 MakeCredential + 확인) → 라이브러리의 `rekey(Change::AddKey)`가 새 키를 확인에 쓴 키와 짝지어 씀 → 결과와 열쇠 확인 코드 → 열쇠 백업 권함. 그런 키가 없으면(짝이 덜 맺힘) "PC의 '열쇠 관리 › 짝 맺기'를 먼저 하세요". PC의 S-ADD-PAIR(꽂혀 있는 다른 키도 함께 짝 맺기)는 아직 없습니다.
- **[열쇠 백업…]**: 위 '새 금고 만들기'와 같은 방법.
- 키 제거, 짝 맺기, 모든 키 새로 잠그기, 비밀번호 변경, 보안 키 켜기·끄기, 열쇠 파일 동기화 켜기·끄기는 PC에서 하라고 안내합니다.

### 4단계의 보안 메모 (Windows와 다른 점 추가)

- **등록도 앱이 PIN을 받습니다.** 잠금 해제와 같이(위 'Windows와 보안이 다른 점') PIN은 앱의 칸으로 받고, 쓰고 나면 지웁니다. PIN이 없는 키에는 그 PIN을 설정합니다.
- **credProtect 확인 위치.** PC에서는 Windows가 credProtect 3을 강제하지만, 휴대폰에서는 키가 돌려준 인증자 데이터의 확장 출력을 Rust가 검사합니다(없거나 3이 아니면 등록하지 않음). 그 키에 이미 만들어진 상주 자격 증명은 남을 수 있습니다(키 관리 도구로 지울 수 있음).
- **흐름 중의 비밀.** 새 금고의 비밀번호, 키 추가의 비밀번호와 Reauth, 잠금 해제의 터치(다른 기기의 열쇠 변경을 받을 때까지)는 Rust 메모리에만 있고, 흐름이 끝나거나 잠그면(앱이 뒤로 가면) 0으로 지워집니다. 다른 기기의 열쇠 변경을 기다리는 동안에는 그 잠금 해제의 터치 출력이 메모리에 남습니다(PC는 같은 흐름의 대화상자 동안 남김).
- **열쇠 백업 임시 파일.** 백업은 앱 전용 저장소의 임시 파일을 거쳐 SAF로 복사한 뒤 지웁니다(취소해도 지움). 열쇠 파일 자체는 비밀번호와 YubiKey로 잠겨 있습니다.
- **서버 줄 공유.** [공유…]는 공개 키 줄만 보냅니다. 개인 키는 여전히 키 저장소 밖으로 나가지 않습니다.

### PC에서 할 일 (요약)

1. 서버 스크립트가 최신인지: PC goyo-sync 설정 창의 '서버에 설치·업데이트'(0.12.0 이상).
2. 휴대폰이 보여 주는 줄을 PC로 보내 클립보드에 넣고, goyo-sync 설정 창의 **Android 기기 추가…** → '예'. (열쇠 파일까지 받으려면 그 금고가 그 PC의 goyo-sync 목록에 있고 PC에서 '열쇠 파일 동기화'를 켰어야 합니다.)
3. 휴대폰이 묻는 **열쇠 확인 코드**: PC 고요 금고의 '열쇠 관리'에 보이는 코드를 읽어 휴대폰에 입력.

### 자동 시험 (4단계)

- `cd android\rust; cargo test`(30개): 위 3단계 시험에 더해, **진짜 서버 스크립트**를 상대로 휴대폰이 서버의 금고 목록(키 파일 있음/줄에 허용 안 됨)을 보고, PC 금고의 최신 버전을 새 파일로 가져와 PC의 열쇠 파일로 열고, 이미 있는 파일과 서버에 없는 ID를 거부하고, 열쇠 파일 동기화 금고(GOYOKS01 시험 파일)의 열쇠 기록을 열쇠 보기로 저장해 라이브러리의 `fetched_key`/`fetched_key_info`가 읽는지(`fetch_tests`); YubiKey 등록의 인증자 데이터 해석(자격 증명 ID, COSE 건너뛰기, hmac-secret·credProtect 3 필수, 잘린 데이터·중복 키·잘못된 형식 거부, 동기화 패스키는 코어가 거부; `reg`); MakeCredential 요청 전송 형식; **가짜 인증자**(라이브러리의 시험용 `fido::fake`)로 보안 키 2개 새 금고 만들기(제외 목록 포함) → 연 뒤 키 추가(틀린 비밀번호의 Reauth 거부) → 세 키 모두로 열기, 비밀번호만 금고 만들기와 덮어쓰기 거부(`flows`); G2 고르기의 번호 해석(`pick_of`).
- 다른 기기의 열쇠 변경 받기(`take.rs`)는 라이브러리의 `login_proved`·`login_candidate`·`adopt` 시험(PC와 같은 코드)에 기대고, 이 다리 자체의 끝까지 시험(열쇠 파일 동기화 금고 두 개를 만드는 시험 서버)은 아직 없습니다. 기기에서 확인이 필요합니다.
- 기기 시험(`connectedDebugAndroidTest`)은 앱을 지우므로(가져온 금고도 지워짐) 실제 사용 휴대폰에서는 돌리지 마세요.

### 직접 해 볼 것 (4단계, 시험 금고로)

1. 휴대폰에 금고가 없는 상태에서 환영 화면의 세 버튼과 설명이 나오는지.
2. **서버에서 가져오기**: ①~③(위), PC에서 'Android 기기 추가…', ④ 목록에 PC의 금고와 '열쇠: 서버에 있음'이 보이는지 → 가져오기 → '서버에서 가져온 금고' 화면 → 비밀번호·PIN·YubiKey(NFC, USB-C) → 배너에 PC의 코드 입력 → 저장 메시지, 그 뒤 '금고 열기' 화면으로 다시 열리는지, PC와 '동기화됨 · 확인 코드'가 같은지. 틀린 코드가 거부되는지.
3. 열쇠 파일 동기화를 쓰지 않는 금고로 2를 하면 '열쇠 파일이 필요합니다' 화면이 나오는지, [열쇠 파일 가져오기]로 PC의 `.goyokey`를 고른 뒤 열리는지(TOFU 코드).
4. **새 금고 만들기**: 짧은 비밀번호·다른 확인이 거부되는지, YubiKey 2개 등록(NFC 하나, USB-C 하나), PIN 없는 키에 PIN이 정해지는지, 같은 키를 두 번 대면 거부되는지, 만든 뒤 열쇠 백업 저장 창.
5. **키 추가**: 3번째 키를 추가하고, 그 키로 열리는지, PC에서 그 변경을 받을 때 휴대폰의 열쇠 확인 코드를 입력하는지.
6. PC에서 키를 추가(또는 비밀번호 변경)한 뒤 휴대폰을 열면 '다른 기기의 열쇠 변경' 배너가 나오고, PC의 코드로 받은 뒤 다시 동기화되는지. PC에서 키를 제거한 뒤에는 G2(잃어버린 키 고르기)가 나오는지.

## Windows와 보안이 다른 점

같은 파일 형식, 같은 암호(Argon2id 256 MiB, XChaCha20-Poly1305, YubiKey hmac-secret)이고, YubiKey 요청도 PC와 같습니다(RP ID `goyo-vault.invalid`, 소금을 해시 없이 그대로, PIN(UV) 필수). 키의 응답은 PC와 같은 코어 검사(`fido::check_assertion`: 요청한 자격 증명인지, rpIdHash, UP, UV, BE/BS 거부, USB/NFC 전송)를 거친 뒤에야 열쇠 파일을 엽니다. 다른 점은 다음과 같습니다.

- **PIN을 앱이 받습니다.** PC에서는 Windows의 보안 창이 PIN을 받지만, Android에는 그런 시스템 창이 없어 앱의 입력 칸에 넣고 yubikit이 키에 보냅니다. 앱은 PIN을 저장하지 않고 쓰고 나면 지웁니다. 그래도 키보드 앱(IME)은 입력을 봅니다.
- **키보드(IME).** 비밀번호·PIN·비밀정보 칸은 비밀번호 입력 칸(자동 수정·학습 끔)이지만, 무엇을 하는지는 키보드 앱에 달렸습니다. 클라우드 동기화나 '입력 학습'을 하는 서드파티 키보드는 쓰지 마세요.
- **자동 완성(비밀번호 관리자).** 앱 창 전체를 자동 완성에서 뺐습니다(`IMPORTANT_FOR_AUTOFILL_NO_EXCLUDE_DESCENDANTS`). 개발 중 이것이 없을 때는 Google 자동 완성이 비밀정보 칸에 "비밀번호 잠금 해제" 제안을 띄웠고, 그 사이 입력이 깨졌습니다(공백이 든 비밀번호가 틀림). 다른 자동 완성 앱을 쓴다면 이 앱에서 아무것도 제안·저장하지 않는지 확인하세요.
- **접근성 서비스.** 화면 읽기나 자동화 앱처럼 접근성 권한을 받은 앱은 화면 글자와 입력 칸을 읽을 수 있고, `FLAG_SECURE`로도 막지 못합니다. Compose의 비밀번호 칸은 접근성 트리에 **실제 글자**를 내놓습니다(개발 중 `uiautomator dump`로 확인). 믿지 않는 접근성 서비스는 꺼 두세요.
- **화면.** 모든 창(대화상자 포함)에 `FLAG_SECURE`를 켜서 스크린샷, 화면 녹화, 최근 앱 미리보기를 막습니다. 앱이 뒤로 가거나 화면이 꺼지면 바로, 3분 동안 손대지 않으면 잠급니다.
- **같은 곳에 있는 두 파일.** PC에서는 열쇠 파일을 USB에 따로 둘 수 있지만, 휴대폰에서는 금고 파일과 열쇠 파일이 같은 앱 저장소에 있습니다. 휴대폰을 통째로 가진 사람에게 남는 장벽은 비밀번호와 YubiKey(와 PIN)입니다. 보안 키 없는 금고(비밀번호만)는 휴대폰에서 PC보다 약하니, 휴대폰에는 **보안 키를 켠 금고만** 가져오기를 권합니다.
- **샌드박스.** 가져온 파일과 이 기기의 열쇠 기록(`GoyoVault/goyo-vault.keys`, PC의 `%LOCALAPPDATA%\GoyoVault`에 해당)은 앱 전용 저장소에 있어 다른 앱이 읽지 못합니다. 앱을 지우거나 '데이터 삭제'를 하면 열쇠 기록도 사라지고, 다시 가져오면 처음 연 금고(TOFU)가 됩니다.
- **루팅·부트로더 해제.** 루팅한 휴대폰이나 악성 루트 앱은 앱 저장소와 열려 있는 금고의 메모리를 읽을 수 있습니다. 잠긴 상태의 파일은 여전히 비밀번호와 YubiKey가 지키지만, 연 동안의 내용은 지키지 못합니다. 루팅한 휴대폰에서는 쓰지 마세요.
- **백업 꺼짐.** `allowBackup=false`이고 클라우드 백업과 기기 간 이전 규칙도 모두 제외합니다. 새 휴대폰으로는 옮겨지지 않으니 PC에서 다시 가져오세요.
- **네트워크.** 1단계 앱에는 인터넷 권한이 없었습니다. 3단계부터 동기화(아래)의 SSH 연결에만 인터넷을 쓰고, Tailscale 주소가 아니면 연결하지 않습니다. 동기화를 설정하지 않으면 네트워크를 쓰지 않습니다.
- **난수.** PC는 CPU의 RDSEED만 씁니다. ARM에는 앱이 쓸 RDSEED가 없어서, Android에서는 커널 난수(getrandom(2), 풀이 처음 채워질 때까지 기다림)를 같은 SHA-512 조건화를 거쳐 씁니다. 실패하면 더 약한 난수로 대체하지 않고 멈춥니다.
- **클립보드.** 복사한 비밀정보는 '민감' 표시(Android 13 이상에서 미리보기·키보드 제안에서 숨김)를 하고 30초 뒤 지웁니다(OTP 코드와 OTP 시크릿은 PC처럼 15초). Android 10~12(예: LG G7)는 이 표시를 모르므로, 키보드의 클립보드 기록 기능이 사본을 남길 수 있습니다. 앱이 뒤에 있을 때는 클립보드를 읽을 수 없어, 그 30초 안에 다른 앱에서 복사한 것도 함께 지울 수 있습니다.
- **메모리.** Rust 쪽 비밀(비밀번호 사본, 키, hmac-secret 출력)은 다 쓰면 0으로 지웁니다. Kotlin 쪽은 바이트 배열을 지우지만, 입력 칸과 화면에 보인 글자(Java 문자열)는 지울 수 없고 가비지 컬렉터가 치울 때까지 메모리에 남을 수 있습니다.
- **파일 저장.** 임시 파일에 쓰고 fsync한 뒤 rename(2)으로 바꾸고 폴더도 fsync합니다. 링크를 따라가지 않고(O_NOFOLLOW) 읽고, 파일 잠금은 flock입니다. Android는 앱이 하드 링크를 만드는 것을 막아서, "새 파일만 만들기" 저장은 고요 금고의 파일 잠금 안에서 확인 후 rename하는 두 단계로 합니다(1단계 앱은 이 저장을 쓰지 않습니다).

## 동기화 (3단계, Tailscale 전용)

PC의 goyo-sync와 **같은 서버, 같은 서버 스크립트, 같은 엔진**으로 휴대폰도 동기화합니다. 규칙은 하나입니다: **Tailscale로만 동기화하고, 그 밖의 경로는 거부합니다.**

- 동기화 엔진(서버와 주고받는 단계 P0~P7, 열쇠 파일 단계 KR·KG·KP, `status`·`helper.state`·`kview` 파일)은 goyo-sync.exe에서 라이브러리(`goyo_vault::syncengine`)로 옮겼습니다. Windows는 지금도 `ssh.exe`를 실행하고, 휴대폰은 같은 엔진을 앱 안의 SSH 클라이언트로 돌립니다. 요청 형식, 크기 제한, 서버 스크립트(`goyo-sync-server.py`)는 PC와 똑같습니다.
- 휴대폰의 동기화는 **암호화된 금고 파일만** 서버와 앱의 동기화 폴더(`vault.goyo.sync`) 사이에서 옮깁니다. 합치기와 올릴 사본 만들기는 PC처럼 **열린 금고**(고요 금고 앱의 몫)가 2초마다 합니다.

### 준비

1. **서버**: PC에서 goyo-sync로 이미 쓰는 서버면 됩니다([SYNC.md](SYNC.md)). 서버도 Tailscale에 들어 있어야 합니다. PC의 goyo-sync 설정 창에서 '서버에 설치·업데이트'로 서버 스크립트를 최신으로 맞추세요(휴대폰은 스크립트를 설치하지 않습니다).
2. **휴대폰**: Play 스토어의 Tailscale 앱을 설치하고 같은 tailnet에 로그인한 뒤 켭니다. MagicDNS를 켜 두면 서버를 `my-server.tail1234.ts.net` 같은 이름으로 적을 수 있습니다.
3. 서버의 SSH 호스트 키 지문을 서버에서 직접 확인해 적어 둡니다: `ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub` (예: `256 SHA256:… root@my-server (ED25519)`).

### 휴대폰에서 설정

1. 금고 열기 화면(또는 열린 목록)의 **동기화 설정 (Tailscale)**. 휴대폰에 금고가 없으면 환영 화면의 **서버에서 가져오기**가 같은 설정으로 시작합니다(아래 '4단계').
2. **서버**에 Tailscale 이름(`…ts.net`)이나 Tailscale 주소(`100.x.y.z`)를 적고, **사용자 이름**, **포트**(보통 22)를 적습니다. 스크립트 경로와 파이썬 명령은 PC의 고급 설정과 같게 둡니다(기본값 `.local/share/goyo-sync/goyo-sync-server.py`, `python3`). **저장**.
3. **키 만들기**: 이 휴대폰 전용 ed25519 키를 만듭니다. 아래에 서버의 `authorized_keys`에 넣을 줄이 나옵니다(PC의 줄과 같은 형식).
   ```
   restrict,command="python3 -I .local/share/goyo-sync/goyo-sync-server.py serve --key-sync=<금고 ID>" ssh-ed25519 AAAA… goyo-sync android-<모델>
   ```
   `--key-sync=`에는 이 휴대폰에 가져온 금고의 ID가 들어갑니다. **줄 복사**로 복사합니다(공개 키라 비밀이 아닙니다).
4. **서버에 줄 넣기** (둘 중 하나):
   - **PC에서(권장)**: 복사한 줄을 PC로 보냅니다(메신저, 메일, Tailscale의 파일 보내기 등). PC에서 그 줄을 클립보드에 복사한 채 goyo-sync 설정 창(보안 키 빌드)의 **Android 기기 추가…** 를 누릅니다. 창이 줄에서 **ssh-ed25519 키와 기기 이름만** 꺼내(이름은 영문·숫자·`. _ -`), **이 PC의** 스크립트 경로·파이썬 명령·목록 금고 ID로 줄을 다시 만들어 보여 주고 한 번 묻습니다(기본 '아니요'). '예'면 PC의 '서버에 설치·업데이트'와 같은 방법(평소 ssh 로그인으로 서버 스크립트의 `authorize`, 줄은 표준 입력으로)으로 넣습니다. 서버 스크립트는 그 줄을 다시 검사하고, 같은 키가 강제 명령 없이 있으면(평소 로그인 키) 아무것도 바꾸지 않습니다. 넣기 전에 `authorized_keys.goyo-backup`으로 백업합니다.
   - **직접**: 서버의 `~/.ssh/authorized_keys`에 그 줄을 한 줄로 붙여 넣습니다. 파이썬 경로는 서버에서 `command -v python3`로 확인하세요.
5. 휴대폰에서 **연결 확인**. 처음에는 "처음 연결하는 서버" 창에 서버의 호스트 키 지문(`SHA256:…`, OpenSSH와 같은 형식)이 나옵니다. 준비 3에서 적은 지문과 **글자 하나까지** 같을 때만 **같습니다, 받기**를 누릅니다. 그 키가 이 서버(이름과 포트)에 고정되고, 다시 **연결 확인**을 누르면 `연결 정상 · 서버에 금고 N개`가 나와야 합니다. 아무것도 쓰지 않는 확인입니다(PC의 연결 확인처럼 512바이트 왕복과 금고 목록).
6. 금고를 엽니다. 열 때 한 번 동기화하고, PC처럼 처음이면 동기화 형식으로 바꿀지 묻습니다(이미 PC에서 동기화하는 금고는 묻지 않습니다). 목록 위의 **동기화:** 줄이 상태입니다.

### 언제 동기화하나요

- 금고를 열 때, 항목을 저장하거나 지운 직후, **지금 동기화**를 누를 때.
- 금고가 열려 있는 동안: 엔진이 할 일이 있다고 할 때(서버 확인 60초 간격, 상태 기록, 실패 뒤 재시도). 열린 금고는 2초마다 받은 사본을 합치고 올릴 사본을 씁니다.
- 백그라운드: WorkManager가 **15분마다**(네트워크 연결이 있을 때) 한 번. 이때는 **금고를 열지 않고** 암호화된 파일만 옮깁니다. 받은 사본은 다음에 금고를 열 때 합쳐집니다. 휴대폰의 절전 정책에 따라 15분보다 늦어질 수 있습니다.
- Tailscale(VPN)이 꺼져 있으면 이름을 찾지도 않고 넘어갑니다(`Tailscale 아님`).

### 열쇠 파일 동기화와 관문

열쇠 파일을 서버로 동기화하는 금고(보안 키 + '열쇠 파일 동기화')도 엔진은 PC와 똑같이 `kreq`(앱의 요청)를 보내고 서버의 기록을 `kview`에 받습니다. 받은 열쇠 파일을 **받아들이는 판단**은 라이브러리(금고 쪽)가 PC와 같은 관문으로 합니다:

- 4단계부터 다른 기기의 열쇠 변경은 **다음 잠금 해제 때** 받습니다(아래 '4단계 › 다른 기기의 열쇠 변경 받기'): 관문이 없으면 [받기…]만, 관문이 있으면 G1(그 기기의 열쇠 확인 코드)이나 G2(잃어버린 키 고르기)를 먼저 묻습니다. 그때까지 휴대폰은 PC처럼 올리지도 합치지도 않고, 서버의 열쇠 파일은 동기화 폴더에 그대로 둡니다.
- 휴대폰이 아직 받지 못하는 변경(갈라진 열쇠 파일, 두 기기의 키 제거 합치기, 보안 키를 끈 결과, 열쇠 파일 동기화 켜기·끄기, 일시 정지되는 키, 양쪽 비밀번호 변경)은 "PC에서 먼저 처리하세요"를 보여 줍니다. PC가 받은 뒤 휴대폰을 다시 열면 PC의 결과를 받습니다.
- 휴대폰에서 키를 추가하면(4단계 '열쇠 관리') 새 열쇠 파일을 PC처럼 동기화 엔진이 올립니다(열쇠 파일 동기화를 쓰는 금고). 다른 PC는 '열쇠 관리'의 받기에서 휴대폰의 열쇠 확인 코드를 입력합니다.

### 보안 모델과 Windows와 다른 점

**같은 것**: 서버 스크립트와 그 검사(강제 명령, `--key-sync`, 열쇠 파일 검사, 크기 제한, 시간 제한), 요청 형식, 업로드 관문(링크·하드 링크·폴더 거부, `GOYOSOU1`로 싼 이 금고의 `GOYOVA02/04`, OTP가 있으면 `06/08`만), 엔진의 모든 단계와 재시도·보류 규칙, 금고 쪽 합치기와 열쇠 관문, 모르는/바뀐 호스트 키 거부, 평소 로그인과 분리된 전용 키와 강제 명령. 엔진은 금고 파일과 열쇠 파일을 열지 않습니다.

**다른 것**:

- **Tailscale 전용.** 연결 전에 서버 이름을 한 번만 풀고, 나온 주소가 **모두** Tailscale 주소(`100.64.0.0/10`, `fd7a:115c:a1e0::/48`)일 때만 바로 그 주소로 연결합니다(다시 풀지 않음). 연결된 소켓의 휴대폰 쪽 주소도 Tailscale 주소여야 하고, 앱은 VPN 네트워크가 켜져 있을 때만 시작합니다. PC의 goyo-sync에는 이 제한이 없습니다(PC는 ssh 설정을 따릅니다).
  - 한계: `100.64.0.0/10`은 통신사의 CGNAT도 쓰는 대역이라, 주소 검사만으로는 Tailscale과 통신사 망을 완전히 구별하지 못합니다. 실제로 서버를 확인하는 것은 **고정된 호스트 키**입니다. 처음 받을 때 지문 비교를 건너뛰지 마세요.
- **SSH 클라이언트.** OpenSSH 대신 Rust의 russh(0.57.1, 암호는 ring)를 앱 안에 넣었습니다. Windows 빌드에는 들어가지 않습니다(android/rust만 씀). RSA, zlib 압축, 비밀번호·키보드 인증, 에이전트, 포워딩, PTY는 쓰지 않고 exec 채널 하나만 엽니다. 서버의 호스트 키는 **ed25519나 ECDSA**여야 합니다(일반 Linux 서버는 ed25519 키가 있습니다).
- **호스트 키.** PC는 `known_hosts`(호스트 이름별)를 쓰고, 휴대폰은 앱 저장소의 고정 키(서버 이름과 포트별, `sync/host_key`)를 씁니다. 처음 받을 때 반드시 지문을 보여 주고 확인을 받습니다(PC의 `accept-new`는 저장한 뒤에 지문을 보여 줌). 바뀐 키는 PC처럼 거부하고, 앱에는 받아들이는 버튼이 없습니다.
- **클라이언트 키.** 휴대폰에서 만든 ed25519 키의 개인 부분(32바이트)은 Android 키 저장소의 AES-256-GCM 키(있으면 StrongBox, 없으면 TEE)로 감싸서만 저장합니다(`sync/client_key.enc`). 키 저장소의 키는 밖으로 나오지 않고 사용자 인증을 요구하지 않습니다(화면이 잠겨 있어도 백그라운드 동기화가 되도록). 개인 키는 내보내기·표시·백업이 없고, 동기화 한 번에만 풀어 Rust로 넘기고 0으로 지웁니다. PC의 전용 키(암호 없음, Windows 계정 권한으로 보호)보다 약하지 않지만, **루팅된 휴대폰**이나 앱 권한으로 코드를 실행하는 공격자는 키 저장소에 풀어 달라고 할 수 있습니다(키 파일을 복사하지는 못해도 쓰는 것은 막지 못함). 휴대폰을 잃어버리면 서버의 `authorized_keys`에서 그 줄(`goyo-sync android-<모델>`)을 **바로** 지우세요.
- **줄의 `--key-sync`.** 휴대폰 화면의 줄은 휴대폰에 가져온 금고 ID를, PC의 'Android 기기 추가'는 **PC 목록의 금고 ID 모두**를 넣습니다(PC의 '서버에 설치·업데이트'와 같음). 이 휴대폰의 키를 훔친 사람은 그 금고들의 열쇠 파일을 받을 수 있고 업로드를 막을 수 있습니다([SECURITY_KEY.md](SECURITY_KEY.md)의 '무엇을 감수하나요'와 같음). 줄이려면 줄을 손으로 관리하세요.
- **백그라운드.** PC 도우미는 로그인해 있는 동안 60초마다 서버를 확인하지만, 휴대폰은 금고가 열려 있는 동안(60초)과 15분마다만 확인합니다. 그래서 서버는 휴대폰이 언제 켜져 있는지 덜 자세히 압니다. 그 대신 휴대폰은 다른 기기의 변경을 늦게 받을 수 있어, 금고를 열 때마다 먼저 한 번 동기화합니다.
- **권한.** 이제 INTERNET(동기화 SSH 연결만)과 ACCESS_NETWORK_STATE(VPN 확인, WorkManager의 네트워크 조건) 권한이 있습니다. WorkManager가 부팅 뒤 작업을 다시 잡는 권한(RECEIVE_BOOT_COMPLETED, WAKE_LOCK, FOREGROUND_SERVICE)도 합쳐집니다. 네트워크를 쓰는 다른 코드는 없습니다.
- **로그.** 엔진의 기록은 PC의 goyo-sync.log처럼 앱 저장소의 `sync/goyo-sync.log`에 남습니다(서버 이름과 시각, 파일 내용과 비밀은 없음). 밖으로 내보내지 않습니다.
- **같은 기기의 두 실행.** 화면의 동기화와 백그라운드 작업이 겹치면 PC의 `--once`와 도우미처럼 동기화 폴더의 잠금(`helper.lock`, flock)으로 차례를 지킵니다.
- **Unix 파일 시각.** Windows의 변경 감지는 파일 생성 시각을 쓰는데 Android에는 그것이 없고 수정 시각도 거칠어서, 동기화 폴더의 변경 감지(`syncfile::Stamp`)는 Unix에서 파일 번호(st_dev, st_ino)를 함께 보고, 동기화 파일을 바꿀 때마다 수정 시각을 이전 파일보다 뒤로(나노초 단위) 정합니다.

### 자동 시험

- PC: `python -X utf8 scripts/run_checks.py`(엔진을 옮긴 뒤에도 Windows 시험 모두 통과), `python -X utf8 scripts/mutate.py --check`.
- `cd android\rust; cargo test`: OTP의 JNI 쪽 함수(`entry_otp`: RFC 6238 코드와 남은 초, 이름과 설정 표시, 편집기의 유지·교체·삭제와 거부, QR 모듈이 라이브러리 기호와 같은지), 금고 ID를 `GOYOVA01`~`08` 머리글에서 읽는지, Tailscale 주소 판정(100.63.255.255 / 100.64.0.0 / 100.127.255.255 / 100.128.0.0, IPv6), 호스트 키 고정과 지문 형식, 서버 줄 형식, 설정 검사, 그리고 **진짜 서버 스크립트**(`python server/goyo-sync-server.py serve`를 파이프로)를 상대로 휴대폰과 PC가 금고를 주고받는 엔진 시험과 열쇠 파일 PUTKEY·GETKEY·CUTKEY·`--key-sync` 없는 줄 시험, 연결 전에 거부하는 경우(Tailscale 아님, 이름 없음, 키 없음), 그리고 시험 안에서 띄운 **진짜 SSH 서버**(127.0.0.1의 russh 서버가 exec마다 서버 스크립트를 실행)를 상대로 처음 보는 호스트 키(지문을 보여 주고 아무것도 보내지 않음), 고정 뒤 HELLO 512바이트 왕복과 LIST, 다른 키로 고정된 서버 거부, 모르는 클라이언트 키의 인증 실패, SSH 위의 엔진 업로드. 127.0.0.1은 시험 빌드에만 있는 스위치로만 허용하고 앱에는 그 스위치가 없습니다. 파이썬이 없으면 실패합니다(`GOYO_SYNC_SKIP_PYTHON=1`이면 건너뜀). 네트워크 연결은 하지 않습니다.
- 기기: `.\gradlew.bat connectedDebugAndroidTest`의 `SyncTest`: 키 저장소로 감싸고 푸는 왕복(바뀐 바이트 거부, 키를 꺼낼 수 없음), 새 키의 저장과 줄, 설정 검사, Tailscale이 아닌 주소를 연결 없이 거부.

### 직접 해 볼 것 (실제 서버까지)

자동 시험은 실제 SSH 서버에 붙지 않습니다. 아래를 **시험 금고로** 해 보세요.

1. PC에서 시험 금고를 만들고 goyo-sync로 동기화를 켜 서버에 올립니다(보안 키 금고면 '열쇠 파일 동기화'도 켜 볼 수 있음).
2. 두 파일을 휴대폰으로 가져옵니다(위 '직접 해 볼 것' 3~4).
3. 위 '휴대폰에서 설정' 1~5. 지문 확인 창이 나오는지, '받지 않기'면 연결하지 않는지, 고정된 호스트 키를 지우면 다시 묻는지, Tailscale을 끄면 'Tailscale 아님'이 되는지, 서버 칸에 LAN 주소(192.168.x.x)를 적으면 연결하지 않는지 확인합니다. (서버의 호스트 키가 바뀐 경우의 거부는 서버 쪽 키를 바꿔야 해서 자동 시험의 고정 판정 시험으로만 확인했습니다.)
4. 휴대폰에서 금고를 열고 항목을 추가 → PC의 고요 금고에 몇 분 안에 합쳐지는지, PC에서 고친 항목이 휴대폰에서 열 때(또는 열린 동안 1분 안에) 보이는지, 두 기기의 '동기화됨 · 확인 코드'가 같은지 봅니다.
5. 휴대폰 화면을 끄고 15~30분 뒤 서버 로그나 PC의 '서버의 금고 목록'에서 휴대폰이 확인했는지(`sync/goyo-sync.log`는 `adb`로만 보입니다) 봅니다.
6. 보안 키 금고에서 PC가 비밀번호를 바꾼 뒤 휴대폰에서 열면 새 열쇠 파일을 받는지, 키를 추가한 뒤에는 다음 잠금 해제 때 '다른 기기의 열쇠 변경' 배너가 나오는지(4단계) 확인합니다.
7. 끝나면 서버의 `authorized_keys`에서 시험한 휴대폰 줄을 지우세요(계속 쓸 휴대폰이 아니라면).

## 알려진 위험과 남은 일

- 실제 YubiKey(NFC, USB-C)로 여는 것은 아직 사람이 확인해야 합니다(위 '직접 해 볼 것'). 파일 가져오기(SAF 파일 선택 창)도 사람이 확인해야 합니다. 개발 중에는 비밀번호만 쓰는 시험 금고를 `run-as`로 앱 저장소에 넣고 화면을 adb로 눌러, 열기(공백 든 비밀번호 포함)·항목 보기·복사·추가·잠그기·뒤로 가면 잠김을 확인했고, 화면 캡처는 `FLAG_SECURE` 때문에 빈 파일이 되었습니다.
- 여러 자격 증명이 든 YubiKey에서 어느 것이 이 금고 것인지는 PIN 토큰으로 조용히 미리 묻고(up=false) 고릅니다. yubikit 자체 클라이언트와 같은 방식입니다.
- (해결) Unix에는 파일 생성 시각이 없고 수정 시각이 거칠던 문제: 동기화 폴더의 변경 감지가 파일 번호와 앞으로만 가는 수정 시각을 씁니다(아래 '동기화').
- OTP 화면(코드 갱신, 복사 뒤 15초에 지움, QR 60초·떠날 때·잠글 때 숨김)은 기기에서 사람이 확인해야 합니다(JNI 함수는 `cargo test`와 `VaultTest`로 확인). OTP 코드는 기기 시계를 쓰니 시계가 틀리면 코드도 틀립니다.
- 동기화의 남은 위험: 실제 서버와 끝까지 주고받는 것은 사람이 확인해야 합니다(위 '직접 해 볼 것 (실제 서버까지)'). russh는 OpenSSH만큼 오래 검증된 구현이 아닙니다. `100.64.0.0/10`은 통신사 CGNAT와 겹치므로 호스트 키 지문 확인이 진짜 방어입니다. 휴대폰의 동기화 키는 루팅이나 앱 권한을 얻은 공격자가 키 저장소로 쓸 수 있습니다(서버 줄을 지우는 것이 대응).
- 4단계의 남은 위험과 일:
  - YubiKey 등록(MakeCredential, PIN 설정, credProtect·hmac-secret 응답), 서버에서 가져오기의 실제 서버 왕복, 서버에서 가져온 금고의 코드 확인과 저장, 관문 배너, 다른 기기의 열쇠 변경 받기는 **실제 기기와 키로 아직 확인하지 않았습니다**(자동 시험은 가짜 인증자와 진짜 서버 스크립트까지). 위 '직접 해 볼 것 (4단계)'를 시험 금고로 해 주세요.
  - 다른 기기의 열쇠 변경 받기의 끝까지 시험이 없습니다(라이브러리 시험에 기댐). 휴대폰이 묻지 못하는 경우는 아무것도 쓰지 않고 PC로 보냅니다.
  - 잠금 해제가 실패했을 때 서버의 새 열쇠 파일로 열어 보는 PC의 길(S-TRY-SERVER-KEY: 다른 기기에서 비밀번호를 바꾼 뒤 새 비밀번호로 열기, S-TRY-OTHERKEY)은 아직 없습니다. 그 경우 예전 비밀번호로 열면 [받기]에서 새 비밀번호를 묻습니다.
  - 키 추가는 '다른 키를 모두 대신할 수 있는 키'의 터치 하나로만 하고, PC의 S-ADD-PAIR(다른 키도 함께 짝 맺기)와 Reauth 갱신은 없습니다. 키 제거·짝 맺기·비밀번호 변경·보안 키 켜기/끄기·열쇠 파일 동기화 켜기/끄기는 PC에서.
  - 열쇠 백업의 SAF 저장 창을 여는 동안 앱이 뒤로 가서 금고를 잠급니다(의도한 동작).
  - 한 휴대폰에 금고는 하나입니다. 영어 화면은 없습니다.
